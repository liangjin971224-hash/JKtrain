## 一、这份脚本在做什么

用 LoRA 把 Qwen2.5-1.5B 调成一个「会按门店合规口径说话」的助手：见到违规表述能指出问题并给出正确说法，遇到资料不足会说没有，涉及用药会劝退。

**不做什么**：不做知识注入。产品信息、法规条文都在检索里，模型只负责「怎么说」。

## 二、与原脚本的对照

沿用原脚本的训练方式，只有 4 处必要差异。

| 参数 | 原脚本 | 本脚本 | 为什么改 |
|---|---|---|---|
| `max_seq_length` | 256 | **384** | 见下方「关键修正 1」 |
| `num_train_epochs` | 5 | **3** | 459 条数据 5 轮易过拟合 |
| 对话模板 | user + assistant | **加 system** | 见「关键修正 2」 |
| warmup | `steps=200` | `ratio=0.1` | 步数基数变了 |

**保持不变的核心参数**（原脚本已验证有效，不动）：

```
LoraConfig(r=16, lora_alpha=32, lora_dropout=0.1, bias="none",
           task_type="CAUSAL_LM",
           target_modules=[q,k,v,o,gate,up,down_proj])
per_device_train_batch_size = 1      # 8GB 显存
gradient_accumulation_steps = 4      # 等效 batch 4
learning_rate = 1e-4
gradient_checkpointing = True        # 用重算换显存
max_grad_norm = 0.3
bf16 = True, fp16 = False
lr_scheduler_type = "cosine"
```

`r=16 / alpha=32` 是原脚本注释里写的「经大量实验，无特殊要求就 16」，本项目任务单一（话术合规），不需要 32。

## 三、关键修正 1：`max_seq_length` 从 256 提到 384

**原脚本 256，本项目不能用。**

实测 120 条样本的 token 分布（含 system）：

| 分位 | token 数 |
|---|---|
| P50 | 219 |
| P75 | 238 |
| P90 | 307 |
| P99 | 322 |
| **最大** | **328** |

| max_seq_length | 截断比例 |
|---|---|
| 256 | **14%** |
| 384 | **0%** |

**为什么截断在这里特别致命**：对话模板的顺序是 `system → user → assistant`，被截掉的总是**末尾的 assistant 部分**，也就是答案。模型只会学到「问题和资料长什么样」，学不到「该怎么答」——**等于白训，而且 loss 还会正常下降，不容易发现**。

384 相对 256 显存增加有限（激活显存随长度近似平方增长，但 1.5B 模型基数小），实测 8GB 卡可跑。

## 四、关键修正 2：训练必须带 system

这是全脚本**最重要**的一处。

**原脚本的 messages：**

```python
messages = [
    {"role": "user", "content": instruction + "\n" + input_text},
    {"role": "assistant", "content": output},
]
```

**本项目的 messages：**

```python
messages = [
    {"role": "system", "content": SYSTEM_PROMPT},     # ← 加这一行
    {"role": "user", "content": instruction + "\n" + input_text},
    {"role": "assistant", "content": output},
]
```

**原因**：本项目推理时（`answer_question.py:649`）每次都传一段 403 字的 system，里面有 8 条硬约束：

```
1. 只用【结构化事实】和【参考资料】里的内容作答，不要凭常识补充
2. 保健食品的回答必须包含「保健食品不是药物，不能代替药物治疗疾病」
5. 资料不足时直接说「资料里没有这个信息」，不要推测
7. 禁止使用绝对化用语：唯一、最有效、第一、100%…
```

如果训练时不带 system，模型没学过这套约束；推理时再喂，对它就是**没见过的输入**，行为会飘。这类「训练-推理错配」（train-inference skew）是微调最常见的失败原因，而且**loss 曲线完全正常**，只能靠推理实测才能发现。

**实现上不手抄，直接 import：**

```python
from application.use_cases.answer_question import AnswerQuestionUseCase
SYSTEM_PROMPT = AnswerQuestionUseCase._system_prompt()
```

我最初手抄过一版，逐字校验是 **403 vs 409 字符**——多行字符串的缩进空格混进了正文。手抄必然漂移：那边改一个字，这边忘了改，训出来的模型就对不上。**共享常量一律 import。**

## 五、训练前的数据校验

脚本在加载模型之前先跑 `precheck_dataset()`，三项不过就直接退出：

| 检查 | 不过的后果 |
|---|---|
| system 与推理侧逐字一致 | 模型行为错配 |
| instruction 含【员工的问题】分区 | 输入格式与推理不一致 |
| output 非空 | 学不到答案 |

放在加载模型之前，是为了**不白等**——加载模型要 15 秒，跑完才发现数据错就更亏。

当前校验结果：

```
✅ 数据校验通过：459 条，system 一致 / 格式完整 / output 非空
```

## 八、验收标准（训完必查）

光看 loss 不够，必须实测。三条硬指标：

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 违规表述识别 | 问「降血糖这样说对吗」→ 应指出不合规并给正确说法 |
| 2 | 拒答能力 | 问资料外的产品 → 应说「资料里没有」，不能编 |
| 3 | 警示语 | 任何涉及保健食品的回答都要带「不是药物」 |

**还要反查「有没有训坏」**：

| 风险 | 怎么查 |
|---|---|
| 过拟合 | 拿训练集外的新问题问，看是否只会背答案 |
| 复读 | 连续问 3 个不同问题，看是否输出雷同 |
| 只会答合规题 | 问正常的业务流程问题，看是否退化成「一律说违规」 |
