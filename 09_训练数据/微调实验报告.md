## 一、结论先行

| 结论                           | 证据                                                      |
| ---------------------------- | ------------------------------------------------------- |
| **1. 格式问题不该靠训练解决**           | 用训练修 Markdown，格式干净了但答案正确表述丢了；改用推理侧正则清洗，格式 100% 干净且不损失内容 |
| **2. 小模型不需要「记住」知识，只要「照抄」资料** | 1.5B 给它【结构化事实】能一字不差复述批准原文；不给就会编造                        |
| **3. 参数量决定「理解力」，不是「记忆」**     | 1.5B 把「阿司匹林能吃吗」答成「不可以擅自停药」；3B 能答对                       |
| **4. 8GB 卡训 3B 必须 QLoRA**    | 3B bf16 权重 5.8GB，训练时 OOM（已分配 6.89GB 仍失败）；4bit 量化后可行     |
| **5. 训练前必须做数据校验**            | 训练/推理 system prompt 不一致会导致整个数据集白做，且 loss 曲线完全正常         |

### 3.2 为什么负样本要占到 35%

**血的教训**：第一版 459 条数据里**没有任何一条「查不到」的样本**，结果模型学到「任何问题都要给出答案」——推理时面对资料外的产品直接编造：

```
问：你们有适合孕妇吃的钙片吗？（资料里没有）
答：我们有一款专门针对孕妇设计的钙片，它含有 DHA 和叶酸…
```

**成因**：94.5% 的样本是「该答」，5.5% 是「该拒」，模型的最优策略自然是「永远尝试回答」。

**修法**：把负样本补到 246 条（35%），按 12 类业务场景系统性覆盖：

| 类别         | 条数 | 示例                  |
| ---------- | -- | ------------------- |
| 产品库没有的产品   | 25 | 「有孕妇钙片吗」「卖不卖蛋白棒」    |
| 目录外的功能声称   | 30 | 「能治失眠吗」「能长高吗」「能抗癌吗」 |
| 诊断/用药/医疗判断 | 20 | 「帮我看看体检报告」「我在吃华法林」  |
| 门店不提供的服务   | 10 | 「能预约专家号吗」「能帮我打针吗」   |
| 内部经营信息     | 10 | 「你们营收多少」「进货价多少」     |
| 未收录的流程政策   | 23 | 「员工请假流程」「能开专票吗」     |
| 闲聊越界       | 10 | 「你多大了」「帮我写工作总结」     |
| 竞品比较       | 10 | 「和汤臣倍健比哪个好」         |
| 模糊问法       | 15 | 「有什么推荐的吗」「随便拿一个」    |
| 超范围专业问题    | 10 | 「GMP 认证审什么」         |
| 虚构产品名      | 15 | 「康源牌灵芝胶囊有吗」         |
| 安全边缘问题     | 14 | 「一次吃十片会怎样」          |
| 客户情绪化追问    | 54 | 「能不能便宜点」「是不是传销」     |

### 3.3 数据格式：必须与推理侧同构（关键设计）

**这是最容易做错、也最致命的一处。**

真实推理时，`answer_question.py:_build_prompt()` 每次都拼一大段上下文：

```
【已核实的事实】  ← 法规层结论（可选）
【结构化事实】    ← 产品库事实：品类/批号/批准功能/不适宜人群/用量
【前几轮对话】    ← 仅用于理解指代（可选）
【参考资料】      ← 检索到的文档片段
【员工的问题】    ← 用户问题
```

**如果训练数据是「裸问题 → 答案」**，模型学到的是**凭记忆答题**——恰好破坏项目最核心的设计（只用资料作答、不凭常识补充）。

**正确做法**：训练数据的 `instruction` 必须模拟这个结构：

```json
{
  "instruction": "【参考资料】（来自培训文档，仅供参考）\n[1] 《功能声称规范》第三章\n降血糖 → 有助于维持血糖健康水平 | 用了医疗术语\n\n【员工的问题】\n新员工介绍产品时说「降血压」，这样对吗？",
  "input": "",
  "output": "不对。正确表述是「有助于维持血压健康水平」，错在用医疗术语。保健食品不是药物，不能代替药物治疗疾病。",
  "system": "<从推理侧 import 的 403 字 prompt>",
  "meta": {"source": "compliance", "ref": "D005"}
}
```

### 3.4 system prompt 必须 import，不能手抄

**实测数据**：手抄推理侧的 8 条约束，逐字校验结果是 **403 vs 409 字符**——多行字符串的缩进空格混进了正文。

```python
# ❌ 错误做法：手抄
SYSTEM_PROMPT = ("你是保健食品门店的资深健康顾问。回答要求：…")

# ✅ 正确做法：直接 import
from application.use_cases.answer_question import AnswerQuestionUseCase
SYSTEM_PROMPT = AnswerQuestionUseCase._system_prompt()
```

校验代码：

```python
assert all(r["system"] == AnswerQuestionUseCase._system_prompt() for r in rows)
```

> **面试要点**：这类「训练-推理错配」（train-inference skew）最阴险的地方是 **loss 曲线完全正常**，只能靠推理实测发现。共享常量一律 import，绝不手抄。

### 3.5 数据清洗踩的 5 个坑

| # | 现象                    | 根因                | 修法                                  |                                                 |
| - | --------------------- | ----------------- | ----------------------------------- | ----------------------------------------------- |
| 1 | 「有助于增强免疫力」被判违规，输出 \`  | 2\`               | 通用表格正则命中了「24 项合法功能目录表」，把合法项当错误说法    | 按 `##` 章节切片，只在第三章/引用块取对照；加防御：去掉「有助于」后两端相同则判为目录项 |
| 2 | 流程图被加句号：` ```。 ` `↓。` | 按行加句号，把代码块和箭头也处理了 | 识别 ` ``` ` 代码块整段跳过，纯符号行丢弃           |                                                 |
| 3 | 表格被切碎：`\| \| 内容 \|。`  | 表格行当正文处理          | `table_to_sentences()` 转成「字段：内容」式语句 |                                                 |
| 4 | 序号列当字段名：`1——主动问候`     | 首格是纯数字            | 剥离数字/圈号列，用下一格做字段名                   |                                                 |
| 5 | 分组表头当数据：`首次到店：老客户复访`  | 两格都很短无标点          | 双短格无标点 + 含「首次/类型/场景」判为表头            |                                                 |

**坑 1 是最危险的**：如果照那样训练，模型会学到「合法表述也违规」，直接训坏。**这个错误是先造 20 条样例人工审出来的**——所以「先出样例再批量」是必要流程。

## 四、训练方案对比（6 个版本）

### 4.1 版本演进与指标

| 版本        | 数据量 | 轮数    | lr   | 数据策略                     | train_loss | val_loss   | 结果                        |
| --------- | --- | ----- | ---- | ------------------------ | ---------- | ---------- | ------------------------- |
| v1        | 459 | **3** | 1e-4 | 原始（无负样本）                 | **0.014**  | —          | ❌ 严重过拟合，编造产品              |
| v2        | 486 | 1     | 5e-5 | +27 负样本                  | 0.1068*    | —          | 拒答仍失败                     |
| v3        | 486 | 1     | 5e-5 | 同上（eval 改独立）             | 0.1068*    | —          | eval OOM，权重侥幸保住           |
| v4        | 705 | 1     | 5e-5 | +246 负样本(35%)            | 0.0695*    | —          | ✅ **答案正确**，但尾部回吐 Markdown |
| v5        | 705 | 1     | 5e-5 | +**output 规范化**(单段/200字) | 0.144*     | **0.2062** | ❌ 格式干净但**正确表述丢失**         |
| **v6**    | 705 | **2** | 5e-5 | 恢复 v4 数据 + 格式交推理侧        | 0.1123*    | **0.1839** | ✅ 内容+格式均可                 |
| **3B-Q4** | 705 | 2     | 5e-5 | 同 v6，基座换 3B              | 0.4652     | **0.1647** | ✅✅ **最优**                 |

> \* 为末段 loss；`train_loss` 字段是全程平均（含早期高 loss），故 v6 显示 0.4674 而末段 0.1123。

### 4.2 v1 的教训：train_loss 0.014 是灾难信号

| 指标        | 正常区间      | v1 实际     |
| --------- | --------- | --------- |
| 训练末段 loss | 0.3 ~ 1.0 | **0.014** |

**0.014 意味着模型在背诵训练集**。表现：训练集内题目答得好，训练集外**开始编造**：

```
问：你们有适合孕妇吃的钙片吗？
答：我们有一款专门针对孕妇设计的钙片，它含有 DHA 和叶酸，
    有助于胎儿大脑发育。
⚠️ 以下为错误示范：          ← 把训练语料的教学结构当输出模板
「这款钙片很适合孕妇吃。」（错误用了绝对化用语）
### 产品说明                ← 复读 Markdown
| 保质期 | 两年 |
```

**三条根因**：

1. 459 条数据训 3 轮 = 342 步，每条约 0.75 步 × 3，记熟了
2. 没有验证集，只有 train_loss 一个信号
3. 数据里残留 Markdown 符号

### 4.3 v5 的教训：格式不该靠训练学

v5 把 output 规范成「单段 + 200 字 + 强制句号」，想把「尾部回吐 Markdown」训练掉。

| 项               | v4           | v5                       |
| --------------- | ------------ | ------------------------ |
| 含 2+ 换行的 output | 362/705（51%） | **0**                    |
| 未以句末标点结尾        | 106/705（15%） | **0**                    |
| **答对「降血压」正确表述** | ✅            | ❌ **变成「有助于改善血管弹性，降低血压」** |

**v5 输出了新的违规表述**——它不是「忘了」，而是只学到「要给出一个替代说法」的**句式骨架**，没记住**具体字符串**。

**结论**：

> **模型管内容，格式管代码。**  
> 让模型学「不输出 Markdown」是职责错配——同一批权重下，正则剥离只需 3 行且 100% 可靠；靠训练学则可能牺牲内容准确性。

**推理侧清洗器实测**（`infrastructure/llm/output_cleaner.py`）：

| 输入                               | 输出                    |
| -------------------------------- | --------------------- |
| `不对。…\n\n【参考资料】\n\| 序号 \| 表述 \|` | `不对。…`（回吐整段被砍）        |
| `### 客户档案记录规范\n#### 一、必填字段\n姓名…` | `客户档案记录规范 一、必填字段 姓名…` |
| `正确说法：\n```\n有助于维持血糖健康水平\n``` `  | `正确说法： 有助于维持血糖健康水平`   |
| `其批准功能是 **有助于维持血脂健康水平**。`        | `其批准功能是 有助于维持血脂健康水平。` |

## 五、显存与性能实测

### 5.1 训练阶段

| 方案                       | 权重显存   | 训练峰值（实测）         | 单步耗时     | 总时长（634 条×2 轮）   | 可行性 |
| ------------------------ | ------ | ---------------- | -------- | ---------------- | --- |
| 1.5B + LoRA（bf16 全精度）    | 3.1GB  | **4.31GB**       | 1.8s     | **579s（10 分钟）**  | ✅   |
| 3B + LoRA（bf16 全精度）      | 5.8GB  | **6.89GB 仍 OOM** | —        | —                | ❌   |
| **3B + QLoRA（4bit nf4）** | ~1.6GB | **4.89GB**       | **4.4s** | **1190s（20 分钟）** | ✅   |

> 峰值显存用 `torch.cuda.max_memory_allocated()` 实测（小样本 12 条跑完整训练步，激活值与数据量无关，故可代表全量训练峰值）。

**3B 全精度的 OOM 现场**：

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 222.00 MiB.
GPU 0 has a total capacity of 8.00 GiB of which 0 bytes is free.
Of the allocated memory 6.89 GiB is allocated by PyTorch.
```

**为什么 6.89GB 还不够**：5.8GB 权重 + LoRA 参数 120MB + 优化器状态 + 激活值（gradient_checkpointing 已开，但 logits 层仍要 222MB）。

### 5.2 可训练参数

| 基座   | 可训练参数      | 总参数           | 占比        |
| ---- | ---------- | ------------- | --------- |
| 1.5B | 18,464,768 | 1,562,179,072 | **1.18%** |
| 3B   | 29,933,568 | 3,115,872,256 | **0.96%** |

> 3B 占比更低，因为 LoRA 参数量由**层数 × 维度**决定，而基座参数随**参数量平方级**增长。

### 5.3 推理阶段

| 项                     | 1.5B + LoRA     | 3B + LoRA (4bit) |
| --------------------- | --------------- | ---------------- |
| 权重文件                  | 73.9MB          | 119.8MB          |
| 推理显存峰值                | 5.30GB          | **6.28GB**       |
| 正常回答耗时                | 15–21s          | **30–38s**       |
| 拒答（不走 LLM）            | 2.1s            | 2.1s             |
| 护栏重试路径                | **93.9s**       | 37.9s（未触发）       |
| **与 bge-m3（2.1GB）共存** | ✅               | ❌ 会挤到 CPU        |
| 吞吐                    | ≈ **2.4 tok/s** | ≈ **2.2 tok/s**  |

### 5.4 一个反直觉的发现：推理速度与模型大小无关

| 模型                 | 参数量  | 显存     | 生成速度          |
| ------------------ | ---- | ------ | ------------- |
| Qwen2.5-7B（4bit）   | 7.6B | 5.65GB | **2.4 tok/s** |
| Qwen2.5-3B（4bit）   | 3.1B | 2.48GB | **2.2 tok/s** |
| Qwen2.5-1.5B（4bit） | 1.5B | 1.51GB | **2.4 tok/s** |

**参数量差 5 倍，速度几乎相同。**

**诊断过程**：

1. 先怀疑 GPU 有问题 → 实测 fp16 矩阵乘 **8.3 TFLOPS**（正常），SM 时钟 2505MHz（接近上限 3105），温度 52°C 无降频
2. 排除算力瓶颈 → 瓶颈在 **transformers 的逐 token 生成循环**（Python 调度 + 每步约 800 次 CUDA kernel 启动），与矩阵规模无关

**推论**：换小模型只省显存、省加载时间，**不省生成时间**。真正提速要换推理引擎——实测 Ollama（llama.cpp 内核）达 **181.8 tok/s**，详见 10.4。

> **面试要点**：这是一个「看起来该归因于模型，实际归因于框架」的典型案例。先量化验证硬件无瓶颈，再定位到软件层。

## 六、训练方法对比

### 6.1 全参数微调 vs LoRA vs QLoRA

| 维度      | 全参微调       | **LoRA**            | **QLoRA**         |
| ------- | ---------- | ------------------- | ----------------- |
| 原理      | 更新全部权重     | 冻结基座，插入低秩矩阵         | 基座 4bit 量化 + LoRA |
| 可训练参数   | 100%       | 0.96%–1.18%（本实验）    | 同 LoRA            |
| 1.5B 显存 | ~12GB ❌    | **4.31GB** ✅        | ~3.6GB ✅          |
| 3B 显存   | ~20GB ❌    | **6.89GB OOM** ❌    | **4.89GB** ✅      |
| 训练速度    | 最慢         | **1.8s/step（1.5B）** | 4.4s/step（3B）     |
| 精度损失    | 无          | 极小                  | 有（量化误差）           |
| 产物大小    | 完整模型（GB 级） | **73.9MB**          | 119.8MB           |
| 本实验结论   | 8GB 卡不可行   | **1.5B 最优选择**       | **3B 唯一可行方案**     |

**选择依据**：

```
模型权重 × 2（bf16） + LoRA 参数 + 激活值 ≤ 显存
1.5B: 3.1GB + 0.04GB + 激活 ≈ 4.31GB  ✅（实测）
3B:   5.8GB + 0.06GB + 激活 ≈ 6.89GB  ❌（8GB 卡失败，实测）
```

**关键数字**：1.5B 训练峰值 4.31GB，3B QLoRA 训练峰值 4.89GB——**两者相差仅 0.58GB**，  
但 3B 全精度比 1.5B 多花 2.58GB。这说明 **4bit 量化把 3B 拉回了 8GB 卡的可用区间**。

### 6.2 LoRA 超参选择依据

| 参数               | 取值                              | 依据                                         |
| ---------------- | ------------------------------- | ------------------------------------------ |
| `r`              | 16                              | 参考脚本注释：「经大量实验，无特殊要求就 16」。本任务单一（话术合规），不需 32 |
| `lora_alpha`     | 32                              | 惯例取 `2 × r`                                |
| `lora_dropout`   | 0.1                             | 防过拟合，小数据量下必要                               |
| `target_modules` | q, k, v, o, gate, up, down_proj | **7 层全开**（Attention 4 + MLP 3）             |
| `bias`           | none                            | LoRA 标准做法                                  |

**效果验证**：`r=16/alpha=32` 下可训练参数 1.18%，验证 loss 能降到 0.16–0.18，说明容量足够。

### 6.3 训练超参的关键调整

| 参数                       | 初值                | 调整后                  | 调整依据                                                                        |
| ------------------------ | ----------------- | -------------------- | --------------------------------------------------------------------------- |
| `max_seq_length`         | 256               | **384**              | 实测 token 分布 P50=219/P90=307/**max=328**。256 会截断 **14%** 样本，且截掉的是**末尾的答案部分** |
| `num_train_epochs`       | 5 → 3 → 1 → **2** | 2                    | 5/3 在 459 条上过拟合（loss 0.014）；1 轮 v5 验证 loss 0.2062 训不够；2 轮 0.1839 最佳         |
| `learning_rate`          | 1e-4              | **5e-5**             | 配合轮数下调，减缓记忆速度                                                               |
| `warmup_steps`           | 200（固定）           | **warmup_ratio=0.1** | 原脚本 200 步是相对 100 条数据；本项目 316 步，按比例更合理                                       |
| `batch × accum`          | 2 × 4             | **1 × 4**            | 8GB 显存约束；等效 batch 4                                                         |
| `gradient_checkpointing` | True              | True                 | 用重算换显存，8GB 卡跑通的**关键**，代价是慢约 20%                                             |

**max_seq_length 的坑要说清楚**：

对话模板顺序是 `system → user → assistant`，**截断总是发生在末尾**，即答案被切掉。模型只学到「问题和资料长什么样」，学不到「该怎么答」——**而且 loss 仍会正常下降，不易察觉**。


### 6.4 验证集策略：为什么 Trainer 内 eval 必然 OOM

实测三次全部失败：

```
torch.OutOfMemoryError: Tried to allocate 1.73 GiB.
Of the allocated memory 5.32 GiB is allocated by PyTorch, 1.09 GiB free.
```

**根因**：eval 要算 `[1, seq_len, 152064]` 的 logits，`1 × 384 × 152064 × 4 bytes ≈ 222MB`，但 cuBLAS workspace + 中间张量合计约 **1.73GB**。训练已占 5.3GB，8GB 必然不够。

**`prediction_loss_only=True` 救不了**——trl 的 `SFTTrainer` 自己接管 `compute_loss`，该参数不生效（实测验证）。

**正确做法**：训练结束后单独评估，此时训练显存已释放：

```python
def evaluate_holdout(mdl, tok, ds) -> float:
    """训练后单独算验证 loss，不进 Trainer。"""
    mdl.eval()
    total, n = 0.0, 0
    with torch.no_grad():
        for i in range(len(ds)):
            ids = tok([ds[i]["text"]], return_tensors="pt",
                      truncation=True, max_length=MAX_SEQ_LENGTH)
            ids = {k: v.to("cuda") for k, v in ids.items()}
            ids["labels"] = ids["input_ids"].clone()
            out = mdl(**ids)              # 只取 loss，不留 logits
            total += out.loss.item(); n += 1
            del out
            if n % 5 == 0:
                torch.cuda.empty_cache()
    return total / max(n, 1)
```

### 6.5 一个工程教训：训练用 try/finally 保存

**事故**：eval 阶段 OOM 抛异常，`trainer.train()` 之后的 `save_model()` 没执行，**109 步训练白跑**（权重文件根本没生成）。

**修法**：

```python
try:
    trainer.train()
finally:
    trainer.save_model(OUTPUT_DIR)      # 无论是否异常都落盘
    tokenizer.save_pretrained(OUTPUT_DIR)
```

## 七、3B + QLoRA 特有的 4 个坑

1.5B bf16 全精度训练时**一个都没遇到**，换 3B + QLoRA 后逐个踩出来。

| # | 报错 | 根因 | 修法 |
|---|---|---|---|
| 1 | `Cannot copy out of meta tensor; no data!` | `device_map="auto"` 与 `low_cpu_mem_usage` 的 meta 设备机制冲突 | 去掉 `device_map`，显式 `model.to("cuda")` |
| 2 | 训练时 `CUDA OOM`（6.89GB 已分配） | 3B bf16 权重 5.8GB + 激活超 8GB | 改 QLoRA 4bit |
| 3 | `ValueError: .to is not supported for 4-bit models` | accelerate ≥1.10 的 `dispatch_model` 单卡分支**无条件** `model.to(device)` | 打补丁：捕获该异常并跳过，手动写 `hf_device_map` |
| 4 | `RuntimeError: indices should be either on cpu or on the same device` | 4bit 只量化**参数**，rope 的 cos/sin 是**非参数 buffer**，留在 CPU | 遍历 `named_buffers()` 逐个搬 GPU |

**补丁 3 的代码**（推理侧 `local_llm_adapter` 也踩同一个坑）：

```python
import accelerate.big_modeling as _bm
_orig_dispatch = _bm.dispatch_model

def _safe_dispatch(model, *a, **kw):
    try:
        return _orig_dispatch(model, *a, **kw)
    except ValueError as exc:
        if "4-bit" not in str(exc) and "8-bit" not in str(exc):
            raise
        dm = kw.get("device_map")
        if dm is not None:
            try:
                model.hf_device_map = dict(dm)
            except (AttributeError, TypeError):
                pass
        return model

_bm.dispatch_model = _safe_dispatch
```

**补丁 4 的代码**：

```python
for _, buf in list(model.named_buffers()):
    if buf.device.type != "cuda":
        buf.data = buf.data.to("cuda")
```

> **面试要点**：这 4 个坑都不在文档里，是「8GB 卡 + 新版本 peft/accelerate + 4bit」这个组合特有的。能定位到它们，靠的是**读堆栈里的具体文件和行号**，而不是猜。

### 9.2 LoRA 挂载为什么排在 buffer 迁移之后

```python
# local_llm_adapter.py 的执行顺序
180  tokenizer = AutoTokenizer.from_pretrained(...)
185  self._model = AutoModelForCausalLM.from_pretrained(...)   # 4bit 量化加载
195  # 4bit 只量化参数，rope 的 cos/sin 是非参数 buffer，仍在 CPU
203  for _, buf in list(self._model.named_buffers()):          # ← 先搬 buffer
204      if buf.device.type != "cuda": buf.data = buf.data.to(...)
207  if self._lora_path: PeftModel.from_pretrained(...)         # ← 再挂 LoRA
221  self._model.eval()
```

| 顺序约束 | 原因 |
|---|---|
| LoRA 必须在 buffer 迁移**之后** | LoRA 会给模型**插入新层**；若先挂 LoRA 再搬 buffer，新插入层的 buffer 会漏搬，训练/推理时报 `indices should be on same device` |
| 必须在 `eval()` **之前** | 确保适配器层也进入推理模式 |

**这个顺序是踩坑后定的**，不是随手排的。

## 十、部署与运维

### 10.1 显存错峰：本地 LLM 与 bge-m3 的冲突

**这是部署时最关键的一条约束。**

| 组件 | 显存 |
|---|---|
| bge-m3（embedding） | 2.12GB |
| Qwen2.5-1.5B（bf16） | 3.1GB |
| Qwen2.5-3B（4bit） | ~1.6GB |
| Qwen2.5-7B（4bit） | 5.65GB |

**实测结论**：

| 组合 | 合计 | 8GB 卡 | 结果 |
|---|---|---|---|
| 7B + bge-m3 | 7.77GB | 临界 | ❌ 加载中途 OOM |
| **3B(4bit) + bge-m3** | 3.72GB | ✅ | ⚠️ 能装下，但**推理峰值 6.28GB**，与 embedding 抢显存 |
| **1.5B(bf16) + bge-m3** | 5.22GB | ✅ | ✅ 推理峰值 5.30GB，**可共存** |

**7B 的 OOM 现场**：

```
bge-m3 加载 → 2.12GB
7B 加载   → CUDA out of memory. Tried to allocate 34.00 MiB.
            Of the allocated memory 7.19 GiB is allocated by PyTorch
```

**降级机制**：`milvus_search_adapter.py:127` 已有「GPU 加载失败自动回退 CPU」的保护：

```python
try:
    model = SentenceTransformer(model_dir, device=device)
except Exception as exc:
    logger.warning("GPU 加载失败（%s），回退 CPU。CPU 编码会慢 10 倍以上。", exc)
    model = SentenceTransformer(model_dir, device="cpu")
```

**实测该降级有效**：7B 占 5.65GB 后，bge-m3 自动退到 CPU，编码耗时 0.88s（可接受），两者共存正常。

### 10.4.1 3B GGUF 完整实测（推荐方案）

**测试环境**：Ollama 0.33.3 + `qwen2.5:3b`（Q4_K_M，1.9GB）+ RTX 4060 Laptop 8GB

| 指标 | 实测值 |
|---|---|
| **生成速度** | **107.0 / 108.0 / 107.7 tok/s**（3 次，203–211 token，**极稳定**） |
| 提示处理速度 | 164 token / 0.13s = **1261 tok/s** |
| **显存占用** | **2760 MiB（2.7GB）**，`100% GPU`（无 CPU 卸载） |
| 首次加载 | 3.02s（之后常驻，0s） |
| **100 token 回答耗时** | **约 0.93s** |
| **200 token 回答耗时** | **约 1.9s** |

**与 transformers 对比**：

| 项 | transformers 3B（4bit） | **Ollama 3B（Q4_K_M）** | 倍数 |
|---|---|---|---|
| 生成速度 | 2.2 tok/s | **107.7 tok/s** | **快 49 倍** |
| 显存 | 2.48GB | 2.7GB | 相当 |
| 100 token 耗时 | 45s | **0.93s** | **快 48 倍** |
| 加载 | 8.8s | 3.0s | 快 3 倍 |

**为什么快这么多**（不是模型小，是框架差异）：

| 环节 | transformers | llama.cpp |

| kernel launch | 每 token 约 800 次 | 合并优化 |

> 同一个 3B 模型、同一张卡，**只换框架就快 49 倍**。
> 这印证了第五节的反直觉发现：速度瓶颈在软件层，不在模型大小。

### 10.4.2 Ollama 加载 LoRA 的正确做法

**先说结论：Ollama 已移除 `ADAPTER` 指令，LoRA 不能直接加载。**

实测记录（都是实际执行的）：

| 尝试 | 结果 |
|---|---|
| Modelfile 写 `ADAPTER <绝对路径>` | ❌ `no Modelfile or safetensors files found` |
| `ADAPTER <相对路径>` + 引号 | ❌ 同样报错 |
| 不带 `ADAPTER` 的 `FROM` 基础 create | ✅ 正常 |
| 查官方 Modelfile 文档 | **指令列表里没有 ADAPTER**（仅 FROM/PARAMETER/TEMPLATE/SYSTEM/LICENSE/MESSAGE/REQUIRES/CAPABILITY） |

**正确链路**（三步）：

```
LoRA 权重（73.9MB）
   ↓ ① peft merge_and_unload()
完整 HF 模型（3.1GB safetensors）        ← 已验证可行，见下
   ↓ ② llama.cpp convert_hf_to_gguf.py
GGUF（Q4_K_M 约 1GB）
   ↓ ③ ollama create -f Modelfile
Ollama 可加载
```

**第 ① 步已验证通过**（`merged_1.5b/`）：

| 指标 | 结果 |
|---|---|
| `merge_and_unload()` | ✅ 成功 |
| logits 最大绝对差异 | 0.53（相对 2.38%，约 6 个 bf16 量化步长） |
| **argmax 是否相同** | ✅ **True** |
| **top-10 重合** | ✅ **10/10** |
| 能力一致性（照抄批准原文） | ✅ 两模型都准确 |

> **判据说明**：不能用 `max|Δlogits| < 1e-2` 这种绝对阈值——bf16 本身只有 8 位尾数，
> 22.25 量级的 logits 单步量化误差就有 0.087。正确判据是 **argmax / top-k 是否一致**
> 以及 **关键结论是否命中**。

**第 ② ③ 步的命令**：

```bash
# ② 转 GGUF（需装转换脚本，无需编译 llama.cpp 本体）
pip install -q gguf sentencepiece
python convert_hf_to_gguf.py "D:\项目\某健康公司培训系统\09_训练数据\merged_1.5b" \
    --outfile health-3b-f16.gguf --outtype f16
# 量化到 Q4_K_M（可选，llama.cpp 的 quantize 工具）
llama-quantize health-3b-f16.gguf health-3b-q4.gguf Q4_K_M

# ③ 建 Ollama 模型
cat > Modelfile <<'EOF'
FROM ./health-3b-q4.gguf
PARAMETER temperature 0
PARAMETER num_predict 200
EOF
ollama create health-advisor:3b -f Modelfile
```

**代价评估**：

| 步骤 | 耗时 | 风险 |
|---|---|---|
| ① merge | **2 分钟**（已验证） | 低，纯 Python |
| ② 转 GGUF | 5–10 分钟 | 中，需装 `gguf`/`sentencepiece`；转换脚本版本要与模型架构匹配 |
| ③ ollama create | **1 分钟** | 低 |

> **注意**：`convert_hf_to_gguf.py` 需要从 llama.cpp 仓库获取（脚本本身是 Python，
> 不需要编译 C++ 本体）。Windows 上转换大模型可能因内存不足失败，建议关掉其他程序。

### 10.4.5 ⚠️ 必须用 `/api/chat`，不能用 `/api/generate`

**这是本次最有价值的工程发现，直接影响能不能用。**

同一个模型、同一个问题，只换调用接口，答案质量天差地别：

| 接口 | 调用方式 | 回答 | 评价 |
|---|---|---|---|
| `/api/generate` | system 内容**手写进 prompt 字符串** | 「知识库中没有具体信息」+ 抄资料 | ❌ **退化** |
| `/api/chat` | system 作为**独立 messages 字段** | 「不能。阿司匹林和鱼油都含抗凝成分，可能增加出血风险」 | ✅ **正确** |

**根因**：GGUF 内置的对话模板是 Qwen 格式：

```
<|im_start|>system
{system}<|im_end|>
<|im_start|>user
{prompt}<|im_end|>
<|im_start|>assistant
```

`/api/generate` **不套模板**，直接拼裸文本。而微调时每条样本都经过
`tokenizer.apply_chat_template()` ——**模型只见过带模板的格式**。
喂裸文本等于换了个任务，行为自然退化。

**正确调用方式**：

```python
# ✅ 正确
requests.post("http://127.0.0.1:11434/api/chat", json={
    "model": "health-advisor:3b",
    "messages": [
        {"role": "system", "content": SYSTEM_PROMPT},   # ← 独立字段
        {"role": "user", "content": context_plus_question},
    ],
    "stream": False,
    "options": {"temperature": 0, "num_predict": 250},
})

# ❌ 错误：system 拼进 prompt，走 /api/generate
requests.post(".../api/generate", json={
    "prompt": SYSTEM_PROMPT + "\n\n" + question,   # ← 模板丢失
})
```

> **这条与 3.4 节「system 必须 import 不手抄」是同一类问题的两个表现**：
> 训练侧和推理侧的任何格式差异，都会让微调效果打折，而 loss 曲线完全正常。

### 10.4.6 量化有没有损失精度？

**结论：Q4_K_M 在这一题上不仅没掉，反而比 bf16 答得更好。**

| 版本 | 「阿司匹林能吃鱼油吗」的回答 |
|---|---|
| **GGUF Q4_K_M（1.9GB）** | 「不能。阿司匹林和鱼油都含抗凝成分，同时服用可能增加出血风险。」 ✅ |
| **transformers merged_3b（bf16）** | 「知识库里没找到相互作用的信息，建议咨询医生。」 ⚠️ 保守 |

**为什么量化没掉**：Q4_K_M 保留关键层为更高精度（`_K_M` 混合量化），3B 规模下
困惑度损失通常在 1–2% 以内，远小于「模板错配」带来的损失。

**但这不代表量化无风险**——多次采样下 Q4 的稳定性仍需更大规模评测（见未完成事项）。

### 10.4.7 实测暴露的残留问题：编造未覆盖字段

**问题**：资料里没给的字段，模型会编。

问「鱼油批准的功能是什么」，给了【结构化事实】只有「批准功能」一项，但模型回答：

```
康源牌鱼油软胶囊的批准功能是「有助于维持血脂（胆固醇/甘油三酯）健康水平」。
…
- 生产许可证号：SC1071                    ← 编的
- 批准文号：国食健注J20193485              ← 编的（真实是 G20250012）
- 功效成分：每粒含Omega-3脂肪酸 200mg      ← 编的
- 每日推荐摄入量：1粒                      ← 编的
```

**根因**：训练集里 62 条「文档 QA」样本的答案较长（P50=111 字），
让模型学到「回答要补充完整信息」的习惯。当资料不足时，它选择**编**而不是**停**。

**缓解手段（按成本排序）**：

| 手段 | 效果 | 成本 |
|---|---|---|
| **调用时给全所有字段**（最有效） | 资料充分时不会编 | 零（真实链路本来就给全量） |
| 推理侧输出清洗 + 关键词校验 | 拦掉明显的编造 | 低 |
| 补「资料只有 N 项时只答 N 项」的训练样本 | 治本 | 中（需重训） |

> **这条与 3.2 节「负样本」是同一个教训的另一面**：
> 负样本教的是「查不到就说查不到」，
> 但「查到一部分、其余不要补」这一类还没教。

### 10.5.3 参考资料里的「示例」必须剔除（问题 1 的完整分析）

**根因不在模型，在 prompt**：

检索命中的 `D012 客户档案记录规范` 里有一段**教学示例**：

```markdown
**填写示例**：

```
沟通要点：
- 客户表示在吃阿司匹林，已建议咨询医生
后续安排：
- 建议客户先咨询医生确认能否食用鱼油
- 3 天后（10-24）电话回访
```
```

**这段与用户问题高度重合，模型直接当答案抄了**——输出的正是「后续安排」那两行。

**判据设计（避免误伤）**：必须同时满足

1. 某行是**块标题**（`填写示例` / `填写范例` / `示例：` / `模板：` / `标准话术模板` …）
2. 从该行往后（跳过空行）第一个非空行是**代码围栏**

| 结构 | 剔？ | 理由 |
|---|---|---|
| `**填写示例**：` + ` ``` ` | ✅ 剔 | 教学样例，本次故障源 |
| `## 七、评分示例` + `> 引用块` | ❌ 不剔 | 评分标准，有用 |
| `### 5.2 八个改写示例` + 表格 | ❌ 不剔 | 改写对照表，有用 |
| 正文「可以参考示例，但别照抄」 | ❌ 不剔 | 只是提了一句 |

**「标题 + 围栏」双条件**是把「教学样例」与「知识内容」分开的最小判据。

**实测效果**（D012）：6524 字 → 5432 字，5 个「填写示例」块全部剔除，
字段说明表、检查清单、`── 沟通记录 ──` 结构全部保留。

| 该剔 | 填写示例块、多个示例块、2 反引号围栏 |
| 不该剔 | 评分示例（引用块）、正文提到「示例」、标题+表格、正常回答 |
| 既有行为 | 按行剔错误示范（不能回退）、空输入 |

> **测试写法的关键**：`test_strips_block_with_two_backtick_fence` 是**先跑失败
> 再修**的——它锁定的正是「源文档 3 个反引号、入库 2 个」这个真实差异。

### 10.5.5 仍未解决：知识未直接覆盖时的回答质量

**②「阿司匹林能吃鱼油吗」**：

```
答：建议您先咨询医生，让医生判断能不能吃、怎么吃。
    我这边不能给用药相关的建议。
    保健食品不是药物，不能代替药物治疗疾病。
```

**没有直接答「不能吃」**，而产品事实里明明有
`不适宜人群：出血倾向者和出血性疾病患者（严重）`，原因写着「与抗凝药同服增加出血风险」。

**这属于模型能力边界，不是代码问题**：

| 层次 | 状态 |
|---|---|
| 数据是否有答案 | ✅ 有（图谱里 severity=CRITICAL，理由直指抗凝药） |
| 是否进了 prompt | ✅ 有（`【结构化事实】不适宜人群：…`） |
| 模型是否会推理 | ❌ **3B 不会从「不适宜人群含出血倾向者」推到「吃阿司匹林就不能吃」** |

**要想解决只有两条路**：

1. **补训练样本**：造「用药冲突」类样本（客户常说「我在吃 XX 药，能吃吗」），让它学会查不适宜人群再回答
2. **推理侧补规则**：命中「抗凝药/华法林/阿司匹林」+ 产品禁忌含「出血」→ 直接判定不可同服

---

### 10.6 回滚方案

本地模型出问题时的降级路径：

```bash
# 一行切回云端（无需改代码）
LLM_PRIMARY=qwen
```

**为什么这是安全的**：

1. `llm_endpoints()` 按 `kind` 分派，云端端点始终保留在列表里
2. 回答链路、护栏、检索全部与模型无关
3. 拒答红线在调 LLM **之前**就生效，不依赖模型

**唯一的差异是话术风格**：云端千问 3–6s 返回，本地 15–38s，但合规约束由护栏保证，不受模型切换影响。

## 十一、结论与工程判断

### 11.1 八个可复用的工程结论

| # | 结论 | 支撑证据 |
|---|---|---|
| 1 | **train_loss 过低是灾难信号** | 0.014 → 模型背诵训练集，集外编造；正常区间 0.3–1.0 |
| 2 | **没有负样本，模型学不会拒答** | 459 条全为「该答」→ 编造产品；补到 35% 后行为改变 |
| 3 | **格式靠代码，内容靠模型** | 训练修格式 → 答案正确表述丢失；正则修格式 → 100% 可靠 |
| 4 | **训练与推理的 system/输入格式必须同构** | 手抄 403→409 字符即错配，且 loss 曲线正常，只能实测发现 |
| 5 | **小模型的价值是「照抄」不是「记住」** | 给【结构化事实】→ 一字不差复述；不给 → 编造 |
| 6 | **速度瓶颈在框架不在模型** | 同一个 3B：transformers 2.2 tok/s → Ollama **101–108 tok/s（快 45–49 倍）** |
| 7 | **推理接口选错会吃掉微调效果** | `/api/generate` 丢模板 → 答「知识库没有」；`/api/chat` → 正确答「不能，有出血风险」 |
| 8 | **参考资料里的「教学示例」会污染问答** | D012 的「填写示例」被整段照抄当答案；按「块标题 + 代码围栏」双条件剔除后才正常 |

### 11.2 模型选择建议（已按 Ollama 实测修正）

**关键前提变了**：上 Ollama 后速度不再是约束，选型只看**质量**和**显存**。

| 场景 | 推荐 | 理由 |
|---|---|---|
| **在线问答（推荐方案）** | **`health-advisor:3b`（Ollama Q4_K_M）** | **101 tok/s，200 token 约 2s**，1.9GB，与 bge-m3 共存 4.8GB |
| 离线批处理/夜间出报告 | Ollama + 3B | 同上，更快 |
| 显存极紧张 | Ollama + 1.5B | 181.8 tok/s，但答案质量不够（会答非所问） |
| 要求最高质量 | 云端千问 | 3–6s，质量稳定，但出网+按 token 计费 |
| **不推荐** | transformers + bitsandbytes | 2.2 tok/s，仅用于**训练**，不用于推理 |

> **重要修正**：本报告早先写「在线问答都不推荐本地」，那是基于 transformers 的 2.4 tok/s。
> **Ollama 3B 实测 107.7 tok/s 后，这个结论不再成立**——本地模型已可用于在线问答。

### 11.3 什么情况下选云端、什么情况下选本地

| 判据 | 选 Ollama 3B | 选云端千问 |
|---|---|---|
| 延迟要求 | 1.9s 可接受 | 需要 < 1s |
| 数据出网 | **不允许** | 允许 |
| 成本 | **0（一次投入）** | 按 token 付费 |
| 峰值并发 | 单卡串行，**高并发不行** | 弹性 |
| 断网可用 | ✅ | ❌ |

**推荐组合**：**Ollama 3B 为主，云端为降级**——
`LLM_PRIMARY` 一行切换，护栏与检索完全不受影响（见 10.5）。

### 11.4 如果重做，会怎么做

1. **先验证拒答红线，再造数据**——避免为一个不存在的问题投入 246 条负样本（虽然负样本对「检索到不相关资料」仍有用）
2. **先做 20 条样例人工审核**——v1 的「24 项目录当违规表」错误就是靠样例审出来的，如果直接批量造 700 条再发现，返工成本高 10 倍
3. **一开始就用 3B**——1.5B 的理解力上限是硬伤，调试话术花的时间不如直接上 3B
4. **格式清洗从第一天就放推理侧**——不要在数据侧反复折腾
5. **推理一开始就用 Ollama，不要用 transformers**——省掉「跑通了但慢 50 倍」的返工。transformers 只该用来训练
6. **先确认推理引擎，再决定模型大小**——顺序反了会误判「小模型不可用」
