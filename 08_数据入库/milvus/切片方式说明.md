# 切片方式说明（含一处已确认的缺陷）

> 编制日期：2026-10-22
> 回答：这次入库用的什么切片方式，以及实测发现的问题

---

## 一、先给你结论

| 项 | 实际做法 |
|---|---|
| **切片方式** | **规则切片（按 Markdown 标题层级）**，不用模型、不用语义分割 |
| **为什么不用模型** | 你的文档有清晰的 `#`/`##`/`###` 层级，规则切片 17.8ms 就能完成；用模型切要数分钟（见 `09_工具与实测/`） |
| **切块数** | 培训文档 338 / 案例 16 / 题库 140 |
| **最大长度** | 1213 字（约 862 token） |
| **模型上限** | bge-m3 支持 8192 token |

**但我设了个 `max_seq_length=512`，导致 16 个案例全部被截断。** 这是我的失误，下面详说。

## 二、三类数据用了三种切法

### 2.1 培训文档：按标题层级切（`split_by_heading`）

```python
def split_by_heading(md_text, max_chars=700):
    """按 #/##/### 标题切块。超长段落再按空行二次切分。"""
    for line in lines:
        if re.match(r"^#{1,3}\s", line):     # 遇到标题就切
            flush()                           # 把上一块落盘
            cur_title = line.lstrip("#").strip()
        else:
            cur_lines.append(line)
```

**特点**：
- 以 `#`/`##`/`###` 为切分点，**每节一块**
- 超过 1400 字符的节，再按空行（`\n\n`）二次切
- **每个 chunk 记录 `section` 字段**（来自标题），保留结构信息

**实测分布**：

| 区间 | 块数 | 占比 |
|---|---|---|
| <150 字 | 70 | 21% |
| 150–300 字 | 175 | 52% |
| 300–500 字 | 53 | 16% |
| 500–800 字 | 29 | 9% |
| 800–1200 字 | 10 | 3% |
| >1200 字 | 1 | 0% |

平均 273 字，中位 218 字，**52% 集中在 150–300 字**。

**21% 的块小于 150 字** —— 这些多是「学习目标」「一句话定义」这类短节。它们不是无效内容，但在检索时会因为信息量低而排不到前面。

### 2.2 情景案例：整案例一块，不切

```python
# 按 "# C01" / "## 案例 C01" 匹配案例边界
pattern = re.compile(r"^(?:#\s+|\#{2}\s+案例\s*)(C\d{2})[：:\s]*(.*)$", re.M)
```

**特点**：
- **每个案例一整块**（1 个案例 = 1 个 chunk）
- 理由：案例包含「客户设定 + 对话脚本 + 必答要素 + 参考答案 + 评分示例」，**切开就断了逻辑链**
- 检索时要么整块召回，要么不召回

**实测**：16 块，平均 **2032 字**，最长 4130 字（C04 停药案例）。

### 2.3 题库：每题一块

```python
q_pattern = re.compile(r"^#{2,3}\s+([QS]\d{3})\s*([★☆]{1,3})?\s*[（(]?[^）)\n]*[）)]?\s*$", re.M)
```

**特点**：
- **每题一块**，`extra` 字段存 `{stage, difficulty, answer}` 的 JSON
- 题干、选项、答案、解析、难点全在一个 chunk 里

**实测**：140 块，平均 191 字。

## 三、已确认的缺陷：案例被截断

### 3.1 问题

`common.py` 第 116 行：

```python
self._model.max_seq_length = 512       # 培训文本不需要 8192
```

我当时想：培训文档平均才 273 字，512 token 够了。**但忽略了案例平均 2032 字（约 1411 token）**。

**后果**：

| 数据类型 | 平均 token | 512 上限下被保留 | 截断情况 |
|---|---|---|---|
| 培训文档 | 183 | 100% | ✅ 无影响 |
| **情景案例** | **1411** | **36%** | ❌ **16 块全部被截断** |
| 题库 | 128 | 100% | ✅ 无影响 |

**具体影响**：C04 停药案例是 4130 字（约 2821 token），**只编码了前 512 token**（约 750 字）。这意味着：

- 案例开头的「客户设定 + 开场白」被编码了
- **后半段的「必答要素」「参考答案」「评分示例」全部没进向量**

**检索时**：问「吃了能停降压药吗」→ 能召回 C04（0.75 分），因为前半段有"停药"字样。但**如果问的是案例后半段的内容（比如"评分标准是什么"），就召不回**。

### 3.2 为什么会犯这个错

我按「培训文档」的长度设了 512，**没检查另两类数据的实际长度**。这是典型的"按第一批数据定参数"，违反了数据设计文档里自己写的原则：

> 「父/子 chunk_size 应**先统计新数据长度分布再定**，别抄数字」

### 3.3 修法（两个选择）

#### 方案 A：把 max_seq_length 提到 4096（推荐）

```python
self._model.max_seq_length = 4096
```

| 项 | 影响 |
|---|---|
| 案例 2821 token | ✅ 完整编码 |
| 培训文档 183 token | 无变化（短文本不受上限影响） |
| 显存 | 峰值增加约 1.2GB（4060 有 8GB，够用） |
| 向量化耗时 | 案例如 16 条会慢 3–5 倍（约 +2 秒） |

**代价很小，收益明确**。

#### 方案 B：案例也切片（按「设定/脚本/要素/答案」四段切）

```python
# 每个案例切 4 块
C04_setting     客户设定
C04_script      对话脚本
C04_elements    必答要素
C04_answer      参考答案
```

| 优点 | 缺点 |
|---|---|
| 每块都很短（300–600 字） | **召回时只拿到片段，看不到完整案例** |
| 检索精度更高 | 需要拼接多块才能用 |
| 显存占用小 | 破坏"一个案例是一个整体"的语义 |

**方案 B 更适合「检索到某个具体答案」的场景，方案 A 更适合「整案例理解」。**

### 3.4 我的建议：**A + 案例不切**

理由：

| 场景 | 需要什么 |
|---|---|
| 学员演练时系统扮客户 | 需要**完整案例**（客户设定 + 脚本 + 追问） |
| 主管查看评阅标准 | 需要**完整案例**（要素 + 参考答案） |
| 检索"类似案例" | 需要**完整案例**（判断这个案例是否类似） |

**三种用法都需要完整案例。切成 4 块反而要在应用层重新拼。**

## 四、另外两个可优化点

### 4.1 培训文档有 21% 的块小于 150 字

| 现状 | 影响 |
|---|---|
| 70 块 < 150 字 | 信息量低，检索时排不到前面 |

**这些短块是什么**：「学习目标」「1.1 一句话定义」「总结」这类。

**两个处理方式**：

| 方式 | 做法 |
|---|---|
| **合并**（推荐） | 把 <150 字的相邻块合并到上一块 |
| 保留 | 它们确实有内容，只是短 |

**但要注意**：「学习目标」这类块虽然短，**却是新人最常搜的内容**（"我要学什么"）。合并可能反而降低召回。

**建议：先不动。** 等有了 40 条测试查询，看实际召回情况再决定。

### 4.2 没有 chunk_overlap

当前实现是**硬切**，块与块之间无重叠。

| 风险 | 例子 |
|---|---|
| 跨块的句子被切断 | 「不适宜人群包括：」在块 A 末尾，「少年儿童、孕妇」在块 B 开头 |

**为什么这次没加 overlook**：
- Markdown 标题切分天然在语义边界上，不像纯文本切分那样容易切断
- 加了重叠会让 chunk 数从 338 涨到 400+，且召回时出现重复

**但有一个真实风险**：如果某个列表跨了两个 `##` 节，会被切断。这个需要抽查确认。

## 五、与常见切片方案的对比

| 方案 | 是否使用 | 说明 |
|---|---|---|
| **固定长度切分**（每 500 字一刀） | ❌ | 会切断句子和列表 |
| **递归字符切分**（RecursiveCharacterTextSplitter） | ❌ | 开发指导里那个项目用的这个；本项目文档有标题层级，用标题切更准 |
| **按标题切分**（当前做法） | ✅ | 保留文档结构，`section` 字段可追溯 |
| **语义切分**（按句向量相似度） | ❌ | 要编码所有句子，375 块要 8–15 秒，不必要 |
| **LLM 切分** | ❌ | 数分钟到数十分钟，差 3–4 个数量级 |
| **父子块**（parent-child） | ❌ | 当前数据没有明显的"父块-子块"关系 |

**选标题切分的理由**：开发指导里提到的 `RecursiveCharacterTextSplitter` 是为**无结构长文本**设计的；你的文档是结构化 Markdown，**用标题切分比递归字符切分更准**——因为标题本身就是作者划的语义边界。

## 六、要不要重修

| 项 | 是否建议 | 成本 |
|---|---|---|
| **案例 max_seq_length 512→4096** | **✅ 必须修** | 重跑 40 秒 |
| 短块合并 | ⚠️ 观察后再定 | 重跑 40 秒 |
| 加 chunk_overlap | ⚠️ 需要抽查 | 重跑 40 秒 |

**建议现在就修第一项**——这是明确的功能缺陷，不是优化。

## 七、一句话总结

> **用的是「按 Markdown 标题层级」的规则切片，三类数据三种切法：**
> **培训文档按节切（338 块）、案例整块不切（16 块）、题库每题一块（140 块）。**
>
> **但模型序列长度设成了 512，导致 16 个案例全部被截断到 36%——这是我的失误，需要改成 4096 重跑。**
