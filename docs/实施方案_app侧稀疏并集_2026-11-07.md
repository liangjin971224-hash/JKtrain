## 1. 为什么不能直接照搬 81 号的结论

81 号的 union（案例库 28/34）是**在 Milvus 单路上**测的。线上链路不是单路，而是：

```
graph(Neo4j) + vector(Milvus bge-m3 dense) + keyword(BM25，2-gram，内存索引)
        → RRF(k=60, 按意图加权) → 可选 rerank → 提示词取前 5 条
```

所以先要回答一个问题：**现有三路融合是不是已经把稀疏该拿的分拿了？**

### 实测：没有

新建 `train/scripts/92_app_retrieval_eval.py`（走真实容器与用例，与 81 号同构），
在 205 题 remap 评测集上测线上链路：

| 口径 | 线上三路（改前） | 纯 dense 单路（81 号） |
|---|---|---|
| 整体 R@5 | **167/205** | 159/205 |
| 案例库 R@5 | **21/34** | 21/34 |
| 文档库 R@5 | 106/131 | 98/131 |
| 题库 R@5 | 40/40 | 40/40 |

结论有两条：

1. 三路融合对**文档库**是真实收益（98→106），BM25 补上了编号/型号类查询；
2. 但对**案例库完全无效**（21/34，与纯 dense 一模一样）——BM25 的 2-gram 字面匹配
   补不上表格型内容（必答要素/权重、违禁正则、评分示例），而 bge-m3 的学习式稀疏可以（25/34）。

## 2. 设计

### 2.1 新增第 9 个端口 `SparseSearchPort`

与 `VectorSearchPort` **并列**，不合并——两者分数不同量纲（余弦 0~1 / IP 无上界），
一个阈值管两种分数线上必错。

> ★ 方法名必须是 `search_sparse` 而不是 `search`：同一适配器类同时实现两个端口时，
> 同名方法会互相覆盖。**实测踩过**——首版把稀疏写成 `search`，结果稀疏路静默跑成
> 第二遍 dense 搜索（`n_sparse=20` 但指标零变化）。

### 2.2 稀疏编码：手算，不用 FlagEmbedding

用已加载的 `SentenceTransformer` + `sparse_linear.pt` 手算 `relu(W·H)` 按 token 取最大。
与官方 `BGEM3FlagModel` 输出实测一致（token 集合相同、权重最大绝对误差 **1e-7**，
仅多出 `<s>`/`</s>` 两个特殊 token，已排除）。

省掉第二份 2.3 GB 权重与约 4s 启动。缺 `sparse_linear.pt` 时**直接报错**，
不静默随机初始化（那是 P0-3 在本机踩过的坑）。

### 2.3 并集窗口，而不是把稀疏当第 4 路

把稀疏丢进 RRF 会稀释（P0-3 实测：案例库稀疏单独 25/34 → 进 RRF 回落到 21/34，
因为 `1/(60+rank)` 会让"两边都中等"压过"单路极强"）。

所以按覆盖组装窗口：

```
fused = RRF头部(2 条) + 稀疏未重复命中 + RRF 尾部回填
```

### 2.4 ★ 关键约束：提示词只取前 5 条

`answer_question._build_prompt` 里是 `for i, hit in enumerate(docs[:5], 1)`。
所以**第 6 位往后放什么都不影响 LLM**——首版把稀疏放在 5 位之后，实测指标零变化。

案例库 34 题的 5 位分配实验（gold 是否落在前 5）：

| 组合 | 命中 |
|---|---|
| app5 + sparse0（不做并集） | 21/34 |
| app4 + sparse1 | 22/34 |
| app3 + sparse2 | 23/34 |
| **app2 + sparse3（采用）** | **24/34** |
| app1 + sparse4 | 25/34 |
| app0 + sparse5 | 25/34 |

取 2+3：与 1+4 只差 1 题（噪声量级），但保留两条「向量+BM25 共识」结果作为保险。
该值固化为 `SPARSE_UNION_HEAD = 2`，并注明**若提示词扩容，此常量必须同步改**。

## 3. 顺带修掉的一个线上级故障

P0-3 给四个 collection 加了 `sparse_vector` 后，`MilvusClient.search` 因存在两个向量字段报：

```
MilvusException: multiple anns_fields exist, please specify a anns_field in search_params
```

而 `milvus_search_adapter.search()` 没有指定 `anns_field` → **向量路整路失败并静默降级**，
线上实际只剩 BM25 一路在工作（不报错、不崩溃，只是召回质量崩塌）。
已在 `search()` 显式 `anns_field="vector"`。

另修 `RetrievalResult.failed` 未计 `sparse_hits`：向量降级、只有稀疏命中时会被判为
"召回失败"从而直接拒答，稀疏收益全部作废（由新增测试抓出）。

## 5. 本轮不做的事

| 不做 | 理由 |
|---|---|
| 把提示词从 5 条扩到 10 条 | 可把案例库覆盖推到 28~30/34，但会改变 prompt 长度与答案行为，需要答案级 A/B，不在本轮 |
| 对文档库也开并集 | 实测无收益（hybrid 105 vs dense 98 已在三路融合里被 BM25 覆盖），只会增加上下文噪声 |
| 调 RRF 权重或 k | 一次只改一个变量 |
| 动阈值 0.50 | 已证实向量分数不能做拒答判据（P0 §9.3-4），改动无依据 |

## 6. 回滚

```bash
# .env
SPARSE_RECALL_ENABLED=false
```

关闭后 `container.sparse` 为 None、`RetrieveUseCase` 不跑稀疏路、窗口回到纯 RRF——
与改动前行为完全一致（`app_current_20261107_171229` 即该状态，167/205）。

代码层面回滚点：`SparseSearchPort` + `search_sparse` + `_union_sparse` + 三个 settings，
互不侵入既有链路（`search()` 只多了一个 `anns_field` 参数，那行必须保留——
它是修 bug，不是新功能）。
