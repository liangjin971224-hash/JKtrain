阿里百炼没有额度，改用火山方舟。**数据格式基本一致**（都是 messages JSONL），主要差异在平台流程和调用方式。

## 0. 与百炼/魔搭的关系

| | 魔搭 PAI-DSW | 阿里百炼 | **火山方舟** |
|---|---|---|---|
| GPU 运维 | 自己做 | 不用 | **不用** |

| 产物 | LoRA 权重（可下载） | 模型名 | **推理接入点 ID（`ep-`）** |

结论不变：**都拿不到权重**，所以这是一次换基座重做，之前所有分数作废。

格式校验覆盖了方舟导入时最常见的拒绝原因：顶层只能有 `messages`、role 合法、system 最多一条且在首位、content 必须是非空字符串、单轮必须是 user → assistant、同源样本不跨 train/val。

**为什么只导 139 条（128+11）**：两份互不重叠的盲测都显示 139 条 → 11/12，扩到 312 条 → 9/12。多出来的部分是负收益，别重复。

## 2. 平台流程

1. **上传 TOS**：把 `ark_train.jsonl` / `ark_val.jsonl` 传到与方舟同区域的 TOS bucket
2. **导入数据集**：方舟控制台 → 数据集 → 新建（类型选「精调」），从 TOS 导入
3. **等校验**：方舟会给校验结果。**以它报的错为准**——我这边只能保证格式没问题，具体的单条 token 上限、最少条数、字段要求以控制台为准
4. **创建精调任务**：选基座、选数据集、设 epoch/学习率
5. **部署推理接入点**：精调完得到一个 `ep-xxxxxxxx`，这才是调用时用的「模型名」

## 3. 基座怎么选

方舟可精调的模型以控制台列表为准。选择原则：

- **优先选与 Qwen 同源的 instruct 模型**——我们这 128 条数据的写法（`【结构化事实】/【参考资料】` 分节、问句短、答案 60–100 字）是在 Qwen 系上验证过的
- 如果只有豆包（Doubao）系可选，也能用，但要注意：**思考开关的字段不一样**（见下），而且模板差异需要先验证
- **不要选对话/创作类模型的「lite」版本**——小参数模型对「资料没有就说没有」这类行为更难稳住

## 4. 训练参数起步建议

| 参数 | 建议 | 依据 |
|---|---|---|
| epoch | 2–4 | 魔搭上 139 条 × 4 epoch 末位 loss 0.37，没过拟合 |
| 学习率 | 平台默认或 1e-4 附近 | 与魔搭那轮可比的量级 |
| batch | 用平台默认 | 不要为了凑步数调整 |
| 训练集 / 验证集 | 128 / 11 | 验证集只用于挑检查点，11 条只能看趋势 |

**判读 loss**：末位 0.4–0.9 正常；低于 0.3 说明在背题，取中间检查点。

## 5. 调用与接线

方舟提供 OpenAI 兼容接口：

| 项 | 值 |
|---|---|
| base_url | `https://ark.cn-beijing.volces.com/api/v3` |
| api_key | 方舟的 API Key |
| model | **推理接入点 ID**（`ep-xxxxxxxx`），不是模型名 |

项目 `.env` 改三行即可（现有代码走的就是 OpenAI 兼容路径）：

```env
QWEN_BASE_URL=https://ark.cn-beijing.volces.com/api/v3
QWEN_API_KEY=<方舟 key>
QWEN_MODEL=ep-xxxxxxxx
```

⚠️ **两件必须在接入前验证的事**：

1. **思考开关**。我们在魔搭上把时延从 19s 压到 1.2s，靠的是「空思考块」——那是 Qwen3 模板的特性。方舟上：
   - 豆包系：请求体传 `thinking: {"type": "disabled"}`
   - Qwen 系：一般传 `enable_thinking: false`
   - 字段名与是否生效**以方舟文档/实测为准**，不要照抄
2. **system 消息是否被保留**。我们的 128 条训练样本里 system 是十条规则；如果平台在推理时丢弃或改写 system，训练与推理就不一致，效果会明显变差。验证方法：用同一道题，对比「带 system」和「不带 system」的输出差异。

## 6. 评测协议（同前，不能省）

换基座后历史分数无效，必须重建基线：

1. 用**未微调的同一个模型**跑 `heldout2_questions.jsonl`（12 题）+ `eval_questions_v3.jsonl`（45 题）
2. 用微调后的 `ep-` 跑同样两批
3. 本地用 `60_score_eval.py` 打分，再跑 `61_apply_guardrail.py` 得到过护栏版本

需要写一个小脚本调 Ark 接口产出 `{qid, answer}` 格式（与 `50_compare.py` 输出同构），评分和护栏脚本可以直接复用。

**判读标准**：

| 结果（留出集 12 题） | 结论 |
|---|---|
| 微调后 ≥ 基座 +4 | 值得用 |
| 微调后 ≈ 基座 | 这批数据在这个基座上不奏效，别硬推 |
| 微调后 < 基座 | 弃用 |

> `heldout2` 至今没被任何模型选型用过，是唯一干净标尺。方舟这一轮用完，它也会降级为验证集。

## 7. 不随平台改变的部分

- 数字核实护栏（`ungrounded_numbers` / `strip_ungrounded_sentences`）
- 禁用词护栏（8 处已修）
- 检索链路
- 十条系统规则（写在 messages 的 system 里，随数据上传）

## 8. 风险

| 风险 | 应对 |
|---|---|
| 拿不到权重，绑定平台 | 接受，或用一层 API 抽象隔离 |
| 基座换成豆包系，模板差异大 | 先做「带/不带 system」与「思考开关」两项验证，再谈效果 |
| 平台改写/丢弃 system | 训练前的数据集校验和推理前的对照实验都要做 |
| 单条 token 上限低于 688 | 我们最大 688 token，若平台限制更低，需裁剪参考资料 |
| 按 token 计费 | 先用 128 条验证，别一次上全量 |

## 9. 执行顺序

1. 控制台：确认可精调模型 + 数据集格式要求 + 最少条数（半小时）
2. 上传 `data/ark139/ark_{train,val}.jsonl` 到 TOS → 导入 → 看校验结果
3. 先跑 **20% 数据的小规模试训**，只确认两件事：loss 会降、system 没被改写
4. 全量精调 → 部署 `ep-`
5. 同基座基线 vs 微调后，跑 12 + 45 两批题
6. 达标再接 `.env`，不达标就停在云端通用模型
