## 1. 为什么选这条路

177 基线的 28 道 miss 归因：12 融合没用上、13 单路 6–20 名、1 阈值、2 召回太远。
静态构图已被 holdout 否决，rerank 天花板只有 8 题；**能改善「单路排序」的只剩微调**。

- 目标：bge-m3 对比学习（query ↔ chunk），现实预期 **+4~5 题**，乐观 +13。
- 不做：LLM SFT（改生成风格，不动检索）、LoRA（当前 FlagEmbedding 不支持）、
  百炼/方舟（拿不到权重、换基座后旧分数作废）。

## 2. 判定口径（先定死，避免再次自欺）

1. **门禁只看 holdout 55**：它与训练数据零重叠；205 全量只作 sanity。
2. 训练数据允许包含「非 holdout 的 150 道评测题」（现有 `embed_pairs_v1_train150`），
   因为 holdout 已把这 150 题排除在外。
3. 新增问题**不得与 205 评测题重复或近似**（≥8 字连续重叠拦截 + 语义抽检）。
4. 门禁用配对题数表述，不用绝对率：
   - **holdout R@5 ≥ 50/55**（基线 47/55），且案例 ≥5/9、文档 ≥31/35、题库 = 11/11；
   - `--compare` 报翻转（up/down）与 McNemar；55 题分辨率约 ±12pp，不做过度解读。
5. 重建 collection 必须在检索门禁之前（query 与 doc 必须同一模型空间）。

## 4. 标注工作包（本轮交付）

产物目录 `train/annotation_wp_v2/`：

| 文件 | 内容 |
|---|---|
| `targets.jsonl` | 225 个 chunk：chunk_id / collection / title / section / text / existing_questions / required_difficulties / bucket |
| `ANNOTATION_BRIEF_FT.md` | 给 Codex 的任务书（硬规则、格式、难度分配） |
| `manifest.json` | 数量、选取规则、源文件与生成时间（可复现） |

标注规则（与 v1 一致并加严）：

1. 每个 chunk **恰好 2 个问题**，难度按 `required_difficulties` 各一：
   `keyword`（搜索框式）/ `paraphrase`（换说法）/ `scenario`（门店情景）。
2. 问题必须**仅凭该 chunk 正文**即可独立回答。
3. 与原 chunk 正文、以及 `existing_questions`（205 评测题）**均不得有 ≥8 字连续重叠**。
4. 不得复述/改写 `existing_questions`，要换角度或问另一个事实点。
5. 输出 JSONL：`{"chunk_id","collection","question","difficulty"}`，UTF-8，无多余字段。

校验：`train/scripts/99_validate_ft_annotations.py`
（schema / 数量 / 难度 / 重复 / 8 字重叠 / 长度；硬违规 exit 1）。

## 9. 实测结果（2026-11-08）

### 9.1 两个必须记住的工程坑

1. **`merge_lora.py` 曾把权重赋给只读属性 `auto_model`**，赋值静默失败，
   `st.save()` 保存的仍是基座权重。首次下载的模型与基座**逐权重相同、cos=1.0**。
   已改为 `st._first_module().model = hf`，并用「人为改权重」的合成 checkpoint
   验证合并确实生效（delta 0.05）。**以后任何合并都要先验证
   `embeddings.word_embeddings.weight` 与 base 不同。**
2. **合并目录缺 `sparse_linear.pt` / `colbert_linear.pt`**：`SentenceTransformer.save`
   不保存 M3 的稀疏/ColBERT 头。已从基座复制这两个头（以及 `sentencepiece.bpe.model`、
   `special_tokens_map.json`）。也就是说：**dense 是微调后的，sparse 仍是基座头**；
   案例库的稀疏路因此没有吃到微调收益，这是本轮的已知限制。

### 9.3 答案级的真实结论（必须如实记录）

- 首次对比出现 41→35 的大跌，但那是 **LLM 通道切换**（旧通道 → qwen3.7-flash）造成的，
  不是微调。用**同一 LLM（DeepSeek）+ 基座/FT 两套集合**重做后是 **37 vs 37**，
  答案质量中性；gold 在上下文 41→43。
- 逐题看：FT 的 R@5 提升主要来自把 gold 拉进前 5，但**支撑块的组合会变**。
  个别题（如 `ev2-01`）gold 在上下文、但含具体答案的支撑块掉出前 5，
  模型因此答「资料里没有」。这类是上下文构图/排序问题，不是 embedding 变差。
- 生产 LLM 选择：**保留 Qwen 主通道**（1.4~3.3s、无空正文），DeepSeek 备用。
  DeepSeek flash 在长 prompt 下偶发把 1024 tokens 全用在 reasoning 上、正文为空
  （`finish_reason=length`），已实测到一次；若切 DeepSeek 主用，需要把
  `max_tokens` 提到 2048+。
- **上下文条数复核（2026-11-08，FT 模型 + Qwen）**：5/6/7 条分别
  **36 / 35 / 32**（45 题），6/7 各多一次拒答；gold 在上下文 43→44 但答案更差。
  **`CONTEXT_DOCS` 保持 5**，与 P1-b 的结论一致——多喂段落是噪声。
