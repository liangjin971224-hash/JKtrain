# 阿里百炼微调方案（2026-10-31）

## 0. 先说清楚：这不是「把 v6 搬到百炼」

v6 是 `DeepSeek-R1-0528-Qwen3-8B` 上的 LoRA。百炼的模型定制**不提供这个基座**（以控制台可选项为准），而且**不返回权重**——训练完只给一个模型名，通过 DashScope 调用。

所以这是一次**换基座重做**，之前所有分数（基座 5–6、v6 11、v7/v8 9）都作废，需要重新建立基线。

换来的是两件好处：

| | 魔搭 PAI-DSW | 百炼 |
|---|---|---|
| GPU 运维 | 自己开机、装环境、传文件 | 不需要 |
| 接进现有应用 | 卡在没有公网入口 | **接口同源**，改一个环境变量即可 |
| 权重 | 可下载、可合并 | **拿不到** |

最后一行是硬约束：选了百炼就等于依赖平台，不能本地部署、不能合并、不能换推理框架。

## 1. 开工前必须确认的三件事（控制台里看，我没法替你查）

1. **可微调的模型清单**——优先选与 Qwen3-8B 同源的 instruct 模型（模板行为最接近我们验证过的）
2. **数据格式与限制**——支持 JSONL、messages 格式；同时看清：单条最大 token、文件大小上限、最少样本数、是否按 token 计费
3. **是否支持 LoRA（高效微调）还是只能全参**——全参更贵，但小数据下过拟合风险也不同

## 3. 上传与创建训练任务

1. 把 `bailian_train.jsonl` / `bailian_val.jsonl` 传到同区域 OSS，拿到 `oss://` 地址
2. 控制台 → 模型定制 → 创建训练任务
3. 参数起步建议（与魔搭那轮对齐，便于比较）：

| 参数 | 建议值 | 理由 |
|---|---|---|
| 训练轮数 | 2–4 | 139 条 × 4 epoch 在魔搭上是 0.37 loss，没有过拟合 |
| 学习率 | 1e-4 附近（若可调） | 魔搭那轮用的就是 1e-4 |
| 批大小 | 由平台决定 | 不要为了凑步数改 |
| 验证集 | 上传 val，用于挑检查点 | 27 条，只能看趋势 |

**判读 loss**：末位落在 0.4–0.9 属正常；低于 0.3 说明在背 139 条，取中间检查点。

## 4. 部署与调用

训练完成会得到一个模型名（形如 `ft-xxxx`）。百炼的 OpenAI 兼容接口与项目现有配置**完全一致**，所以部署只需要：

| `.env` | 值 |
|---|---|
| `QWEN_BASE_URL` | `https://dashscope.aliyuncs.com/compatible-mode/v1`（不变） |
| `QWEN_API_KEY` | 现有 key（不变） |
| `QWEN_MODEL` | **换成微调后的模型名** |

⚠️ **必须验证 Qwen3 的思考开关**：我们之前把时延从 19s 压到 1.2s，靠的是「空思考块」。百炼侧由平台的 chat template 决定，需要在请求里显式关掉思考（Qwen3 系在 extra_body 传 `enable_thinking: false`，具体字段以百炼文档为准）。

**验证方法**：拿同一道题调两次（开/关），比较首 token 时延和输出长度。如果关不掉，时延会回到十几秒，`≤20s P95` 的目标要重新评估。

## 5. 评测协议（这一步不能省）

换基座后，所有历史分数无效。按下面顺序重做：

1. **同基座基线**——用**未微调的同一个模型名**跑 `heldout2_questions.jsonl`（12 题）和 `eval_questions_v3.jsonl`（45 题）
2. **微调后模型**——同样两批题
3. **本地打分**——用现成的 `60_score_eval.py`，再跑 `61_apply_guardrail.py` 得到过护栏版本

调用的接口就是 DashScope 兼容模式，所以可以用一个小的 OpenAI 客户端脚本跑两批题，产出与 `50_compare.py` 同格式的 jsonl（含 `qid` / `answer` / `prompt`），后续评分和护栏脚本可直接复用。

**判读标准**（沿用魔搭的结论）：

| 结果 | 结论 |
|---|---|
| 微调后 > 同基座 ≥ +4 | 值得用 |
| 微调后 ≈ 基座 | 说明这批数据在这个基座上不奏效，别硬推 |
| 微调后 < 基座 | 弃用，保留云端通用模型 |

> **heldout2 还没被任何模型选型用过**，是当前唯一的干净标尺。百炼这一轮用完它之后，它也会降级为验证集。

## 6. 应用侧不动的部分

这些和平台无关，继续保留：

- 数字核实护栏（`ungrounded_numbers` / `strip_ungrounded_sentences`）
- 禁用词护栏（8 处已修：`×`、引号、`治疗药物`、同服三形态等）
- 提示词里的十条规则——但注意：**百炼会用我们的 messages 原样拼进模板**，所以 system 消息仍然生效
- 检索链路

## 7. 风险清单

| 风险 | 影响 | 应对 |
|---|---|---|
| 基座换了，模板行为不同 | 之前调优的空思考块、模板对齐全部作废 | 先做时延与格式验证再谈效果 |
| 拿不到权重 | 无法本地部署、无法合并、迁移成本高 | 接受平台绑定，或用 API 层做一层抽象 |
| 百炼的计费按 token | 大样本量成本不可控 | 先小批（139 条）验证思路，再决定是否扩 |
| 数据里含内部文档 | 上传到云端 | 确认权限等级，必要时脱敏 |
| 平台的 min 样本数/最大长度 | 可能卡住 273 条或个别长样本 | 以控制台提示为准，先传 val 试 |

## 8. 建议的执行顺序

1. 控制台确认可微调模型 + 格式限制（半小时）
2. 只导 139 条 → 转 messages → 传 OSS
3. 先跑一个 **小规模试训**（比如全量的 20%）看 loss 曲线形态，再跑全量
4. 同基座基线 → 微调后模型 → 两批题打分
5. 达标再接 `.env`，不达标就停在云端通用模型

第 3 步的试训是我加的：魔搭那边四轮训练里有两轮是白训的，先用小规模确认「loss 会降、格式没被平台改写」，比直接烧全量便宜。
