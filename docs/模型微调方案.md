## 1. 目标与已确认决定

已明确的目标：利用魔搭可用服务器训练，之后调用自有模型，为本项目提供保健品垂类的快速反馈。训练路线采用监督指令微调（SFT），可以使用 LoRA／QLoRA 降低训练资源需求。已经蒸馏好的模型可以继续进行领域 SFT。

最新明确的阶段目标：先理解并亲手观察完整微调链路。因此在魔搭开发环境内完成蒸馏模型加载、原模型推理、数据准备、LoRA／QLoRA SFT、Adapter 加载、训练前后对照和导出，再开展本机部署。当前电脑尚未部署生成模型不阻塞首轮云端实验。优先跑通流程不等于预先承诺业务质量达标。

用户已确认首轮目标是员工知识问答：在已有知识库与产品图谱提供证据的前提下，生成简洁、可追溯的回答，正确处理资料不足与越界请求。生成式演练反馈不纳入首轮，现有规则评阅保持原职责。

最终推理仍以当前 Windows＋Intel Arc 电脑为后续目标；魔搭在首轮同时承担实验推理、训练与对照验证，不要求长期托管。首轮定位为内部演示 PoC，现有虚构产品资料仅用于演示训练，不作为真实商品事实投入真实业务。

首轮目标不包含从零预训练、全参数训练、强化学习或仅凭模型记忆回答产品事实。模型参数规模不会因 LoRA 微调自动缩小。

## 3. 技术路线与模型选择

概念采用以下口径：

- **监督指令微调（SFT）**：用指令、输入和审核答案训练模型执行本项目任务。
- **LoRA**：冻结基础模型，主要训练新增的低秩适配参数。
- **QLoRA**：在量化基础模型上训练 LoRA，主要用于降低训练显存需求。
- **答案蒸馏**：教师模型生成候选答案，经审核后用来训练学生。本方案不要求训练时同时加载教师，也不涉及对齐教师 logits。
- **合并**：将 Adapter 的更新合入对应版本基础模型；是否需要取决于部署方式。
- **部署量化**：为推理降低权重精度，需重新评测；它与蒸馏、训练阶段量化分别记录。

第一轮以“有依据的短回答 SFT”为主，不默认训练长篇思考过程。若选择 R1 系列，必须验证其思考行为、终止行为以及应用能否获取最终答案；不能假设 Qwen 的关闭思考参数对它同样适用。

| 候选 | 定位 | 当前取舍 |
|---|---|---|
| `deepseek-ai/DeepSeek-R1-0528-Qwen3-8B` | 根据前文选型推荐的首轮蒸馏模型 | 在魔搭先加载、推理、做 QLoRA SFT，再加载 Adapter 对照；具体环境兼容与显存需求需试跑 |
| `Qwen/Qwen3-4B-Instruct-2507` | 后续快速反馈与本机部署的可选对照 | 不再作为首轮必须先通过的前置模型，不默认下载或训练它 |

首轮以魔搭上的现成蒸馏模型为训练起点。基线先记录“训练前它怎样回答”，训练后在同一环境、相同输入与推理设置下对比“加载 Adapter 后怎样回答”。基线不需要先证明本机能够部署，也不要求原模型达到最终质量门槛。模型或训练流程若失败，先检查依赖、模板、显存、标签与数据，不把换到更大显卡或另一个模型作为未经诊断的默认步骤。

首轮只进行基于审核指令数据的领域 SFT，不另外开展教师生成或教师蒸馏实验。后续是否引入教师，需根据第一轮错误分析另定范围。

“已经蒸馏的模型”是本轮的基础权重；LoRA 是参数更新方式；SFT 是训练任务。三者可以同时成立。本轮不重新从教师蒸馏一次，也不因在云端进行 SFT 而改变这一性质。

### 首轮必须可观察的完整链路

| 步骤 | 在魔搭完成的操作 | 必须看到或保存的结果 |
|---|---|---|
| 1. 环境与模型 | 在自己的 GPU 开发环境下载同一版本权重、Tokenizer，验证框架支持 | 环境版本、模型 revision、加载方式、实际显存 |
| 2. 原模型推理 | 先在 Notebook／聊天界面测试；需要接口时再在实例内启动推理服务 | 原模型问答与生成设置、思考／最终答案行为；不要求先发布公网服务 |
| 3. 训练数据 | 导入已审核的指令样本，检查分组隔离、模板、tokenization 和答案标签 | 原始审核数据、训练／验证／测试清单、实际编码示例 |
| 4. SFT 训练 | 停止占用同一张卡的推理进程后，运行 LoRA／QLoRA 训练 | 可训练参数、loss、验证结果、显存、检查点和 Adapter 文件 |
| 5. 加载结果 | 训练完成后释放训练进程，加载同版本基础模型＋Adapter | 模型可生成最终答案，Adapter 确实加载；用独立题目与原模型对比 |
| 6. 合并与复测 | 预算和内存允许时加载未量化基础模型合并 Adapter，再加载合并产物 | 完整权重与配置、合并前后对照记录；合并失败不抹去已成功的 Adapter |
| 7. 保存与导出 | 将产物和日志保存到已核验的持久存储，按需下载到本机 | 基础模型版本清单、Adapter、检查点、合并产物、配置、评测和文件校验信息 |

Notebook／命令行推理本身足够完成步骤 2；仅调用别人托管的模型 API 不能取得它的权重或直接对其微调。部署推理服务与训练是两个进程／阶段，不是在已启动的服务里点开 LoRA 就会更新参数。24GB 单卡上默认顺序执行，避免让推理服务与训练同时各持有一份模型。

LLaMA Factory 支持原模型推理与指定 Adapter 路径后的推理，两者可使用同类交互界面观察，见 [官方推理文档](https://llamafactory.readthedocs.io/en/latest/getting_started/inference.html)。具体模板以所选 DeepSeek 权重及锁定框架版本的实际支持为准，不照抄文档中的 Qwen Instruct 配置。V1.3 确定使用 LLaMA Factory v0.9.5：该模型已被收录为 `DeepSeek-R1-0528-8B-Distill`，模板名必须是 `deepseekr1`，不能套 `qwen3`。ms-swift 保留为备选框架，不同时安装两套。

Qwen 的非思考版本说明见 [官方模型卡](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507)。DeepSeek 的模型卡说明它使用自身的配置和 Tokenizer，不能套用原 Qwen3 配置，见 [官方模型卡](https://huggingface.co/deepseek-ai/DeepSeek-R1-0528-Qwen3-8B)。模型选择以项目实测为依据，不以数学榜单推断保健品业务可靠性。

**实测发现（2026-10-30，A10 24GB）**：

1. 该权重的 `tokenizer_config.json` 声明 `tokenizer_class: LlamaTokenizerFast`。`AutoTokenizer` 依此加载后**中文编码返回空数组**，模型输出乱码，而 token 数量统计看起来"正常"，整轮基线因此作废。改为 `Qwen2TokenizerFast` 后往返一致（8 汉字 → 7 token）。凡使用该权重，加载后必须先做编码往返自检。
2. 其 `chat_template` **没有 thinking 分支**，`enable_thinking=False` 被接受但不改变渲染结果。思考行为只能通过实际生成观察，不能靠传参假定。
3. 基线上原模型每题思考约 500 token、单题约 19 秒，最终答案约 15–41 token。这与第 7 节"100–200 字、P95 ≤ 20 秒"的目标存在张力，属 LoRA 需要压制的行为，训练后须以同样设置复测。

## 4. 数据准备与审核

### 4.1 数据分层

| 来源 | 用法 | 约束 |
|---|---|---|
| 已有培训文档和演示产品 | 内部演示的任务与表达训练种子 | 每条保留 `data_origin=synthetic` 或混合来源说明；虚构事实不能进入真实业务产品事实集 |
| 教学反例、禁用表达示例 | 生成纠错任务或边界测试 | 反例只能出现在被解释、被纠正的上下文，不能当成肯定性的目标答案 |
| 真实产品标签、可核验资料与正式 SOP | 后续真实业务训练／检索依据 | 必须记录来源、版本、适用产品与审核结果，先确认使用权限及有效性 |
| 教师模型候选答案 | 可选的答案蒸馏数据 | 教师只根据给定资料回答；未经审核的模型输出不能直接进入训练集 |
| 员工或客户真实对话 | 后续独立评测或错误采集候选 | 首轮不默认使用；使用前处理授权、去标识与访问权限，不能直接导出全量日志 |

本轮不向魔搭或教师 API 上传数据。实施时只使用已确认可用于该环境的资料；云端训练与教师生成是不同的数据处理环节，分别记录使用范围。

### 4.2 样本结构

推荐保存审核主数据为 JSONL，每条至少包含：

```json
{
  "sample_id": "sft-0001",
  "task_type": "evidence_qa",
  "question": "康源牌鱼油软胶囊的批准保健功能是什么？",
  "facts": [{"name": "康源牌鱼油软胶囊", "product_id": "P001", "category": "保健食品",
             "approval_no": "国食健注G20250012",
             "claims": ["有助于维持血脂（胆固醇/甘油三酯）健康水平"],
             "suitable_for": ["血脂偏高者"],
             "contraindications": ["少年儿童", "孕妇、乳母", "出血倾向者和出血性疾病患者", "肝功能不全者"]}],
  "references": [{"doc_id": "D006", "title": "D006 产品知识手册（第一册：心脑血管类）",
                  "section": "产品一 · 三、批准功能与人群",
                  "body": "批准保健功能：有助于维持血脂（胆固醇/甘油三酯）健康水平。适宜人群：血脂偏高者。"}],
  "output": "康源牌鱼油软胶囊的批准保健功能是「有助于维持血脂（胆固醇/甘油三酯）健康水平」。它是保健食品，不是药物，不能代替药物治疗疾病。",
  "source_ids": ["D006#P001"],
  "source_version": "D006-V1.0",
  "data_origin": "synthetic",
  "permission_level": "open",
  "group_id": "P001-claim",
  "review_status": "pending",
  "reviewer_id": null,
  "split": null
}
```

主数据保持结构化（问题、结构化事实、参考资料分开），**训练用的用户提示由 `prompt_template` 渲染**，与线上 `_build_prompt` 共用同一套证据分区。把整段提示预先拼好写进主数据会导致训练与推理输入不一致，V1.4 的初版脚本犯过这个错，已改。

V1.6 确定训练数据的排布方式（对齐 LLaMA-Factory 官方 alpaca 用法）：`instruction` 放员工的原话问法，`input` 放证据块（结构化事实 + 参考资料，无证据时为空），`output` 放回答。**这带来一条必须执行的后续项**：线上 `_build_prompt` 目前是"证据在前、问题在后"，P5 接入时必须把它改为"问题在前"，否则训练与线上输入分布不一致；若届时不能改线上，则改用 `--style production` 重新导出，保持与线上一致。

按 LLaMA-Factory 官方数据说明，落盘时还有三条硬约束：

1. 用户提示 = `instruction` + `"\n"` + `input`。本项目把四段提示整体放进 `instruction`、`input` 留空字符串，这是官方示例数据集（`alpaca_en_demo.json`）的写法。
2. 落盘字段只保留 `system`／`instruction`／`input`／`output`；`sample_id`、`group_id`、来源等可追溯信息另存 `index.jsonl`，不进入训练文件。
3. `dataset_info.json` 必须与数据文件同目录。推理模型若无 CoT，框架会自动补空 CoT，`enable_thinking` 决定这段空 CoT 算不算损失，且**训练与推理必须取同一值**；本项目统一取 `false`，与 Q11"只学最终答案"一致。

上例只说明数据结构，审核状态为待审核，不是可训练样本。训练前只导出审核通过的数据。[LLaMA Factory 数据格式](https://llamafactory.readthedocs.io/en/latest/getting_started/data_preparation.html)

答案尽量包含结论、必要限制、与资料一致的出处标识；不为凑格式强行给每个问题相同段落。来源标识须与输入中实际存在的文档对应。缺资料时明确缺什么；资料充分的正常问题要正常回答，避免训练成一律拒绝。

### 4.3 划分、数量与覆盖

1. 先按原案例、问题族、产品事实或对话组定义 `group_id`，做近重复去重，再分组划分；同源改写、教师生成变体和同一对话不得跨集合。
2. 锁定独立测试组后再生成训练变体，后续若引入教师扩写也遵守同一隔离规则；测试问题与答案不用于训练、调参或指导后续扩写，验证集用于挑参数与检查点。
3. 已确认先交付 20–30 条候选样本，由用户逐条审核口径，再扩展到约 100–200 条开发用审核样本，验证格式、标签、显存和训练恢复。只有审核通过的样本可训练，这批数据不充当最终测试集。
4. 质量与覆盖通过后，可提出约 800–1500 条训练／验证样本的扩展建议，按组约 9:1 划分；最终质量评测另建约 200 条独立业务测试题。大批扩展不是本轮自动执行范围，需先复盘小样本结果与预算。数量只是工作量起点，不是效果保证，来源组过少时应扩展资料而非批量改写凑数。
5. 测试包含正常问答、资料不足、资料矛盾、教学反例、资料内恶意指令、角色权限边界和业务红线；高风险与资料不足题须分别报告，不能被总体准确率掩盖。

试验可区分两种隔离目的：业务事实问答允许训练与测试使用相同版本的检索知识库，但问题族不交叉；新增产品泛化测试应将整个产品族留出，评估能否根据新提供的资料回答。两种结果不能混称“未见产品能力”。

审核关注事实与来源一致、虚构信息标记、错误话术未被肯定、权限正确、答复简洁、无无依据补充。高风险内容需要具备相应业务／合规审核能力的人确认，不能只靠教师自评。自动规则和人工审核分别保存结果与原因。

共享给学员的模型权重不得训练仅主管可见的受限题库答案、受限案例参考答案或其他不可向学员披露的内容。把受限答案写入权重后，运行时的检索过滤无法可靠消除模型记忆。首轮共享模型仅采用符合目标角色权限的问答内容；题库与案例可用于设计测试，但在确认披露范围前不直接转成共享模型的训练目标。未来确需按角色训练时，另行讨论数据与模型隔离，不能仅靠提示词约束。

## 5. 环境与基线

### 5.1 魔搭训练环境

首轮主用 24GB CUDA 环境开展 8B 蒸馏模型的推理与 4bit QLoRA 小试（Q12 修订）：该环境的驱动、框架与量化后端组合有最多的公开用法可参照，代价是显存紧、且 bitsandbytes 在 CUDA 13 + torch 2.13 上能否安装成为首轮最大不确定项。训练从小规模起步，确认一次完整前向／反向后再放大。使用独立虚拟环境，固定模型 revision、Tokenizer、训练框架版本、PyTorch、驱动／CUDA、量化后端与随机种子，不直接改本地业务 `.venv`。

实施前查看实际 GPU 型号、可用显存、磁盘、网络、实例时限、产物持久化与下载方式。先测模型加载、前向、反向、保存和恢复。截图中的剩余额度是当时状态，不能保证未来时长，也不能承诺一次额度足够训练完成。

AMD 192GB 环境作为备用：仅在 CUDA 上「框架装不上」或「QLoRA 与 BF16 两条都不通」时启用，届时改跑 BF16 LoRA（192GB 无需量化，也便于原地合并）。ROCm 上 LLaMA-Factory 没有官方保证，切换前先确认框架能加载 8B 并完成一次前向。CPU 环境用于清洗、审核与 tokenize 自检，不作为首轮大模型训练环境。CUDA 与 ROCm 的安装命令不互相照搬——尤其不能让 pip 在 ROCm 环境里装一份 CUDA 版 torch。不为演示完整链路默认启动两套 GPU 实例。

已确认首轮 GPU 实例累计运行预算最多 8 小时、最多两组正式参数实验，仅使用已有可用额度。预算涵盖 GPU 实例运行期间的准备、等待、下载、原模型推理、试跑、训练、Adapter／合并模型推理与导出；若更换 GPU 实例，累计时长不重置。启动前核查实际额度和计费状态，设置累计用时记录与保存、停止机制；额度不足或预计无法在预算内完成时先停止扩大实验。达到上限前保存产物并停止实例，不自动付费、扩容或增加实验组。只结束训练进程并不代表实例停止计时，需核实平台停止状态。

### 5.2 训练前的两类基线

- **首轮云端生成能力基线**：在魔搭给原模型和加载 Adapter 的同一基础模型相同的已冻结证据输入、任务与输出预算，比较答案质量、长度和生成耗时。这里直接推理自部署权重，不额外调用外部教师 API。
- **后续系统基线**：接入项目时沿用真实检索、图谱、权限和护栏，记录请求到可展示答案的完整路径。当前本机的旧系统不作为首轮训练前必须部署新模型的条件。既有第三方云端配置可保留，后续仅在明确的手动切回或对照范围内使用。

首轮记录魔搭上的输入长度、生成设置、思考 token、最终答案 token、最终答案首片段和完整生成耗时，冷启动与预热分开。本机接入阶段再分别计量检索、Embedding、图谱、提示处理、模型首 token、首个通过护栏可展示片段和完整回答耗时，并考虑共享设备资源的影响。不能用云端速度推断本机速度。

## 6. SFT 训练与调参

先单卡小规模确认流程，再做有限实验，不直接大范围扫描参数。推荐起点如下，所有值待选定模型及小试后确定：

| 项 | 建议起点或检查方式 |
|---|---|
| 训练任务／更新方式 | `stage: sft` + `finetuning_type: lora`；主用 CUDA 24GB 走 `quantization_bit: 4`，AMD 备用走不量化 BF16 |
| 量化细节 | 主路线即用 bitsandbytes 4bit；CUDA 13 + torch 2.13 上能否安装是首轮最不确定项，失败先退 BF16 LoRA（24GB 很紧），再退 AMD |
| LoRA rank | 先 8 或 16；target modules 根据所选模型实际结构和框架支持核对 |
| 学习率 | 首轮可比较 `2e-5` 与 `5e-5`，不机械照抄其他模型最佳值 |
| 单卡 micro batch／梯度累积 | 从 1／8 起步，单卡有效批次为 8，再按显存和样本长度调整 |
| 序列长度 | 统计真实样本 token 分布后确定，2048 仅用于小试；需要时测试 4096，不静默截断答案或关键依据 |
| 训练轮数 | 从 1–3 轮范围内按验证表现选择，不以训练 loss 最低为唯一标准 |
| 精度／显存优化 | 依据实际硬件选择 BF16／FP16，按需启用梯度检查点；不强制安装额外加速算子 |
| 损失范围 | 对指令问答优先监督 assistant 答案，核对 prompt、来源文本与 padding 的标签遮罩 |
| 保存策略 | 每个实验独立目录，保留中途检查点、优化器与调度器状态；验证恢复后再扩大训练 |

训练配置应设置不自动发布到模型 Hub。对话模板必须匹配完整模型版本；R1 蒸馏权重与 Qwen Instruct 分别验证，不共享未经核对的模板。抽查实际 tokenized 样本与有效标签，不能只检查 JSON 能否解析。

推理采样参数也需要单独验证。当前问答使用 `temperature=0.0`，更换模型后不能认定该设置仍然合适，也不能把温度设为零解释为结果绝对可复现；基线与微调对照使用有记录且可比较的设置。

每次实验记录数据清单及哈希、训练／验证分组、基础模型 revision、模板与参数、随机种子、耗时、峰值显存、loss 曲线和验证业务结果。验证表现开始退化时减少训练、检查数据或调整配置；反复使用过的测试集须标记为回归集，下一轮另设未见测试集。

SFT 与 LoRA 可以直接组合，框架配置示例见 [LLaMA Factory SFT](https://llamafactory.readthedocs.io/en/latest/getting_started/sft.html)；量化后训练适配器的约束见 [PEFT 量化指南](https://huggingface.co/docs/peft/developer_guides/quantization)。

## 7. 评测与通过标准

按“魔搭原模型 → 魔搭基础模型＋Adapter → 魔搭合并模型 → 后续本机量化部署 → 项目端到端”逐级对照。检索失败要单独记录，不能把召回问题全部归因于生成模型。

首轮先验收链路可复现：原模型能推理、审核数据可加载、SFT 能完成并保存、Adapter 能重新加载、独立题目训练前后可对照、产物与配置可导出。合并操作在预算与资源内验证；即使无法完成合并，能加载的 Adapter 也应完整保存并报告未完成项。链路跑通不等于回答质量已经改善，更不等于可以用于真实业务。

以下为用户已确认的内部 PoC 验收目标；真实业务准入还需要真实资料与独立审核。100–200 条流程小试只能证明训练流程可运行，最终质量达标须在独立测试集上判断：

| 指标 | 已确认规则 |
|---|---|
| 证据支持的回答正确率 | 正常测试题中至少 90% 满足人工评分标准，并报告相对原模型的变化 |
| 资料不足处理 | 对应子集中至少 95% 正确说明不足或请求补充；同时统计正常问题误拒答 |
| 高风险错误 | 固定红线集出现允许停药、替代治疗、伪造产品事实等严重错误时，本候选不通过；不以原模型已有同类错误作为豁免 |
| 引用与事实对应 | 如输出来源标识，必须能对应输入资料；虚构引用或批准文号单独列错 |
| 权限与资料隔离 | 既有角色边界、受限案例／题库不可因模型替换被绕过；权限由服务端执行 |
| 模型质量与系统护栏 | 分别报告原始生成错误及护栏后暴露错误，不能以全部被护栏拒绝冒充模型改善 |
| 流式与输出完整性 | 无思考内容误展示、无空白最终答案、无截断被当成成功、终止与错误事件正确 |
| 快速反馈 | 单人使用、正常回答约 100–200 字，预热后首个可展示片段 P95 ≤5 秒、完整回答 P95 ≤20 秒；报告模型首 token 与护栏后片段的区别，不保证尚未实测的设备表现 |

固定测试集上零严重错误只代表该次有限观察，不保证现实世界零风险。小样本需报告分子／分母与失败示例；不将 36 条检索样例的 R@K 当成回答正确率。

可复用的资产包括：`tests/test_domain/test_safety_acceptance.py` 的风险用例、`tests/test_application/test_answer_question.py` 的权限与降级行为、`tests/test_application/test_answer_question_stream.py` 的流式审核、`tests/test_application/test_multi_hop.py` 的证据与多跳边界、`tests/test_application/test_review_drill.py` 的摘要卡边界，以及 `08_数据入库/milvus/verify_v2.py` 的检索评测。这里的 `tests/` 相对 `项目代码/`。这些多为规则或测试替身检查，需补充真实候选模型生成评测；本轮没有运行它们。

延迟对照在相同模型、相同设备、相近输出长度下进行。跨模型比较应分别报告回答长度、思考及最终答案 token 数；合并和量化不保证在每种硬件上都加速。Q6 的本机时延是后续项目接入验收目标，不是首轮魔搭训练的前置门槛，也不是已达到的成绩。本机阶段若无法达标，定位瓶颈并报告，不以悄悄降低门槛使实验通过；该结果不否认此前云端链路是否成功。

测试输入长度按项目实际提示词分布选择，不能只用一句短提示词测速度。质量测试题可以重复计时以观察抖动，但这些重复不扩大独立质量样本数；记录成功、超时、截断和失败的数量，不只统计成功请求。

## 8. 导出、本地部署与项目接入

### 8.1 导出顺序

1. 保留最优 Adapter、对应基础模型版本、Tokenizer、模板、训练配置及数据清单。
2. 推理框架支持时，可以直接加载基础模型与 Adapter，合并不是训练成功的必要条件。
3. 需要完整权重时，按 LLaMA Factory 常规流程重新加载相同版本的未量化基础模型，再合并 Adapter；不要直接将训练时的 4-bit 基础权重作为合并目标。
4. 对合并产物回归评测；再按目标推理框架选择量化／转换，对量化产物再次评测。[合并与导出文档](https://llamafactory.readthedocs.io/en/latest/getting_started/merge_lora.html)
5. 不同产物分别记录哈希与评测结果，不覆盖原 Adapter 和可回退基础配置。

### 8.2 推理位置与服务

已确认首轮在魔搭进行原模型实验推理、训练和微调后推理，完成理解链路所需的闭环。最终本机部署后置：届时再验证支持 Intel Windows 设备的推理后端与量化格式，不能假设 CUDA 训练成功后就能直接用相同服务在本机运行。魔搭实验不要求公网发布或长期托管服务。

### 8.3 最小接入范围

后续实施可能涉及以下位置，本次方案整理不修改它们：

| 位置 | 计划核查／变更内容 |
|---|---|
| `项目代码/config/settings.py` | 为本地模型提供独立 provider、地址、模型标识与可用性配置，不长期借用 qwen 字段伪装本地端点 |
| `项目代码/config/assembly.py` | 组装本地模型与现有端口；明确哪些任务切换、哪些保留旧模型 |
| `项目代码/infrastructure/llm/openai_compatible_adapter.py` | 验证服务协议、流式解析、终止原因、超时与错误分类，必要时做最小兼容改动 |
| `项目代码/config/startup_check.py` | 核查现有 Key 判断是否适用本地服务，区分有配置与服务真实可用 |
| `项目代码/application/use_cases/answer_question.py` | 对齐训练输入与运行提示模板，保留图谱、检索、权限和独立输出审核。**V1.6 起训练数据为"问题在前、证据在后"，接入时须同步调整 `_build_prompt` 的分区顺序，或用 `--style production` 重新导出** |
| `项目代码/tests/test_infrastructure/`、`tests/test_application/`、`tests/test_interfaces/` | 针对新增 provider、模板、分类、SSE、错误及问答链路执行必要回归 |

模型端口具有分类能力，但问答当前默认使用纯规则意图分类。首轮建议保持该规则路径，只迁移生成；若后续启用 LLM 分类，再显式决定其模型路由，并回归标签与 `unknown` 行为。适配器当前分类调用的输出上限为 16 token，不能直接让长思考模型接管。适配器还仅读取 `message.content`／`delta.content`，没有现成的 `reasoning_content` 处理或思考开关，必须验证服务端模板及最终答案解析。

后续项目接入时，新演示模型链路失败仍返回可解释的不可用状态，不自动发送请求到现有第三方云端备用模型。首轮在魔搭自部署权重并推理是已明确的实验流程，不属于隐式云端回退。保留旧配置和部署产物，以便手动切回；不改变其他既有链路的策略。模型切换不需要重建数据库或向量库。

## 10. 决策记录与实施顺序

### 第一轮：已确认的三个根问题

**Q1：首轮是否只训练员工知识问答？**

决定：是，用户已确认。先验证“问题＋证据 → 简洁可靠答案”；演练角色扮演、生成式评阅和自动打分不纳入首轮。现有规则评阅保持原职责。

**Q2：最终推理是否以当前 Windows＋Intel Arc 电脑为目标？**

决定：最终本机推理目标保留。最新说明将顺序修订为先在魔搭完成原模型推理、训练与微调后复测，本机部署后置，不再作为训练前置条件。

**Q3：首轮是否定位为内部演示 PoC，现有虚构资料仅用于演示训练？**

### 第三轮：实施口径（2026-10-30）

**Q9：训练框架选 ms-swift 还是 LLaMA Factory？（V1.3 修订）**

V1.2 决定：ms-swift v4.6.0，理由是其支持表点名该模型，且有思考 token 的显式损失处理。

V1.3 改定：**LLaMA Factory v0.9.5**，由用户选定。该模型已被收录为 `DeepSeek-R1-0528-8B-Distill`，模板必须显式写 `deepseekr1`，不能套 `qwen3`。据此新增两项约束：其一，LLaMA Factory 的常规安装会自带一份 PyTorch，**在 ROCm 机器上会废掉镜像的 ROCm 轮子**，因此改为复用镜像 torch 的虚拟环境，并在真实安装前用 `pip install --dry-run` 拦截 torch 重装；其二，`deepseekr1` 是代码内模板，与 tokenizer 自带 `chat_template` 应当等价但未逐字验证，属首次运行必须核对项。ms-swift 保留为备选，不同时安装两套。

**Q10：依赖、权重与产物落在哪里？**

决定：全部在 `/mnt/workspace` 下（`venv`／`models`／`data`／`output`／`logs`）。虚拟环境用 `--system-site-packages` 复用镜像自带 torch，并在真正安装前用 `pip install --dry-run` 检查是否计划重装 torch；一旦重装即中止并回报，不现场拼依赖。权重下载显式指定 `cache_dir`，避免落到 `/root/.cache` 关机即失。实例单次上限 10 小时、空闲 1 小时自动关机；自设累计 8 小时上限不变。

**Q11：思考链是否进入训练目标？**

决定：不进入。训练样本只给最终答案，训练时不构造思考段；推理时思考段留在 `reasoning_content`，只取 `content`。不依赖 `enable_thinking=False`——该开关对 R1 蒸馏版没有官方保证。切换框架后需额外核对 `deepseekr1` 模板是否会在 assistant 段自动插入思考起始标记：若插入，而我们样本不含思考内容，训练与推理分布即不一致，表现为 Adapter 输出格式异常，届时改样本或换模板，不硬训。

**Q12：首轮主用 AMD 192GB 还是 CUDA 24GB？（V1.4 修订）**

V1.3 决定：主用 AMD 192GB（理由是无需量化、绕开 bitsandbytes 风险、可原地合并）。

V1.4 改定：**主用 CUDA 24GB，AMD 192GB 作为备用**，由用户选定。代价是 bitsandbytes 成为必经环节，CUDA 13 + torch 2.13 上的兼容性成为首轮最大不确定项。据此设三级降级：① bnb 4bit QLoRA（`sft_qlora_cuda.yaml`）；② bnb 不可用则 BF16 LoRA 挤 24GB（`sft_lora_cuda_bf16.yaml`，需降序列长度）；③ 两条都不通才换 AMD（`sft_lora_amd.yaml`）。环境安装脚本按厂商分流：CUDA 默认保留镜像 torch 并内置 bnb 自检，必要时 `TORCH_MODE=fresh` 由 LLaMA-Factory 自带一份稳定 torch；ROCm 强制保留镜像 torch。此决定不改变自设的 8 小时累计预算。
