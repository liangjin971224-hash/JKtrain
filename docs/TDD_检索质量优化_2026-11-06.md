## 1. 设计原则

沿用项目既有架构约定，不为本需求引入新模式：

1. **端口/适配器**：Rerank 是新能力 → 域层声明 `RerankPort`，基础设施层给实现，装配根注入（照抄 `CachePort` → `InMemoryCacheAdapter` 的模式）。
2. **降级优先**：任何新组件失败都不能让问答不可用（`rerank_enabled=false` 一键回到现状）。
3. **领域层零框架**：`RerankPort` 不 import sentence-transformers，与 `VectorSearchPort` 同规矩。
4. **红线语义不变**：rerank 只重排「已通过权限过滤与分数阈值」的候选，不参与判空决策。

## 4. 模块设计

### 4.1 RerankPort（新增 `domain/ports/rerank_port.py`）

```python
class RerankPort(Protocol):
    def rerank(
        self, query: str, hits: list[FusedHit], *, top_k: int = 5
    ) -> list[RankedHit]: ...
```

- 新值对象 `RankedHit(FusedHit)`：加 `rerank_score: float`、`original_rank: int` 两个字段（放 `domain/value_objects.py`，风格同 `VectorHit`）。
- 输入用 `FusedHit`（融合后的统一形态）；`FusedHit` 需暴露块文本——确认现有 `FusedHit` 已含 `ChunkMeta.text`，若不含则取 chunk 的只读引用，**不在领域层复制文本**。
- 失败语义：适配器内部异常 → 抛 `RerankError`（挂到 `infrastructure/exceptions.py`，被接口层 `is_infrastructure_error` 识别为 503）；但用例层捕获后**降级为原排序**并记 warning——rerank 挂了问答不能挂。

### 4.2 BgeRerankerAdapter（新增 `infrastructure/rerank/bge_reranker_adapter.py`）

- 模型：`BAAI/bge-reranker-v2-m3`（CrossEncoder，~2.2GB，与 bge-m3 同家族，中文表现好）。
- 加载：照抄 `milvus_search_adapter._ensure_model()` 三件套——
  - 模块级 `TRANSFORMERS_OFFLINE=1` / `HF_HUB_OFFLINE=1`
  - 惰性加载（`__init__` 不碰权重）
  - CUDA 失败 → 回退 CPU（本机即 CPU 路径；20 条候选 CPU 约 300~800ms，问答总延迟占比可接受，量入 `rerank_timeout_sec` 超时熔断）
- 推理：`query-chunk text` 成对打分，batch=16；`max_length=512`（reranker 输入是「问题+块」，块超长按现有切块粒度可接受，截断尾部）。
- **注意与 bge-m3 的显存共存**：若两者都上 GPU，合计 ~4.5GB，8GB 卡可容纳但需验证；CPU 回退路径必须实测可用。

### 4.3 retrieve.py 接入与降级矩阵

接入位置：`RetrieveUseCase` 中 `reciprocal_rank_fusion()` 返回之后、构造最终 Top-N 之前。

| 场景 | 行为 |
|---|---|
| `rerank_enabled=false`（默认首次上线） | 代码路径完全不进 rerank 分支，行为与现状**逐字节一致** |
| `rerank_enabled=true`，端口构造失败（`container.rerank is None`） | 跳过，记一次 warning |
| `rerank_enabled=true`，单次调用异常/超时 | 本次请求用原排序，记 warning；不熔断全局（简单优先） |
| 候选数 < 2 | 跳过（无重排意义） |

细则：

- 候选池 = RRF 融合后向量路 + 关键词路的 Top-`rerank_candidate_k`（默认 20）；**图谱路命中的结构化结果直接保留在前排**，不参与 rerank（图谱命中是精确边查询，没有「语义排序」问题）。
- rerank 后 Top-`top_k`（默认 5）与图谱命中合并，顺序：图谱命中 → rerank Top-5（保持现有「图谱权重主导安全类意图」的语义不被破坏）。
- `MIN_VECTOR_SCORE` 判空逻辑保持在融合前（各路原始分数上），rerank **不参与**判空——拒答语义与现状一致（PRD §7 红线 2）。
- 多跳：`query_plan.py` 中每个子步骤最终走同一个 `RetrieveUseCase`，自动继承，无需单独改；验收时用「补钙推荐+禁忌」样例回归。

### 4.4 MIN_VECTOR_SCORE 重校准（新增 `train/scripts/88_calibrate_threshold.py`）

- 输入：retrieval_eval_v1 中全部 gold（query, gold_chunk）对 + 100 条乱码/无关查询。
- 输出：相关对相似度分布（P5/P50/P95）与无关对分布（P50/P95），推荐阈值 = 使「相关召回 ≥99% 且无关误放 ≤1%」的分位点；打印建议值与依据。
- 人工确认后改 `retrieve.py` 的常量与**注释里的依据数字**（0.55–0.78 这段注释必须同步更新，否则下一个接手的人会被误导）。

### 4.5 检索评测集 schema

`train/data/retrieval_eval_v1.jsonl`，每行：

```json
{
  "qid": "re-001",
  "origin": "gen_b | judge_a | miss_log",
  "question": "客户问这款能不能改善视力，我该怎么答？",
  "intent": "功能声称",
  "collection": "health_training_docs",
  "allowed_permissions": ["public", "internal"],
  "gold_chunk_ids": ["D005-004-01"],
  "notes": "人工抽检备注（可空）"
}
```

- 一条查询允许多个 gold（同义块）；`origin` 记录来源便于分层分析。
- `hard_negatives_v1.jsonl`：`{qid, chunk_id, source: "judge_a" | "mining"}`。

### 4.6 Codex 标注工作包（脚本 80/82/83/84/85）

工作包是一个自包含目录，你把它丢给 Codex 执行即可，**Codex 不需要访问 Milvus**：

```
train/annotation_wp_v1/
├── ANNOTATION_BRIEF.md        ← 给 Codex 的任务书（口径、格式、示例、禁止事项）
├── chunks/
│   ├── health_training_docs.jsonl   ← 293 条（chunk_id/title/section/text/permission_level）
│   ├── health_case_library.jsonl    ← 117 条
│   ├── health_question_bank.jsonl   ← 140 条
│   └── health_self_test.jsonl       ← 30 条
├── judge_a_queries.jsonl      ← 45 条 v3 评测题 + miss_log 抽样（脱敏）
├── candidates/                ← 82 号脚本预生成的 Top-30 候选（供策略 A）
├── outputs/                   ← Codex 写标注结果到这里
│   ├── gen_questions.jsonl
│   └── judge_results.jsonl
└── outputs/HUMAN_REVIEW.md    ← 分歧/低置信项清单（人工填）
```

任务书要点（写进 `ANNOTATION_BRIEF.md`）：

- **策略 B**：每 chunk 生成 2~3 问，难度三档（关键词式/转述式/情景式）；情景式按 v3 的口吻（「客户问……我该怎么答」）；**禁止出现原文连续 ≥8 字**；问题必须能用该 chunk 独立回答。
- **策略 A**：对给定 (query, candidate chunk) 判 `relevant | partial | irrelevant`；rubric：块含回答该问题所需的核心事实 = relevant；只沾边 = partial（partial 不计入 gold，计入可讨论负例池）。
- 盲评纪律：候选顺序已由 82 号脚本打乱，chunk 元数据中不给权限/审核字段。
- 输出必须逐行合法 JSON，字段名固定。

机器校验（`83_validate_annotations.py`）：

1. JSON schema 校验、chunk_id 存在性、qid 唯一性
2. **近抄袭检测**：问题与 chunk 文本的最长公共子串 ≥8 字 → 打回
3. 重复问题检测（归一化后精确重复 +编辑距离 <0.85 近重复）
4. 产出质检报告（各 collection 条数、难度分布、违规清单）

交叉复判（`84_cross_judge.py`）：用项目现有 Qwen/DeepSeek Key（OpenAI 兼容协议）对策略 A 的判定独立复判一遍；一致 → 收录；分歧 → 写入 `HUMAN_REVIEW.md` 人工裁决。目标 100~200 条经 `85_merge_eval_set.py` 按意图×权限分层抽样合成终版。

### 4.7 Embedding 微调管线

**数据（86/87 号脚本，本地跑，连 Milvus）：**

- `86_build_embed_pairs.py`：retrieval_eval_v1 的 (question, gold_chunk.text) 全量正例 + 题库 question↔knowledge_point 块对；train/val 8:2（val 集与 81 号评测集 qid 级互斥）。
- `87_hard_negative_mining.py`：对全部 580 chunk 的生成问题 + 评测问题跑当前模型检索，Top-10 中非 gold 即难负例；合并 hard_negatives_v1。
- 格式：`{"query": ..., "pos": [...], "neg": [...]}`，兼容 FlagEmbedding。

**训练（云端 `/mnt/workspace`，新增 `train/configs/embed_lora_v1.yaml`）：**

- 方案：bge-m3 + LoRA（r16, alpha 32, dropout 0.05），对比学习损失（MultipleNegativesRankingLoss 或 FlagEmbedding Finetuning），cutoff 512（检索对是「问题↔块」，远短于 4096）。
- 学习率 1e-5~2e-5 起步（比现有 LLM SFT 的 1e-4 低一个量级，embedding 对灾难性遗忘更敏感）；2~3 epoch，看 val R@5 早停。
- 合并 LoRA → 导出完整模型目录（safetensors + `1_Pooling/`，与 sentence-transformers 加载格式一致）。
- **维度断言**：导出后本地跑 `get_sentence_embedding_dimension() == 1024`，不匹配立即报错（`expected_embed_dim` 门禁已有）。

**上线切换：**

1. 新模型放 `models/bge-m3-ft-v1/`
2. `08_数据入库/milvus/build_collections.py` 重跑（读 `EMBED_MODEL_DIR`，全量重建 4 collection，~2 分钟）
3. `EMBED_MODEL_DIR=models/bge-m3-ft-v1` → `main.py` 自检 → 81 号检索评测 + v3 答案级回归 + 1255 测试 + 88 号阈值校准
4. 全过 → 改 `.env` 上线；**任一不过** → `EMBED_MODEL_DIR` 指回旧目录 + 重建 collection，10 分钟内回滚

## 8. 安全与合规

- 标注工作包只含内部培训语料（虚构演示产品设定），在本机 Codex 内闭环处理，不调用第三方在线标注服务；若后续改走云 API，需先确认数据出境约束。

- rerank 不触碰权限过滤结果集之外的数据；审计日志保持现有粒度，`HealthResponse` 的 `ready_ports` 自动带上 rerank 状态，运维可见。
