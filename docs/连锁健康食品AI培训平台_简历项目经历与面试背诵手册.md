## 一、简历项目经历

### 项目名称

**连锁健康食品企业 AI 培训与知识管理平台**

**项目时间：**20XX.XX—20XX.XX（按实际时间填写）  
**担任角色：**AI 应用开发工程师

### 项目介绍

为某连锁健康食品企业定制开发内部 AI 培训与知识管理平台。该企业通过直营网点及加盟门店开展产品销售，总部需要持续向门店同步产品资料、服务流程、售后规范及宣传边界。随着门店和产品线扩展，传统的群文件、集中授课和人工答疑存在资料版本分散、新员工学习周期长、总部重复答疑、门店服务口径不一致等问题。

平台围绕总部培训负责人、区域管理人员、店长和门店员工，提供知识问答、客户情景演练、在线考核、培训任务及学习记录管理功能。总部统一发布培训资料和考核内容，区域及门店按授权查看学习进度、知识薄弱项和考核结果，形成“知识发布—员工学习—情景练习—考核反馈—内容优化”的业务闭环。

针对通用模型在门店问答任务、服务表达和风险边界上的适应不足，基于 **DeepSeek-R1-0528-Qwen3-8B** 使用 **LLaMA-Factory** 完成监督微调，通过 **QLoRA** 在冻结的 4-bit 基础模型上训练 LoRA 适配参数。结合 **BGE-M3、Milvus 与 Neo4j** 构建文本与图谱联合检索，提供版本明确、可追溯的产品及服务依据，并通过规则校验、数字核对和人工复核控制无依据回答与不当宣传。系统支持模型、Adapter、提示词和知识版本的统一管理及发布回滚。

### 开发环境

Linux + Windows + Python 3 + PyTorch + CUDA + Docker + Git

### 涉及技术栈

Python + FastAPI + Pydantic + PyTorch + HuggingFace Transformers + PEFT + LLaMA-Factory + DeepSeek-R1-0528-Qwen3-8B + SFT + QLoRA + bitsandbytes + BGE-M3 + Milvus + Neo4j + MySQL + Redis + Docker + pytest

### 架构设计

采用 **DDD 思想与四层架构**，按知识管理、培训学习、考核评价及模型服务等业务边界组织模块。

- **接口层：**接收员工问答、情景演练、考核提交及后台管理请求，完成参数校验和响应封装。
- **应用层：**组织知识问答、培训发布、考核提交和模型版本切换等用例，协调权限、事务、检索、模型调用与结果校验。
- **领域层：**封装知识发布状态、适用范围、培训任务、答卷提交、考核规则及版本绑定等业务规则，保持与具体数据库和模型 SDK 的独立。
- **基础设施层：**实现 MySQL 持久化、Milvus 向量检索、Neo4j 图谱查询、Redis 缓存、模型推理及外部服务适配。

业务层通过接口使用模型和检索能力；核心业务状态由确定性规则控制。基础模型训练与评测流水线作为独立任务运行，经过评测与发布审核的版本再接入在线问答。

### 项目职责

1. **业务分析与架构设计：**参与企业总部与门店培训需求分析，梳理知识发布、员工问答、客户情景演练、在线考核及培训反馈流程；采用 DDD 四层架构划分用例、领域规则和技术适配，设计总部、区域、门店与员工之间的授权和数据关联。

2. **领域数据集建设：**整理产品手册、门店 SOP、培训教材和客户沟通案例，构建产品介绍、信息澄清、客户异议、售后处理和风险边界等指令样本；完成去重、事实核对、人工审核与格式转换，并按来源及业务语义划分训练、验证与留出评测数据，降低同源问题泄漏。

3. **SFT 与 QLoRA 微调：**基于 DeepSeek-R1-0528-Qwen3-8B，使用 LLaMA-Factory 配置监督微调，通过 bitsandbytes 进行 4-bit 模型加载并训练 LoRA 参数；结合 BF16、梯度累积和梯度检查点控制训练显存与有效批量，完成 Adapter 训练与产物管理。

4. **训练调参与版本选型：**围绕学习率、训练轮次、LoRA rank、样本比例及模板一致性开展对照实验；结合验证损失、业务通过情况、拒答行为和泛化表现选择模型版本，定位扩充样本后出现的过度拒答、产品概念混淆及回答退化问题。

5. **培训知识库与图谱建设：**对企业资料进行解析、切分和版本标记，使用 BGE-M3 生成向量并写入 Milvus；利用 Neo4j 管理产品、产品类别、服务流程、注意事项及来源文档之间的关系，为文本与图谱联合检索提供支持。

6. **RAG 与回答校验：**构建问题澄清、授权检索、上下文组装、答案生成及引用返回流程；根据模型实际使用的上下文校验回答数字与来源，结合风险规则处理不当宣传、无依据结论及证据不足问题，保留安全且有用的回答内容。

7. **模型评测体系建设：**建立产品事实、回答完整性、证据引用、风险边界及拒答行为等评测维度，区分裸模型表现与经过提示词、检索和护栏处理的系统表现；通过同题对比、错误归因和消融实验评估基础模型与不同 Adapter 的效果。

8. **培训业务与数据分析：**开发知识问答、情景演练、培训任务、在线考核及学习记录接口，固定题目与培训内容版本；按区域、门店、课程和能力项汇总完成情况、错题分布及薄弱知识点，支持总部调整培训内容。

9. **知识与模型版本治理：**关联知识文档、片段、图谱事实和历史问答所使用的版本；管理基础模型、Adapter、Tokenizer、提示词与护栏的发布组合，支持灰度验证、失败回滚及缓存失效，减少版本混用。

10. **模型服务化与运行保障：**使用 FastAPI 提供业务接口，分离业务服务与 GPU 推理服务，通过 Docker 部署组件；结合 Redis 缓存、请求限流、并发控制、健康检查和脱敏日志监控服务状态，定位检索、生成及校验环节的延迟和失败原因。

## 三、面试常见问题与参考答案：35 题

### 1. 请用一分钟介绍这个项目

**参考回答：**

这是为一家连锁健康食品企业定制开发的内部 AI 培训平台。企业门店分布较广，总部需要持续更新产品资料、服务流程和宣传口径，原来的群文件和人工培训难以保证知识及时、统一地传达到员工。

平台提供知识问答、客户情景演练、在线考核和门店培训记录。技术上基于 DeepSeek-R1-0528-Qwen3-8B 进行 QLoRA 微调，改善门店问答任务和表达边界；通过 Milvus、BGE-M3 与 Neo4j 提供知识依据，结合规则和评测控制无依据输出。

我重点负责数据构建、微调实验、模型评测和 RAG 校验，并将选定模型接入业务服务，形成训练、评测、发布和反馈闭环。

**速记关键词：**企业门店 → 培训痛点 → 微调适应任务 → 检索提供事实 → 评测与业务闭环。

### 2. 你在项目中具体负责什么

**参考回答：**

我主要负责三条链路：第一，整理审核样本，建立基础模型基线并完成 QLoRA 训练；第二，比较 Adapter、提示词和护栏组合，分析事实错误、过度拒答与泛化退化；第三，接入知识检索、回答校验和模型版本管理。

其中最能体现个人工作的，是扩充数据后留出题表现反而回落的分析。我没有只看训练 loss 或回归总分，而是拆开数据覆盖、拒答行为和留出题表现，选择更稳定的版本。

**速记关键词：**数据训练 → 对比评测 → 检索服务；用具体实验说明贡献。

### 3. 系统如何采用 DDD 四层架构

**参考回答：**

接口层处理 FastAPI 请求与 DTO 校验；应用层组织问答、培训发布、考核提交等用例，协调鉴权、事务和外部能力；领域层封装知识发布、题目版本、答卷状态和培训任务等规则；基础设施实现 MySQL、Milvus、Neo4j、Redis 和模型服务适配。

例如提交答卷时，接口层接收答案，应用层重新检查当前权限并组织事务，领域模型检查答卷是否允许提交和题目版本是否匹配，仓储负责保存结果。

模型可以辅助生成反馈，但不能绕过领域规则把未提交答卷改成通过。四层分工便于替换模型或检索实现，同时保留业务约束。

**速记关键词：**接口收请求 → 应用管用例 → 领域守规则 → 基础设施做适配。

### 4. 已经有 RAG，为什么还要微调

**参考回答：**

RAG 提供回答所需的事实，但不保证模型能稳定按门店任务要求使用这些事实。例如证据不足时仍可能补造信息，或遇到风险问题时把正常知识教学也全部拒绝。

微调主要改善回答习惯、澄清方式和边界表达。会更新的产品事实继续通过知识库提供，确定性校验由规则完成。

我把微调、检索和规则分别评测，避免把检索或提示词带来的收益全部归因于 Adapter。

**速记关键词：**RAG 供事实 → 微调塑行为 → 规则控边界 → 分开归因。

### 5. 为什么选 DeepSeek-R1-0528-Qwen3-8B？它是什么模型

**参考回答：**

它是基于 Qwen3-8B Base，经 DeepSeek-R1-0528 推理数据后训练得到的 8B 模型，不能把它与完整规模的 DeepSeek-R1 混为一谈。模型架构、Tokenizer 和模板要按该模型的配置核对。[官方模型卡](https://huggingface.co/deepseek-ai/DeepSeek-R1-0528-Qwen3-8B)

项目选型考虑中文问答、任务表现、可部署性和训练资源。选择依据来自企业题集基线，不直接把公开数学榜单成绩当成门店业务能力。

对于企业问答，我还关注推理输出长度和延迟，评估最终答案是否稳定，避免为了复杂推理增加不必要的响应成本。

**速记关键词：**8B 衍生模型 → 核对配置 → 业务基线 → 资源与延迟。

### 6. LoRA 的原理是什么

**参考回答：**

LoRA 冻结原始权重，用两个低秩矩阵表示权重增量。以标准形式说明：

```text
W 为 d_out × d_in 的原始权重
A 为 r × d_in，B 为 d_out × r
W_eff = W + (alpha / r) × B × A
```

训练时主要更新 A、B。单个矩阵对应的低秩参数量约为 `r × (d_in + d_out)`，通常小于全量权重参数量。实际总量取决于 rank 和目标模块，需要查看可训练参数统计。[PEFT LoRA 文档](https://huggingface.co/docs/peft/developer_guides/lora)

**速记关键词：**冻结 W → 训练 A、B → 低秩增量 → 查看实际参数量。

### 7. QLoRA 与普通 LoRA 有什么区别

**参考回答：**

LoRA 解决的是用较少参数完成适配；QLoRA 进一步降低基础权重的存储开销，将冻结基座以低比特形式加载，训练低秩适配参数。

它不是把所有参数都用 4-bit 直接训练。前向和反向计算仍涉及较高精度运算，梯度通过量化基座对应的计算路径传到可训练适配参数。[QLoRA 原论文](https://arxiv.org/abs/2305.14314)

项目配置采用 4-bit bitsandbytes 加载与 LoRA 训练，同时结合 BF16 和显存优化。不能仅凭“4-bit”就推导出具体显存峰值。

**速记关键词：**LoRA 减可训练参数 → QLoRA 再压缩冻结基座 → 计算精度与存储精度不同。

### 8. NF4、Double Quantization 和梯度检查点分别解决什么问题

**参考回答：**

NF4 是面向相关权重分布设计的 4-bit 表示；Double Quantization 进一步压缩量化所需的元数据；梯度检查点通过反向时重算部分前向，减少激活保存，用计算换显存。[量化说明](https://huggingface.co/docs/transformers/quantization/bitsandbytes)

这些方法作用于不同部分，不能互相替代。项目 YAML 明确记录了 4-bit、bitsandbytes 和梯度检查点；如果被问实际 NF4、双重量化或优化器设置，需要引用该次运行解析后的配置，不能根据框架可能的默认值猜测。

**速记关键词：**权重表示 → 量化元数据 → 激活重算；原理和实际配置分别说明。

### 9. 8B 模型 4-bit 后大约 4GB，为什么训练还会显存不足

**参考回答：**

`8×10^9 × 4bit` 只是约 4GB 十进制的权重位数估计，不是训练总显存。

还要考虑量化元数据、未量化模块、LoRA 参数及优化器状态、激活、临时张量和运行时开销。序列长度、微批量、目标模块及注意力实现都会影响峰值。

我先查看实际峰值，再按瓶颈调整序列长度、微批量和梯度检查点，通过梯度累积保持合适的有效批量。不能只根据参数量承诺某张卡一定可训。

**速记关键词：**权重只是部分 → 激活与优化器 → 实测峰值 → 调长度和微批量。

### 10. 微调数据是怎么构建的

**参考回答：**

从经审核的产品资料、培训教材、SOP 和咨询案例中整理任务，覆盖正常介绍、产品不明确时的澄清、异议处理、信息不足和风险边界。

每条样本记录来源、版本、业务类别和审核状态，检查事实与回答边界后转换成指令格式。数据不仅包括拒答，也包括可以正常回答的相邻案例，防止模型只学会保守拒绝。

示例结构可以是 `instruction、input、output`，其中 input 提供本题需要的资料，output 展示基于资料作答的方式。隐私材料先处理，不能把受限资料无差别写入共享权重。

**速记关键词：**审核资料 → 场景覆盖 → 来源版本 → 正反对照 → 指令格式。

### 11. 为什么只有 139 条？训练集、验证集和评测集如何划分

**参考回答：**

139 条是选定实验版本的审核样本总数，具体拆分为 128 条训练、11 条验证，不是 139 条全部训练。该轮目标是小规模任务行为适配，不能据此宣称模型已经掌握全部领域知识。

划分时要按业务语义、来源和近重复问题分组，避免同一答案只换一种问法就跨集合。验证集用于调参；一旦反复用某套留出题挑版本，它也承担了开发评测作用，需要另外保留新的最终测试集。

**速记关键词：**139 总样本 → 128/11 → 行为适配 → 语义分组 → 留出不等于永远盲测。

### 12. 训练参数怎么设置？为什么这样设置

**参考回答：**

交付配置中，LoRA rank 为 8、alpha 为 32、dropout 为 0.05；学习率为 `1e-4`，训练 4 个 epoch；单设备微批量为 1，梯度累积为 4，截断长度为 2048，启用 BF16 和梯度检查点。

这些是该轮实验设置，不是通用最优值。rank 控制适配容量，学习率和轮次影响学习幅度，长度决定可见上下文范围。单卡情况下有效 batch 为 4，多卡还要乘数据并行规模，实际更新步数以训练日志为准。

后续调整时，我尽量控制变量，结合验证与业务题集判断，而不是同时改多个参数后直接归因。

**速记关键词：**r8/alpha32 → lr1e-4 → 4epoch → batch1累积4 → 长度2048 → 控制变量。

### 13. LoRA rank 越大越好吗？lora_target=all 是全量微调吗

**参考回答：**

不是。rank 越大，可训练参数和容量增加，但小数据下也可能增加记忆、资源开销和不稳定性，需要用业务评测比较。

`lora_target: all` 表示让框架选择相应的 LoRA 目标模块，不等于解冻基础模型做全量微调。具体覆盖哪些模块，要看框架版本和实际展开结果，并核对 trainable 参数列表。

我会同时记录 rank、alpha、目标模块与可训练参数量，避免只报一个 rank 就认为实验可复现。

**速记关键词：**容量有代价 → 小数据看泛化 → all 不等于全量解冻 → 检查目标模块。

### 14. 训练 loss 下降，就能说明微调成功吗

**参考回答：**

不能。训练 loss 表示模型对参与监督的 token 更容易预测，并不直接代表事实正确、引用正确或边界行为合适。

我会检查验证趋势与真实输出，尤其是正常问题是否过度拒答、风险问题是否越界，以及回答格式是否变化。还要确认训练标签和掩码处理正确，避免把不需要学习的提示内容也当成目标。

loss 用于观察训练过程，最终选型由独立业务评测与错误分析共同决定。

**速记关键词：**loss 看拟合 → 标签掩码 → 验证趋势 → 业务错误与拒答行为。

### 15. 为什么训练、评测和线上必须使用一致的对话模板

**参考回答：**

角色标记、特殊 token、结束符和生成前缀都会影响输入分布。训练时用一种格式，推理时手写另一种拼接，即使权重相同，也可能出现复读、格式异常或明显退化。[Transformers 模板文档](https://huggingface.co/docs/transformers/chat_templating)

项目记录使用 `deepseekr1` 模板并设置 `enable_thinking: false`，训练最终答案。这个设置需要在使用的模板渲染路径中验证，不能推断任意接口收到同名字段都会生效。

排查时固定模型与 Tokenizer 版本，比较渲染后的文本、特殊 token 和输入 token ID。模型配置应按对应仓库核对，不能随意混用其他模型的配置。

**速记关键词：**同模板 → 同特殊 token → 同生成前缀 → 实际 token 核对。

### 16. 为什么数据增加到 300 多条，效果反而下降

**参考回答：**

项目对比中，139 条版本在两组留出题上均通过 11/12；300 条版本在第一组为 9/12，312 条版本在第二组为 9/12，数据增加没有带来该轮留出题的正收益。

可能因素包括新增样本质量、类别比例、拒答样本过多、重复内容和训练设置。回归表现提高而留出表现下降，是泛化退化的信号，但不足以单独证明唯一原因就是过拟合。

我会抽取新增错误做分类，比较新增样本和训练过程，控制总更新量等因素复验。最终选择依据是目标业务表现，不是样本数量更多。

**速记关键词：**更多不等于更好 → 检查分布与质量 → 控制训练量 → 错误分类 → 选业务稳定版本。

### 17. 模型评测具体看哪些指标

**参考回答：**

按场景分别看产品事实、回答完整性、引用支持、应答与拒答、表达边界以及延迟。事实题检查是否与指定版本资料一致；风险题检查是否越界；正常教学题检查是否被误拒。

自动评分器做关键词、必要项和禁用项检查，人工复核语义和业务可用性。BLEU、ROUGE 或另一个模型给出的分数可以辅助分析，但都不能单独代表企业问答质量。

结果必须同时报告分母、样本分布和失败类型，不能只报一个综合通过率。

**速记关键词：**事实 → 完整 → 引用 → 拒答 → 边界 → 性能；规则结合人工复核。

### 18. 两组各 12 题的结果可以说明什么

**参考回答：**

交付表记录：第一组基础模型为 6/12、v6 为 11/12；第二组基础模型为 5/12、v6 为 11/12。分别多通过 5 题和 6 题，说明在这些小规模题目上观察到了改善。

这不是企业线上准确率，也不能仅因为两组都是 11/12 就证明提升稳定适用于所有场景。还要核对题目是否参与版本选择，基线与 Adapter 是否使用相同提示词、证据和护栏。

45 题回归集有训练覆盖，只用于发现退化；45 条参考答案通过评分器，也不能替代真实模型输出评测。

**速记关键词：**保留原始计数 → 小样本 → 同条件 → 防选择偏差 → 参考答案不等于模型输出。

### 19. 如何证明收益来自微调，而不是提示词、检索或护栏

**参考回答：**

做同题消融：固定数据、模板、证据和生成设置，比较基础模型与 Adapter 的裸输出；再对两者施加同样护栏，观察系统输出。

检索收益单独通过无检索、实际检索及固定证据条件比较；提示词变化也作为独立实验因素。保存题目、上下文、输出和评分版本，并区分“模型原始答对”和“被规则替换成安全模板”。

最终完整系统可以使用多种机制，但介绍 Adapter 效果时只引用控制了其他条件的对照。

**速记关键词：**同题同条件 → 裸输出 → 同护栏 → 检索和提示词分别消融。

### 20. 怎么避免模型为了安全而什么都拒答

**参考回答：**

数据与评测都要包含相邻对照：有充分资料的正常介绍应回答，产品不明确时应澄清，资料不足时说明缺口，超出边界的请求才拒绝或转交。

我把正确拒答、错误拒答和遗漏风险分开统计，并检查模型是否把含有风险词的教学问题也全部拦截。规则需要识别否定、引用和教学语境，不能只做字符串命中。

发生过度拒答时，先定位是模型还是护栏，再调整数据比例或规则，不统一放宽所有限制。

**速记关键词：**可答/澄清/未知/拒答四分 → 正反对照 → 模型与规则分开定位。

### 21. 数字护栏怎么做？数字出现在资料里就一定正确吗

**参考回答：**

先以模型本次真正看到的上下文为依据，核对回答中的数字，避免用另一次检索或静态资料替代。产品规格还要关联单位、实体和版本，不能只判断某个数字在材料里出现过。

项目中的数字检查可以拦截部分无依据数值，但不能证明整句正确；相同数值可能属于另一个产品，合法算术推导也可能被简单匹配误拦。

因此我把它作为防线之一，结合实体和语义核对，对被删空的输出返回明确模板，保留错误原因供评测分析。

**速记关键词：**实际上下文 → 数字加单位实体 → 不等于事实证明 → 误拦也要评测。

### 22. 流式输出怎样做校验？危险内容已经发出去还能拦住吗

**参考回答：**

已经发送的内容无法靠后续服务端过滤撤回，所以不能先把未经检查的 token 发给用户，再称它经过护栏。

低风险文本可以缓冲到合适边界后检查再释放，但句级检查也存在跨句语义遗漏。高风险任务采用完整缓冲或经批准模板，检查通过再展示。

项目流式链路会保留上下文与检查状态，完整处理结束符、分句和中断；评测同时覆盖非流式与流式，避免两条路径的校验口径不同。

**速记关键词：**发出不可撤回 → 先缓冲校验 → 高风险完整检查 → 流式非流式同评测。

### 23. RAG 的检索链路怎样设计

**参考回答：**

先判断问题是否缺少产品或场景信息，需要时澄清；再按员工权限、资料状态和版本检索。文档按产品、章节和流程切分，使用 BGE-M3 向量化，Milvus 返回相关片段。

检索结果经过实体核对、去重和上下文裁剪后进入提示词，保留文档、片段及版本标识。回答返回引用，证据不足时说明缺口。

检索单独评估证据召回、错误产品和过期版本，生成单独评估事实与引用，避免把“没有检索到”直接理解为“企业没有这条知识”。

**速记关键词：**先澄清 → 权限版本过滤 → 检索去重 → 带引用生成 → 分层评测。

### 24. 已有 Milvus，为什么还需要 Neo4j

**参考回答：**

Milvus 适合发现语义相近的文本；Neo4j 用于查找明确实体及关系，例如产品类别、注意事项和来源材料的关联。

问题涉及已识别产品及结构关系时，我做有界图查询补充证据，再与文本检索结果核对。同一关系也保留来源、版本和适用范围，图谱不能因为结构化就被当成绝对真理。

不是所有问题都查图。简单流程问答只使用文本即可；引入图谱需要证明它改善了具体关系型问题，不能以组件增加代表效果提高。

**速记关键词：**向量找相似 → 图谱查关系 → 关系有来源 → 按问题使用。

### 25. 产品资料更新后，MySQL、Milvus、Neo4j 和缓存怎么保持一致

**参考回答：**

新资料保存为新版本，MySQL 记录来源、审核状态和同步任务；向量与图谱都携带相同知识版本。后台按稳定标识幂等构建，核对就绪后再发布检索版本。

三套存储不能当成一个本地事务。失败任务可重试和对账，旧任务不能覆盖新发布版本；检索展示前回查有效版本。缓存键带知识和策略版本，发布后失效，不能只依赖 TTL。

历史问答保留当时引用，新问题使用当前版本。若允许暂时使用旧版，需要明确标识，不能静默展示成最新资料。

**速记关键词：**新版本 → 幂等同步 → 就绪发布 → 回查 → 缓存失效 → 历史保留。

### 26. 多门店管理如何避免看到其他门店的数据

**参考回答：**

总部、区域、店长和员工有不同的数据范围。服务端从认证上下文解析身份与可访问门店，不信任客户端随意传入的门店 ID。

权限检查覆盖用例、列表、导出、缓存和检索结果：店长查看本店培训记录，区域人员查看授权门店汇总，普通员工只能查看自己可访问的学习材料与记录。

共享微调数据只包含批准用于共享的内容；门店专属资料通过受控检索提供，不能寄希望于模型权重记住后还能按请求权限准确隔离。

**速记关键词：**认证范围 → 全链路校验 → 缓存检索同约束 → 专属资料不进共享权重。

### 27. 在线考核怎样避免模型随意评分

**参考回答：**

客观题按固定答案和规则评分，题目、答案和评分规则在发布时固定版本。答卷有明确状态和提交记录，重复提交通过幂等与唯一约束处理。

情景演练或主观题可由模型按量表给出辅助反馈，但必须引用员工回答，区分遗漏点与错误点，争议结果交给人工复核。不能只凭一段模型评语就自动修改培训通过状态。

培训统计也需要明确分母，例如按已分配任务计算完成率，避免把未分配人员和重复尝试混入同一口径。

**速记关键词：**客观题确定性 → 主观题证据量表 → 发布版本 → 幂等提交 → 统计分母。

### 28. FastAPI 如何接入模型？为什么业务服务与推理服务分离

**参考回答：**

FastAPI 负责业务鉴权、请求校验、检索和响应组织，GPU 推理服务常驻加载模型，通过受控接口提供生成能力，避免每次请求重新加载权重。

这样可以分别扩展普通业务与 GPU 资源，限制推理并发和排队时间，也便于替换推理后端。调用模型时不长期持有数据库锁或事务。

推理服务需要明确超时、取消、流式协议、版本返回和错误码。业务接口不能因为声明了 async，就假定 GPU 推理或同步 SDK 不再阻塞。

**速记关键词：**业务与 GPU 分离 → 常驻模型 → 并发排队 → 短事务 → 明确调用协议。

### 29. Adapter 发布和回滚怎么管理

**参考回答：**

发布的是一组相互匹配的版本：基础模型、Adapter、Tokenizer、模板、提示词、生成参数、知识版本和护栏规则。

每组版本保存评测记录，先在受控范围验证，再切换发布指针。请求开始时固定组合，避免请求中途混用新旧配置。发现退化后回滚整个已验证组合，而不只是换回一个 Adapter 文件。

加载与切换前检查基座兼容性、权重路径和资源状态；回滚演练还要检查缓存和引用是否跟随正确版本。

**速记关键词：**版本组合 → 评测审批 → 请求固定 → 整组回滚 → 兼容性检查。

### 30. 如何优化响应速度与成本

**参考回答：**

先拆解检索、图查询、上下文组装、排队、首 token 和完整生成各阶段耗时，再看 P95 延迟与输出长度。

优化方向包括减少无关上下文、限制不必要生成、缓存可复用检索结果、分离离线任务和在线推理，以及按负载调整批处理与并发。不能把某次单题延迟当成系统 SLA。

模型量化可能降低权重内存，但不保证任何硬件上都更快。上线前要在实际硬件、长度和并发条件下比较质量、吞吐与延迟。

**速记关键词：**分段测量 → 排队与生成 → 上下文裁剪 → 实际负载比较。

### 31. 线上怎样监控和定位模型问题

**参考回答：**

用请求标识关联检索、模型和护栏，记录版本、耗时、安全错误码、召回数量和拒答类型。监控超时、资源占用、排队、空证据、护栏触发及异常拒答。

日志默认不打印完整员工问题、个人信息和模型上下文。需要分析的样本在授权、脱敏和保留期限约束下单独管理。

故障定位先区分数据、检索、生成、规则与服务错误。模型服务不可用时返回明确故障或批准的替代路径，不能把它归类为业务知识不存在。

**速记关键词：**请求标识 → 版本耗时 → 分层错误 → 脱敏样本 → 明确降级。

### 32. 如何处理提示注入或用户要求模型忽略规则

**参考回答：**

用户输入和检索文档都作为待处理数据，不允许其中的文字修改工具权限、知识范围或系统发布配置。文档进入知识库前审核来源，但仍按不可信内容处理指令。

实际可调用能力由后端白名单和用例鉴权控制，模型输出不能直接变成数据库更新或任意查询。高风险请求经过独立规则与证据校验。

评测中加入“忽略限制”、伪造总部指令和资料夹带指令等样本，验证权限由程序控制，而不是只验证模型能否礼貌拒绝。

**速记关键词：**输入是数据 → 权限在程序 → 工具白名单 → 注入负向测试。

### 33. 自动评分器通过，为什么还需要人工评测

**参考回答：**

规则评分器容易覆盖明确必要项和禁用项，但不一定识别否定关系、实体混淆、因果暗示或看似完整却无依据的回答。

我用包含正常样本、错误样本和边界反例的集合校验评分器本身，并抽样核对自动通过与失败结果。人工评价需要统一标准，对争议样本记录理由，避免完全凭个人感觉。

另一个大模型可以辅助评价，但应固定其版本与规则，并与人工标注对齐。评分器通过率是某一规则体系下的结果，不能直接改名为事实准确率。

**速记关键词：**评分器也要验证 → 语义反例 → 人工统一标准 → 指标名称准确。

### 34. 后续是否考虑 DPO、更多数据或更大模型

**参考回答：**

先看错误来源。如果主要是检索遗漏，先改知识和召回；如果是规则误拦，先改校验；如果是回答偏好不稳定，再考虑增加审核对照样本或偏好优化。

DPO 需要质量可靠的偏好对和相应评测，不是用小规模问答数据直接替代 SFT。扩大样本或模型规模也要衡量收益、成本和部署条件。

我会先建立按业务错误分类的学习闭环，在冻结评测条件下证明改进，再决定增加训练复杂度。

**速记关键词：**按错误定位 → 数据质量 → 偏好对前提 → 评测后再增加复杂度。

### 35. 项目里最有代表性的坑是什么

**参考回答：**

一个代表案例是输出规则误伤正常内容。规格中的乘号曾被当作错误示例标记，导致规格段在上下文处理中被剔除；一些包含风险词的劝阻或教学句，也可能被当成不当宣传。

定位时我保存模型实际输入和规则命中位置，区分检索缺资料、提示词丢资料和输出被过滤。修复后用正常规格、教学引用、真实越界句和否定表达成组回归，检查误拦与漏拦。

这个问题说明，模型、提示词和规则都会影响最终结果，必须记录完整版本链并对失败原因归层。

**速记关键词：**规则误伤 → 保存实际输入 → 命中定位 → 正反成组回归 → 分层归因。

## 五、项目亮点与口述稿

### 1. 微调、检索和规则形成明确分工

微调学习门店任务行为，RAG 提供可更新事实，图谱提供实体关系，规则检查部分确定性边界。各部分可分别评测、定位与替换。

### 2. 按业务表现选择 Adapter

没有仅依据训练 loss 或样本量选择版本，而是结合留出题、回归题、正确拒答和误拒答分析，保留表现更合适的版本。

### 3. 评测包含完整系统与模型消融

裸输出、提示词、检索和护栏各自有评测口径，既检查最终可用性，也避免把系统改进全归因于微调。

### 4. 输出检查绑定实际模型上下文

校验时使用本次真正进入模型的证据，减少因为使用错误上下文导致的误删，并保留单位、实体和版本核对需求。

### 5. 知识发布与模型发布都可追溯

知识按来源和版本组织，模型按基座、Adapter、模板及规则组合发布。历史回答可以定位当时使用的知识和配置。

### 6. 从 AI 问答延伸到培训管理闭环

将问答和演练与课程、考核、学习记录关联，按门店及知识点分析薄弱项，给总部提供内容改进依据。

### 60 秒亮点口述稿

> 我重点强调三点。第一，微调、RAG 和规则各有分工，产品更新不依赖重新训练，回答行为则通过审核样本适配。第二，模型选择基于分层评测，我比较过不同样本规模和 Adapter，并分析扩数据后泛化退化的问题。第三，系统记录知识、模型和规则版本，把问答接入培训、考核与反馈流程，既方便业务使用，也方便定位错误。

## 六、开发中的坑与复盘案例

### 1. 常见问题清单

| 问题 | 表现或原因 | 处理与验证 |
| --- | --- | --- |
| 数据扩充反而退化 | 更多样本带来类别失衡、噪声或不一致目标 | 比较新增错误与分布，控制训练量，检查留出表现 |
| loss 很低但业务不稳 | 拟合样本不代表正确处理新场景 | 同时看语义、证据、边界和误拒答 |
| 训练与推理模板不一致 | 角色标记和生成前缀变化 | 固定模板与 Tokenizer，比较渲染内容和 token |
| 产品不明确仍直接回答 | 训练样本默认已知产品 | 增加澄清任务与正常回答对照，单独评测 |
| 规格中的乘号被误过滤 | 将“×”视为错误示例标记 | 区分规格与示例标记，补正常规格回归 |
| 风险词命中导致过度拒答 | 忽略引用、否定或教学语境 | 场景化规则与正反对照，检查误拦和漏拦 |
| 数字核对使用错误证据 | 校验资料不同于实际输入 | 绑定本次 prompt 证据，记录上下文版本 |
| 合法计算被数字护栏误删 | 只做字面数字存在性检查 | 明确当前取舍，后续引入可验证计算链 |
| 流式答案提前泄露 | token 在检查前发出 | 先缓冲检查，再释放；高风险完整校验 |
| 检索命中旧版或其他产品 | 版本、实体过滤不完整 | 发布状态与实体核对，保存原文引用 |
| Adapter 与基座配置混用 | 权重、Tokenizer、模板不匹配 | 组合版本管理，加载前校验和固定回归 |
| 图谱与向量同步不完整 | 多存储写入不是一个事务 | 持久化任务、幂等构建、就绪发布与对账 |

### 2. 复盘案例：139 条比 300 多条更合适

**背景：**为提升门店问答表现，在审核样本上训练多个 Adapter，并扩充数据尝试改善边界行为。

**现象：**139 条版本在两组留出题上均为 11/12，扩充后的版本在对应留出组降至 9/12；部分回归指标却有所提高。

**分析：**将失败分为正常问题误拒、证据使用错误、产品类别混淆等，检查新增样本比例及训练设置。把结果视为泛化退化信号，不仅凭总分断言唯一原因。

**处理：**采用目标题集上更稳定的版本，新增样本重新分类与审核，后续实验控制样本分布和更新量，保留旧版本与失败结果。

**验证：**同题同模板比较，区分模型原始输出和护栏后输出，检查正常应答、边界题与已有能力是否同时满足要求。

**口述句：**

> 这次实验让我意识到，扩数据必须看增加了哪些行为信号。样本更多、回归分数更高，都不能替代留出表现和错误分析。我的选择依据是目标业务质量，同时保留对小样本和实验变量的解释。

### 3. 复盘案例：护栏使用错误证据造成误删

**背景：**模型根据组装后的上下文作答，输出端进行数字核对。

**问题：**如果校验使用的是静态资料或另一份检索结果，就可能把模型依据实际上下文生成的合法数字判为无依据。

**处理：**统一生成与检查使用的证据输入，绑定版本，保存适当的诊断标识；对数字、单位及实体逐步提高核对粒度。

**验证：**构造证据存在、证据缺失、实体错误、合法计算、上下文被裁剪等情况，检查误删及漏检。护栏通过仍需语义复核，不能等同整段事实正确。

| 不足 | 实际影响 | 改进方案 | 验证方式 |
| --- | --- | --- | --- |

> 目前优先改进三点：扩大并冻结更有代表性的评测集，提高产品澄清和语义边界判断能力，以及优化长上下文下的响应。是否扩大模型或引入偏好优化，要看错误来源和受控实验结果。

| LLaMA-Factory | 组织数据、模板与训练配置 | 只会点界面，讲不清数据和实验 |
| RAG | 用检索证据支持当前问题的回答 | 以为有检索就不会幻觉 |
| Milvus | 向量存储与相似度检索 | 把相似度当成事实正确性 |
| Neo4j | 查询明确实体及关系 | 以为图谱天然正确且无需来源 |
| MySQL | 保存业务事实、版本和学习记录 | 将多存储写入当成同一事务 |
| Redis | 缓存与请求控制等辅助能力 | 忽略缓存的权限和版本维度 |
| FastAPI | 组织业务请求与模型调用 | 把业务 API 框架当成完整推理引擎 |

### 5. 十句话速记

1. 产品事实放在可更新知识库，微调主要改善任务行为。
2. QLoRA 量化冻结基座，训练的是适配参数。
3. 139 条是总样本，训练与验证分别为 128 和 11。
4. 更多数据和更低 loss，都不能替代业务评测。
5. 留出题不进训练，也可能因反复选型产生选择偏差。
6. 裸模型、检索、提示词和护栏的收益需要分开比较。
7. 校验依据必须对应模型本次实际看到的上下文。
8. 数字匹配不等于事实正确，规则通过不等于语义安全。
9. 发布的是模型、模板、知识和规则的匹配组合。
10. 效果数据保留分母和实验条件，能够解释失败比只报高分更有说服力。
