## 3. ★ 组卷算法的两个约束冲突

### 3.1 冲突本身

需求给了两个约束，但它们会打架：

| 约束 | 强度 | 原文 |
|---|---|---|
| 知识点全覆盖 | **硬**（必须满足） | 「组卷结果应满足知识点全覆盖」 |
| 难度配比 | 软（可降级） | 「难度配比：各难度等级的题目数量」 |

冲突场景：要 6 题、3 个知识点、难度各 2 题，但难度 1 只有 1 道。

**取舍：保覆盖，难度降级并写进 warnings。**

理由：覆盖不到的知识点 = 这次没考那个模块，是**实质缺陷**；
难度不准 = 卷子偏难或偏易，是**可接受偏差**。

### 3.2 算法三步

```
① 覆盖优先：每个知识点先保 1 题（这一步保证硬约束）
② 填难度配额：按 quota 补齐，优先从已覆盖知识点里挑
③ 补足题量：轮转知识点，避免某点过量
```

把覆盖放第一步而不是最后校验，因为最后发现问题时已无法补救。

## 4. ⚠️ 过程中发现的 5 个真实缺陷

### 4.1 ★★ 题库 84% 的题干丢失（数据层，最严重）

**现象**：140 道题只有 23 道能解析出题干，117 道正文直接从 `A. 选项` 开始。

**根因**：入库脚本的正则写错。

```python
r"^#{2,3}\s+([QS]\d{3})\s*([★☆]{1,3})?\s*[（(]?[^）)\n]*[）)]?\s*$"
```

`[^）)\n]*` 允许匹配任意非换行字符，而 `\s*$` 里的 `\s` **匹配换行符**。于是：

```
源文件：
    ## Q005 ★☆☆
    （空行）
    **以下哪个标识是保健食品的专用标志？**
    （空行）
    A. 绿色食品标志

正则实际匹配到：
    '## Q005 ★☆☆\n\n**以下哪个标识是保健食品的专用标志？**\n'
                                  ↑ 题干被当成标题的一部分吃掉了
```

`m.end()` 落在题干之后，正文从 `A.` 开始 → **题干永久丢失**。

**修法**：`fix_question_text.py`

```python
# 修前：[^）)\n]*  +  \s*$   → 跨行
# 修后：[^\n]*?(?=\n|$)      → 只吃自己那一行
_Q_RE = re.compile(
    r"^#{2,3}[ \t]+([QS]\d{3})[ \t]*([★☆]{1,3})?[^\n]*?(?=\n|$)", re.M)
```

**结果**：116 条修复成功 / 0 失败 → **140/140 全部可解析**。

> ★ 注意：`text` 改了但**向量没重算**。
> 组卷不走向量（只按知识点/难度筛选），不影响 P6。
> 若要用向量检索题目，需要重跑 embedding。

### 4.2 组卷越界抽题

要求覆盖 `KP_00/KP_01`，卷子里却出现 `KP_02`。

**原因**：「补足题量」那步从全库抽，没限制在要求范围内。

**后果**：主管只要求考「功能声称边界」，卷子却混进「接待流程」，
考试结果无法反映他关心的模块。

**修法**：指定了知识点就锁定候选池。

### 4.3 ★ 覆盖阶段吃掉难度配额（连修两次）

| 版本 | 做法 | 结果 |
|---|---|---|
| v1 | 覆盖阶段随机抽 | 随机到 3 道难度 3，配额只剩 4 道 → 报「不足」，而题库有 28 道难度 3 |
| v2 | 按「题库量/配额」挑最紧缺 | **修反了**：难度 3 比例 28/7=4 被当成最紧缺 → 14 题全抽难度 3，难度 1/2 一道没抽 |
| **v3** | 按**剩余配额**动态挑（剩得多的优先） | ✅ 正确 |

v3 的效果：14 题自然摊成 2:6:4，既不吃光某档，也顺手完成大部分配额。

**验证**：4 个种子下难度配比都精确命中 2/6/7，零警告。

### 4.4 `Field(...)` 后面多了个逗号

```python
difficulty_quota: dict[str, int] = Field(
    default_factory=dict,
),      # ← 这个逗号让整个 Field 变成 tuple
```

**症状**：`AttributeError: 'tuple' object has no attribute 'items'` → 接口 500。

**为什么难查**：报错在运行时，看起来像 Pydantic 的问题，但其实是 Python 语法层面。

同类坑还有：`dict[str, int] = {}` 不能用 —— Pydantic 把 `{}` 当**类属性**
（不是字段默认值），实例上拿到 tuple。

### 4.5 导出时难度配比键是字符串

JSON 存的是 `{"1":3}`，读回来 `ExamSpec` 要求 `int` 键 →
`ValueError: 难度只能是 1/2/3，实际 ['1','2','3']` → 导出 500。

**修法**：`_to_paper` 里转换键类型，脏数据跳过不让导出挂掉。

### 8.1 并发组卷卷号竞争（用户决定：暂不处理，后续优化）

**状态**：⬜ **已知未修**（2026-10-23 用户确认「先不考虑并发，记录下来后续优化」）

**问题**：`BuildPaperUseCase._next_paper_no` 是「先查再插」，存在竞争窗口：

```
请求A: 查到今日已用 1 → 取序号 2
请求B: 查到今日已用 1 → 取序号 2   ← 撞号
请求C: 插入 S1-20261023-002 成功
请求B: 插入 S1-20261023-002 失败（唯一索引）→ 返回 500
```

**当前兜底**：`uk_paper_no` 唯一索引保证**不会产生重复卷号**（数据不会脏），
但第二个请求会拿到 500，主管需要重试一次。

**影响面**：
- 培训场景并发低（通常一个主管出卷），实际几乎不会触发
- 不会产生脏数据，只是体验上偶发失败

**后续优化方案（按推荐度排序）**：

| # | 方案 | 做法 | 代价 |
|---|---|---|---|
| 1 | **重试 + 重新取号** | 捕获唯一键冲突（MySQL errno 1062），重新算卷号重试 2–3 次 | 最小，改 20 行 |
| 2 | `INSERT ... ON DUPLICATE KEY UPDATE` | 撞号就覆盖（不能接受，会丢卷子） | ❌ 不可用 |
| 3 | 独立序列表 + 行锁 | `SELECT ... FOR UPDATE` 取号 | 多一张表，可靠 |
| 4 | 数据库序列 / Redis INCR | 原子自增 | 引入外部依赖 |

**建议采用方案 1**：改动小、无新依赖，且因为唯一索引已经存在，
重试逻辑很直接。等真正出现并发需求时再做。
