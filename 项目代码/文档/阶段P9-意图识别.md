## 1. 缺陷复述（改造前）

`AnswerQuestionUseCase.execute(intent="")` 的默认值是空串，
而接口层**从不传** `intent`，所以永远走：

```python
intent=intent or "开放问答"     # 永远是「开放问答」
```

结果：13 套权重表里只有 1 套被用到。

| 意图 | 图谱 | 向量 | 关键词 | 改造前 |
|---|---|---|---|---|
| 禁忌咨询 | **0.6** | 0.2 | 0.2 | ❌ |
| 要停药 | 0.5 | 0.3 | 0.2 | ❌ |
| 文号查询 | 0.2 | 0.2 | **0.6** | ❌ |
| 设备使用 | 0.2 | **0.7** | 0.1 | ❌ |
| 开放问答 | 0.1 | **0.8** | 0.1 | ✅ 全部走这个 |

**最直接的损失**：问「在吃阿司匹林能吃鱼油吗」时，答案在图谱的
禁忌关系上（这条路最准），但图谱权重只有 0.1，而向量（最不准的一路）是 0.8。
**权重结构与业务判断完全相反。**

## 2. 设计决策

### 2.1 为什么先做规则分类，不做 LLM 分类

| 考虑 | 规则 | LLM |
|---|---|---|
| **是否破坏红线** | 不碰 | ⚠️ 分类器在链路最前面，一旦调 LLM，「召回为空不调 LLM」在链路上被绕过 |
| 延迟 | ~0.05ms | ~300ms 且每次问答都付 |
| 可复现 | 完全确定 | 同一句话可能判两次不同 |
| 覆盖长尾 | 差 | 好 |

**结论**：规则为主，LLM 兜底做成开关，**默认关**。

> ★ 这条决策的关键不是「规则够不够准」，而是**红线**：
> 乱码输入 `zzzzqqqqxxxx` 若先调一次 LLM 分类，就等于「召回为空也调了 LLM」。
> 成本假设一变，后续所有关于「不编答案」的论证都要重算。

### 2.2 为什么放在用例层，不放在接口层

接在接口层的话：

```
POST /api/ask         → 要记得传 intent
POST /api/ask/stream  → 要记得传 intent
CLI / 批处理          → 要记得传 intent
```

**「某个入口忘了传」正是这次缺陷的成因**。放到 `AnswerQuestionUseCase._resolve_intent()`
里就只写一次，任何调用方自动获得意图。

### 2.3 三档取值规则（顺序不能换）

1. 调用方**显式**给了合法标签 → 用它（`intent_source=explicit`）
2. 否则分类器判（`rule` / `llm`）
3. 标签不在权重表里 → **退回开放问答**并打 warning

第 3 条是防「静默兜底」：`weights_for_intent` 对未知标签会返回默认权重，
**日志里看不到任何异常，但实际权重完全不同**，这类问题最难查。

## 5. 红灯记录：两个真实误判

### 5.1 `有.{1,6}么` 把功效询问整类抢走

**现象**：「鱼油有什么功能」→ 判成「产品名查询」。

**根因**：规则 `有.{1,6}么` 里 `.` 匹配到了「什」，于是「有什么」被当成问货句式。

**修法**：负向前瞻 `有(?!什么|啥|哪些|哪几|没有|没)[^什啥哪吗]{1,8}吗`。

★ 教训：**中文里「有」是最常见的虚词之一**。用它做锚点必须限定后面的词，
否则一条规则能吃掉一整类。

### 5.2 「吃了能停降压药吗」没有「停药」二字

**现象**：判成「禁忌咨询」，因为命中了「降压药」。

**根因**：规则写的是标准词「停药」，而客户实际说的是「能停」。

**修法**：补 `能停|能不能停|可以停|可不可以停`。

★ 教训：**规则要按客户的实际说法写，不按标准术语写**。
标准词出现在培训文档里，不出现在客户嘴里。

## 6. 遗留与风险

| # | 项 | 说明 |
|---|---|---|
| 1 | 规则覆盖有限 | 长尾问法会落到开放问答。要提升就打开 `use_llm_fallback`（会破坏「不调 LLM」的成本假设，需单独评估） |
| 2 | 准确率是工程自测 | 30 条用例集不是业务标注集。要业务可信，需请业务方标注 100+ 条 |
| 3 | 「多意图」未处理 | 「补钙的有什么推荐，有什么禁忌」应拆两个子查询，当前只判一个（子查询拆分属另一项遗留） |
| 4 | 意图未用于 prompt | 当前意图只影响权重。按意图切换回答模板（FR-003 后半句）还没做 |
