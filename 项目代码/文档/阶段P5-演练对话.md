## 2. ★ 核心设计：客户台词必须来自脚本

### 2.1 为什么不让 LLM 扮演客户

| 问题 | 后果 |
|---|---|
| 难度不可控 | 同一份答卷两次演练难度不同 → **学员之间无法横向比较** |
| 追问可能跑偏 | 漏掉关键考察点（漏了 F3 就完全测不到禁忌识别） |
| 无法复现 | 学员申诉时说不清「当时客户到底问了什么」 |

### 2.2 实际做法

**台词 100% 来自案例脚本，只有「什么时候进下一句」由状态机判断。**

```
开场「你们有鱼油吗？」
  → F1「血脂有点高，吃这个管用吗」  考功效边界
  → F2「要吃多久」                考不给疗程承诺
  → F3「在吃降压药」              考禁忌识别
  → F4「怎么知道是真的」           考信任建立
  → F5「该不该吃」                考不替客户判断
```

### 2.3 LLM 在演练里的位置

**不在「扮演客户」**，而可能在：
- 学员答完给即时提示（可选，需 LLM）
- 生成模拟答卷做演示（可选）

当前实现没接 LLM —— 演练本体是纯状态机，零依赖。

## 3. 会话状态

### 3.1 状态字段

| 字段 | 说明 |
|---|---|
| `current_question` | 当前该问的问题（结束后为空串） |
| `current_follow_up_id` | 当前追问编号（开场阶段为 None） |
| `progress` | `(第几问, 总问数)`，都从 1 开始 |
| `remaining` | 还剩几问 |
| `turn_count` | 已答轮次 |
| `is_finished` | 是否结束 |
| `duration_sec` | 用时（结束后冻结） |

### 3.2 三个必须校验的点

| 校验 | 报错 | 理由 |
|---|---|---|
| 结束后再答 | `ValueError("会话已结束")` | **静默忽略会让前端以为答成功了**，但内容没进评阅 |
| 空回答 | `ValueError("回答不能为空")` | 空轮次会污染评阅的轮次编号 |
| 案例无开场白 | `ValueError("缺少开场白")` | 没开场白无法开始演练 |

### 3.3 一个容易写错的地方

**构造时 `_finished` 必须恒为 False**，即使案例没有追问。

原因：开场白也是一个问题，必须学员答了才算完成。
初版写成 `len(follow_ups) == 0 and False`（恒 False 但逻辑绕），已清理。

## 5. ⚠️ 演练跑出来的 3 个真实缺陷

### 5.1 ★★ 「替客户判断」整类漏检（最严重）

**发现过程**：模拟一个「说了但不够好」的学员，答「可以的，一起吃没问题」，
系统**完全没报风险**。

**这是项目级漏洞，不只是评阅问题**——P4 的输出护栏也没有：

```python
check_forbidden_claims("可以的，一起吃没问题。")   # → []
check_forbidden_claims("我觉得您应该吃。")         # → []
```

**为什么这是最严重的**：

| 话术 | 风险 |
|---|---|
| 「可以的，一起吃没问题」 | 客户在服降压药，学员替他判断同服安全 —— **可能导致实际伤害** |
| 「我觉得您应该吃」 | 替客户做决定，越界 |
| 「放心吃，肯定管用」 | 替客户担保 + 效果承诺 |

**为什么原有六类都没覆盖**：
它不含禁用词根（不说「降血脂」），也不是效果承诺，是**判断越界**——
一个全新的类别。

**修法**：新增第七类「替客户判断」，5 条规则：

```
JD-01  您应该吃 / 您该用          —— 替客户做决定
JD-02  可以一起吃 / 放心用        —— 越界判断同服（带「咨询」前置排除）
JD-03  放心吃 / 肯定管用          —— 越界担保
JD-04  一起吃没问题 / 不影响      —— 语序变体（否定语在句尾）
JD-05  没事，一起吃就行           —— 让步语在前
```

**验证：漏放 0 / 误拦 0**（9 个违规 + 8 个合规样本）。

**合规样本必须放行**，这些是标准话术：
```
建议先咨询医生后再决定是否同服
一起吃之前请咨询医生
我不建议您自行决定
请您自己判断，我只能提供信息
不能替您决定该不该吃
```

### 5.2 同一句话被报两次

**现象**：
```
🔴 critical「一起吃没问题」      — 越界判断同服安全性
🔴 critical「可以的，一起吃没问题」— 越界判断同服安全性
```

两条几乎一样，学员会怀疑系统在凑数。

**根因**：两条规则命中同一句的不同长度片段（短的是长的子串）。

**修法**：去重规则改为「同位置下片段互为子串时保留最长」。

这个改动踩了**两次**：

| 第一版（错） | 第二版（错） | 最终 |
|---|---|---|
| 键含 rule_type → 「降血脂」被案例规则+全局规则报两次 | 键为「位置+类别」→ 丢掉同句的不同类别违规 | 键为「位置」，片段互为子串才合并 |

**关键平衡点**：

| 情形 | 处理 |
|---|---|
| 同片段被不同规则命中（「降血脂」） | 只报一次 |
| 同位置片段互为子串（「一起吃没问题」⊂「可以的，一起吃没问题」） | 保留最长 |
| 同位置但互不相关（「降血脂」+「带两盒」） | **都报**——两件不同的事 |

第三条最重要：合并会让学员以为只需改一处。有专门测试守住
（`test_unrelated_matches_both_reported`）。

### 5.3 一个死代码

```python
self._finished = len(self._follow_ups) == 0 and False   # 恒 False
```

逻辑绕且没有意义，已清理并写清规则。

### 6.2 一个测试设计上的注意

`test_good_answer_no_critical` 里我特意写了注释：

> 缺警示语会触发 `final_verdict.blocked`，但那**不属于 risk_items**。

这个区分很重要——否则「要素没说到」会被误当成「说了违规话术」，
两者对学员的改进方向完全不同。

### 7.1 关于「语义型触发条件」

案例文档里有这类描述：

| 触发条件原文 | 类型 |
|---|---|
| 「学员回答 F1」 | 顺序型 ✅ 可判定 |
| 「学员报完产品信息后」 | 内容型 ⚠️ 需判断 |
| 「学员回避或含糊」 | 内容型 ⚠️ |
| 「社会证明（他人经验）」 | **这是客户台词类型，不是触发条件** |
| 「折中妥协（给台阶）」 | 同上 |

C04 的「触发条件」列填的其实是**客户的施压话术类型**，不是触发条件。
所以按顺序执行更合理 —— 当前实现就是这个策略。
