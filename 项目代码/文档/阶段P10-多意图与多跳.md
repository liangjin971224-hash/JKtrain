# 阶段 P10 验收记录：多意图拆解 + 多跳检索

> 日期：2026-10-23
> 目标：把未完成事项清单里那条「多意图还没拆子查询」做掉，
> 并加入**顺序多跳**——后一步的检索以前一步的结果为前提下。
> 用户原话：「前一句话查询的结果是后一个查询的前提，
> 比如改善体脂都可以吃什么保健品，其中那种最便宜。」

---

## 1. 要解决的两件事（语义不同，不能混）

| 类型 | 例子 | 语义 |
|---|---|---|
| **并列** | 「补钙的有**什么推荐**，有**什么禁忌**」 | 两个问题互不依赖，各自独立召回，最后合并 |
| **顺序（多跳）** | 「改善体脂都可以吃什么保健品，**其中那种最便宜**」 | 第 2 步的候选集**只来自**第 1 步 |

用户要的是第二种。第一种是清单原文那条。

**为什么必须分开建模**（这是本次最关键的判断）：

- 把并列当依赖 → 「有什么禁忌」被塞进第 1 步的产品集合，
  变成「在推荐的这几个里找禁忌」，范围被无端缩小
- 把依赖当并列 → 「那种最便宜」重新全库检索，
  比出一个**第 1 步里根本没有**的产品

第二种错**在真实数据上错得非常自然**：全店最便宜的保健食品是
「维生素C咀嚼片 98 元」，它和体脂毫无关系，但「最便宜」这个条件它满足。
答案看起来有理有据，实际答非所问。

---

## 2. 关键事实：这个问题的正确答案是「没有」

动手前先查了真实图谱（`jiankangshujuku`）：

```
EFF_09「有助于控制体内脂肪」        目录第 9 项，存在
MATCH (p:Product)-[:CLAIMS]->(EFF_09)   产品数 = 0
P020 代餐奶昔   普通食品   primary_scenario=体重管理
                HAS_WARNING → 「禁止功能声称」，没有 CLAIMS
P014 膳食纤维   保健食品   声称「有助于润肠通便」，不声称控脂
```

**结论**：目录里有这个功能，但**本店没有任何产品声称它**。

这决定了整个设计方向：多跳不能「想办法凑一个答案出来」，
它必须能**如实说出「本店没有」**，并且分得清两句话的区别：

| 说法 | 对不对 |
|---|---|
| 「法规不允许声称改善体脂」 | ❌ **错**（目录第 9 项就是它） |
| 「本店在售产品没有声称该功能的」 | ✅ 对 |

合规培训系统教错法规，比不回答严重得多。

## 4. 设计

### 4.1 两层分离：规划（纯领域）+ 执行（应用）

| 层 | 文件 | 职责 |
|---|---|---|
| 规划 | `domain/services/query_planner.py` | 把一句话拆成有序 `SubQuery`，标注依赖 |
| 匹配 | `domain/services/demand_matcher.py` | 口语需求词 → 目录功能项 |
| 执行 | `application/use_cases/query_plan.py` | 逐跳执行、候选集传递、比价、合并 |

**为什么规划不做成 LLM**：

1. 成本：每次问答多一次调用（~0.3s），而多数问题只有一步
2. **红线**：`AnswerQuestionUseCase` 的约束是「召回为空不调 LLM」，
   规划器在链路最前面，一调就绕过了
3. 可复现：同一句话拆法不同，答案会不一样，排障时说不清

拆错比不拆更贵（多一次召回 + prompt 变长 + 合并出错），
所以规则刻意**保守**：拿不准就只保留一步。

### 4.2 判断「是不是真的在指代前面」

只认**回指词**，不认「顺序连接」：

```
「其中」「里面」「这几个」「上述」「这些」「那种/哪种/哪款」
「最便宜」「价格最低」   →  标记 depends_on_previous=True
「有什么禁忌」           →  只是第二个问题，不标依赖
```

★ 必须**双向测**（`test_dependency_not_triggered_by_plain_second_question`）：
只测「该标的时候标了」会做出一个「永远标依赖」的实现，
那比不做还糟 —— 它会把并列问题错误地收窄范围。

### 4.3 候选集显式传递（本模块的铁律）

```
depends_on_previous=True 的步骤：
    候选集 = 前一跳的 product_ids
    候选集为空 → 明确说「前面没找到，无法比价」
    **不许自己去全库找**
```

**为什么不能靠上下文顺延**：两种做法在结果上能分得出来 ——
集合传参时第 2 跳候选数 ≤ 第 1 跳结果数；顺延则会冒出第 1 跳没有的产品。
前文那个 98 元的维生素C 就是专门用来抓这个错误的诱饵（测试里也放了）。

### 4.4 三种证据必须查齐（`_gather_evidence`）

「只让比价用候选集」是**用了一半的前提** —— 回答正文仍然不知道前提是什么。
所以每一跳先查三件事，把结论作为权威事实喂进 prompt：

| # | 证据 | 决定什么 |
|---|---|---|
| ① | 目录里有没有这个功能（`list_efficacy_catalog`） | **法规上能不能这么说** |
| ② | 本店哪些产品声称了它（`find_products_by_efficacy`） | 有什么可推荐 |
| ③ | 两者都空 | 必须说「没查到」，不替法规下结论 |

### 4.5 新增端口方法（`GraphQueryPort`）

```python
find_efficacy_by_keyword(keyword) -> list[EfficacyRef]   # 目录里按词查
list_efficacy_catalog()          -> list[EfficacyRef]    # 目录全量（十几项）
```

**为什么必须与 `find_products_by_efficacy` 分开**：
后者从 Product 出发，本店没产品声称时必然 0 行。
而「目录里有没有这个功能」是**法规问题**，与库存无关。
混用就是把「法规不允许」和「本店没有」说成同一件事。

## 5. 实测结果（真实三库 + HTTP 链路）

### 5.1 「改善体脂都可以吃什么保健品，其中那种最便宜」

```
跳数: 2   kinds: ['simple', 'price_rank']   depends: [False, True]
  [0] simple      dep=False        候选=()   :: 改善体脂都可以吃什么保健品
  [1] price_rank  dep=previous_hop 候选=()   :: 其中那种最便宜
cheapest: None

答：本店在售的保健食品中，**没有一款**声称「有助于控制体内脂肪」这一功能
   （尽管该功能在国家批准的保健食品目录中存在，编号为第 9 项）。
   ……
   **关于价格**
   上一问没有找到符合条件的产品，所以无法比价。
```

✅ 法规说对了（目录里有，本店没有）
✅ 比价没有硬凑，如实说无法比价
✅ 第 2 步标了 `depends_on_previous`，前端能解释「是在上一问的范围里比的」

### 5.2 「补钙的有什么推荐，有什么禁忌」

```
跳数: 2   kinds: ['simple', 'simple']   depends: [False, False]
  [0] 候选=('P011',) :: 补钙的有什么推荐
  [1] 候选=('P011',) :: 补钙的有什么禁忌
products: ['P011']
```

✅ 推荐段给出了 P011（来自图谱，不是文档推测）
✅ 禁忌段给出了真实禁忌（少年儿童 + 每日 2000mg 上限）
✅ 两跳互不依赖，各自独立召回

修复前的对比：改造前整句被判成「禁忌咨询」，推荐完全没答，产品为 `()`。

### 5.3 单步问题不变（性能约束）

```
「鱼油有什么功能」→ 跳数 1，LLM 只调 1 次，answers/citations 与改造前一致
```

★ 有测试守着（`test_single_step_calls_llm_once`）：单步问题若走多跳，
延迟和成本直接翻倍，P95 立刻恶化。

## 6. 红灯记录：4 个真实缺陷

### 6.1 假替身语义错 → 多跳「假通过」

`FakeGraphQueryPort.find_products_by_need` 是「返回所有保健食品」的简化实现
（只保方法契约，不模拟跳数）。用它测多跳会得到**假通过**：

```
第 1 跳候选 = 所有保健食品（含无关的维生素C）
第 2 跳在这个集合里比价 → 比出维生素C 98 元
断言「候选不能超出第 1 跳集合」→ **通过**
但第 1 跳集合本身就是错的
```

**修法**：替身必须能表达「空列表」这个合法结果
（＝本店没有该功能的产品），并支持注入「没人声称的目录项」。

★ 教训复现：**假替身全绿 ≠ 系统可用**（P4 记过一次，这里是第二次）。

### 6.2 `有.{1,6}么` 把功效询问整类抢走

「鱼油**有什么**功能」被判成「产品名查询」——`.` 匹配到了「什」。

**修法**：负向前瞻 `有(?!什么|啥|哪些|…)[^什啥哪吗]{1,8}吗`。

### 6.3 主题补全补错，反而污染主语

「鱼油有什么功能？蛋白粉有什么功能？」拆开后第二句被补成
「鱼油蛋白粉有什么功能」—— 这是**两个话题**，不是一个主题的两个方面。

**修法**：只在「句首是疑问词/动词/人群词」（即自身无主语）时才补。
判据放句首，因为中文主语在句首。

### 6.4 ★ 单测绿 ≠ 接口可用（本次最有价值的一条）

直连用例跑「改善体脂」，回答正确（说对了法规）。
**走 HTTP 接口，又变回编造**「目录中没有改善体脂等表述」。

**根因**：路由层 `_build_multi_hop` 的 `answer_one` **漏透传 `fact_hints`** ——
多跳查到的事实传不到生成层。同一处还漏了 `product_ids`，
导致护栏拿不到产品类别。

**修法**：补上透传，并新增 `tests/test_interfaces/test_ask_multi_hop_api.py`，
从 HTTP 入口打进去、检查 LLM 实收的 prompt。

**自证过**：把透传删掉，这个测试准确 FAIL（2 failed）——
不是「写了就绿」的假测试。

★ 这是 P4「545 个测试通过后接真环境，一次跑出 5 个问题」的第二次复现。

## 7. 顺带修掉的护栏缺陷（两个，都在真实链路上暴露）

### 7.1 禁词表漏了「体脂」

`_ORDINARY_FOOD_FORBIDDEN` 里只有法规原文「控制体内脂肪」和旧称「减肥」，
**没有客户口语最常用的「体脂」** → 「能改善体脂」被放行。

依据：D005 第 62 行「第 9 项 有助于控制体内脂肪」、第 110 行「旧称减肥」。

★ 但**不能直接加裸词「体脂」**：门店有台「体脂仪」（D010 整篇讲它），
「请用体脂仪测量」是客观描述 —— 实测裸词会把设备类 4/4 全误拦。

**修法**：改走组合式 `_EFFICACY_CONTEXT_RE`（功效动词 + 体脂类词），
双向断言 13 条守着（`TestBodyFatClaims`）。

### 7.2 JD-02「替客户判断」大面积误报

```
误报：「可以喝牛奶补钙」（日常饮食，不是用药安全）
     「本店没有能喝的产品」（名词化定语）
     「孕妇能喝吗」（疑问句，学员在问）
后果：整段合规回答被替换成拒答模板（真机上已发生）
```

根因：原规则任何「可以吃/能喝」都拦。**「能喝」在中文里绝大多数时候
不是在做同服判断**。

**修法**：要求显式出现并列词或药物线索，覆盖三种语序：
```
① 可以一起服用          ② 可以和华法林一起吃
③ 能吃阿司匹林
```
新增 `tests/test_domain/test_overreach_rules.py`（21 条，双向）。

★ 教训：**误报的代价与漏报同级**。

## 10. 遗留与风险

| # | 项 | 说明 |
|---|---|---|
| 1 | 拆解靠规则 | 长尾问法拆不出来（会退化成单步）。要提升需 LLM 拆解，但会破坏「不调 LLM」红线，须单独评估 |
| 2 | 最多 3 步 | 一句塞满逗号会被截断。上限存在是因为一步 = 一次三路召回 |
| 3 | 只支持「比价」一种依赖跳 | 用户要的场景是比价。其他依赖型（如「这款和那款哪个更适合孕妇」）还没做 |
| 4 | 需求词映射有硬编码表 | `_SYNONYMS` 约 40 条。数据层没有「功效别名」节点，这是业务知识，暂放在领域层 |
| 5 | 多跳未做流式 | 流式入口仍走单步。多跳要逐跳输出，需重新设计事件协议 |
| 6 | 比价只在保健食品内 | 普通食品价格不进比价（它没有功能声称，混在一起容易被理解成「有效又便宜」） |

## 11. 一句话结论

**多跳真的跳起来了**：第 2 跳的候选集锁定在第 1 跳的结果内，
且第 1 跳查到的事实会进入生成层 ——
「改善体脂…最便宜」这类问题从「编错法规 + 不比价」
变成「说对法规 + 如实说明无法比价」。
