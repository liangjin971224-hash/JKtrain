## 3. ★★ FR-048「权限变更应即时生效」

### 3.1 问题

如果把角色写进令牌就不管了：

```
学员升主管 → 要等 8 小时令牌过期才生效
主管降学员 → 这 8 小时内他**仍是主管**，能继续组卷、导出试卷
```

后者是**真实的安全问题**（离职/降职当天仍然有权限）。

### 3.2 做法

令牌载荷里加显式标记：

```python
payload = {
    "sub": employee_no,
    "role": role,
    "role_is_snapshot": True,   # ← 提醒：这个角色是快照，不可信任
}
```

每个请求都**回库取最新角色**：

```python
def current_identity(...):
    payload = signer.verify(token)       # 只验签名与过期
    account = repo.get_account(payload["sub"])   # ★ 回库取最新角色
    return Identity(account.employee_no, Role.parse(account.role))
```

### 3.3 实测验证

| 场景 | 结果 |
|---|---|
| 学员升主管，用**旧 token** 访问 | ✅ 立即 200 |
| 主管降学员，用**旧 token** 访问 | ✅ 立即 403 |
| 停用账号，旧 token 访问 | ✅ 立即 401 |

代价：每请求一次 DB 查询。培训系统这点并发完全可接受。

## 5. ★ 安全细节（都是真实攻击面）

### 5.1 登录报错不能区分「用户不存在」和「密码错」

区分了就等于给了一个**账号枚举接口**——攻击者能批量探测哪些工号有效。

统一话术：`工号或密码不正确`。实测两种失败的响应完全一致。

### 5.2 用户不存在时也要跑一次哈希校验

否则：
- 「不存在」立即返回（0ms）
- 「密码错」要等 bcrypt（约 250ms）

通过**响应时间**就能区分账号是否存在（时序侧信道）。

做法：用户不存在时对一个固定假哈希跑一次 verify，让两条路径耗时接近。

### 5.3 签名比较必须用 `hmac.compare_digest`

```python
if not hmac.compare_digest(sig, expected):   # ✅
    return None
# if sig != expected:   ❌ 可通过响应时间差逐字节猜签名
```

### 5.4 停用账号也返回同样的登录失败话术

否则等于告诉对方「这个工号存在，只是被停用了」。

### 5.5 不能停用自己的账号

会把自己锁在系统外。返回 400 明确提示。

## 8.3 ★★★ 上线后发现的身份伪造漏洞（已修，2026-10-23）

### 起因

用户测试日报功能，发现「日志没保存」。排查时发现两件事：

1. **表面问题**：日报页的「工号」是手填输入框，不填就保存失败
2. **根本问题**：那个输入框本身就是一个安全漏洞

### 漏洞实测

原实现里，日报/员工接口的 `requester` 和 `role` 来自**请求参数**：

```python
def save_summary(req: SaveSummaryRequest, ...):
    uc.execute(requester=req.requester, role=req.role, ...)   # ← 信任前端
```

实测结果：

| 攻击 | 结果 |
|---|---|
| 学员传 `requester=M001` 写日报 | **200，写进了 M001 名下** |
| 学员传 `role=manager` 看全部日报 | **200，看到了别人的** |

### 根因

**把身份当成普通参数了。**

身份是由令牌**证明**的，不是由调用方**声明**的。
前端说「我是主管」不算数，令牌说才算。

### 修法（三层，缺一不可）

1. **schema 里删掉字段** — `SaveSummaryRequest` 不再有 `requester`/`role`，
   前端连传都传不进来
2. **路由从 `Identity` 取** — `identity = Depends(current_identity)`，
   工号与角色都来自令牌
3. **补测试锁死** — 7 条测试专门验证「传了别人的工号也还是写自己」

### 为什么 P8 原来没发现

P8 只给「组卷/试卷/日志/账号」挂了 `require_feature` 权限依赖，
**日报和员工这几个路由只做了业务层的数据权限判断，没接身份**。

而当时的数据权限测试用的是 `auth_required=False` + 前端传 `requester` 来
「模拟身份」—— 那正好把这个漏洞掩盖了。

**教训：测试用「传参模拟身份」时，测不出「身份可伪造」。**
必须用真实登录链路。

### 前端同时修的

工号输入框改成**只读**，值由登录态填充：

```javascript
if ($('dlTrainee')) $('dlTrainee').value = AUTH.employee_no;
```

这样既解决了「不填就保存失败」，也消除了「能填别人工号」。

## 8.4 全路由越权扫描（用户要求，2026-10-23）

用户要求「把剩下所有路由再扫一遍」。扫描方法：从 OpenAPI 取权威参数清单，
逐个判断参数是「身份」还是「业务筛选」。

### 又扫出三处

#### ① ★★ `POST /api/ask` 的 `allowed_permissions` 来自请求体

```python
allowed_permissions=tuple(req.allowed_permissions)   # ← 信任前端
```

学员传 `["public","internal","restricted","confidential"]` 就能越权检索受限内容，
直接违反 FR-050「权限过滤必须在检索阶段生效」。

> 当前 `health_training_docs` 里还没有受限内容，所以实测数字没变。
> 但这是**定时炸弹**：一旦加入参考答案/评语标准，立刻变成真漏洞。

**修法**：字段从 schema 删除，检索级别由 `identity.role.retrieval_levels` 决定。

#### ② ★★ 演练会话**完全不校验归属**（IDOR）

`/api/drill/answer` 和 `/api/drill/review` 只按 `session_id` 取会话，
不检查是谁的 —— 知道 session_id 就能替别人作答、看别人的摘要卡。

session_id 是 16 位随机十六进制，不好猜，但会出现在前端、浏览器历史、日志里。

**修法**：加 `_get_own_session()` 校验归属。主管也不能接管学员的实时会话 ——
他要看表现应该看演练记录，不是替学员答题。

#### ③ `POST /api/drill/start` 的 `trainee_id` 来自请求体

可以给别人建演练会话。
**修法**：用 `identity.employee_no`。

### 判定为误报的两处

| 路由 | 参数 | 判定 |
|---|---|---|
| `GET /api/audit-logs` | `actor` | 主管**筛选**要看谁的日志，不是声明自己是谁 |
| `GET /api/summaries` | `trainee_no` | 主管筛选参数；学员传了已被用例层强制覆盖 |

### 顺带补齐的两处

## 8.5 案例详情按角色裁剪（已修，2026-10-23 用户确认方案）

### 问题

`GET /api/cases/{id}` 把评阅侧信息一并返回给学员。FR-050 原文：
「参考答案、评阅标准应设为受限级别，**仅主管可见**」。

实测 C01 的字段内容：

| 字段 | 实际值 | 性质 |
|---|---|---|
| `judgement_note` | 「出现「有」+ 产品名，或「没有」。不能是"好像有"…」 | **评分标准原文** |
| `weight` | `20` | 分值 |
| `focus` | 「功效边界 + 不承诺」 | **考察点** |
| `trigger_note` | 「学员报完产品信息后」 | 流程控制 |

`judgement_note` 和 `focus` 基本等于把答案给了学员。

### 决策（用户确认）

| 字段 | 学员 | 主管 | 理由 |
|---|:---:|:---:|---|
| `element_id` / `name` | ✅ | ✅ | 不给就不知道该说什么 |
| `required` | ✅ | ✅ | 知道哪些必答 |
| `weight` | ❌ | ✅ | 会给学员「只为高分答」的导向 |
| `judgement_note` | ❌ | ✅ | 这是评分标准 |
| `follow_up.question` | ✅ | ✅ | 客户会问什么，演练必须知道 |
| `focus` | ❌ | ✅ | 等于提前给答案 |
| `trigger_note` | ❌ | ✅ | 流程控制信息 |

### 实现

**服务端按角色构造**，不是「先全给再让前端隐藏」：

```python
def _element_view(e, *, is_manager: bool) -> dict:
    if is_manager:
        return {..."weight": e.weight, "judgement_note": e.judgement_note}
    return {"element_id": ..., "name": ..., "required": ...}
```

> ★ 为什么必须服务端做：前端隐藏只是不显示，抓包照样能拿到。
>   字段不在响应体里，才是真的权限控制。

### 实测对比

```
学员：{"element_id":"E1","name":"明确回答有 / 没有","required":true}
主管：{"element_id":"E1","name":"明确回答有 / 没有","weight":20,
       "required":true,"judgement_note":"出现「有」+ 产品名，或「没有」…"}

学员：{"follow_up_id":"F1","question":"我体检说血脂有点高，吃这个管用吗？"}
主管：{"follow_up_id":"F1","question":"…","trigger_note":"学员报完产品信息后",
       "focus":"功效边界 + 不承诺"}
```

学员响应体里 `judgement_note` / `weight` / `focus` **全部不存在**。

### 新增测试 8 条

`test_idor_scan.py::TestCaseDetailContentPermission`：
- 学员看不到 4 个敏感字段（逐字段断言）
- 学员仍能看到 `name` 与 `question`（不能过度裁剪）
- 主管能看到全部
- **响应体字符串里不含这些字段名**（证明是服务端过滤，不是前端隐藏）

测试：1104 → **1112 passed**
