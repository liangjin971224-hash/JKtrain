## 2. ⚠️ 先说清楚：这不是性能优化，是架构冲突

流式和「护栏必经」天然冲突：

| 做法 | 结果 |
|---|---|
| 边收 token 边发给用户 | 违规内容在检测前就展示了 → **违反约束 #1** ❌ |
| 收完全文再发 | 没有流式体验，P95 依旧 3–5s ❌ |
| **分句缓冲 + 逐句过护栏** | 已发出的每一句都过了护栏 ✅ |

**核心保证**：**已 emit 的每一句都通过了护栏**，所以「输出必经护栏」在流式下依然成立。

```
LLM token 流
    ↓  SentenceBuffer：缓冲到切分点
完整片段
    ↓  OutputGuardrail（带上下文）
通过 → emit      不通过 → 截断，后续全部丢弃
```

## 3. 首块延迟实测（优化前后）

### 3.1 优化前后对比

| 版本 | 首块延迟 | 说明 |
|---|---|---|
| 非流式（改前） | 3.0–5.0s | 等全文 |
| 流式 v1（只按句号切） | **3.70s** | 等第一整句（约 60 字） |
| **流式 v2（逗号提前切）** | **1.18s（中位）** | 当前版本 |

**关键发现**：流式 v1 几乎没收益——因为第一句太长，等句号等于等大半篇。
原生首 token 只有 **0.46s**，但按句号切分后变成 3.70s，**91% 的收益被丢掉了**。

### 3.2 6 条查询实测分布

| 查询 | 首块 | 总耗时 | 块数 |
|---|---|---|---|
| 你们有没有量子能量水（拒答） | **0.06s** | 0.06s | 1 |
| 吃了能停降压药吗 | **0.56s** | 2.38s | 15 |
| 鱼油适合哪些人 | 1.02s | 4.47s | 26 |
| 在吃阿司匹林能吃鱼油吗 | 1.18s | 2.73s | 10 |
| 客户说太贵了怎么应对 | 1.63s | 11.96s | 60 |
| 鱼油有什么功能 | 3.15s | 4.38s | 8 |

| 指标 | 值 |
|---|---|
| 首块 min / 中位 / max | 0.06 / **1.18** / 3.15s |
| 总耗时 min / 中位 / max | 0.06 / 4.38 / 11.96s |

### 3.3 仍需说明的两点

**（1）「鱼油有什么功能」首块仍要 3.15s**

原因：第一句 `康源牌鱼油软胶囊（P001）是保健食品，` 有 20 字才到第一个逗号，
而 LLM 生成 20 字需约 3s。这不是实现问题，是**这句话本身开头就长**。

可进一步优化：把 `FIRST_CHUNK_CHARS` 降到 12（约 2 秒），
代价是切分更碎、跨段检测压力更大。当前值 24 是保守选择。

**（2）「客户说太贵了怎么应对」总耗时 11.96s**

原因：LLM 输出了 60 块（约 600 字），生成量大。
首块 1.63s 是可接受的——用户 1.6s 后就看到内容了，虽然全文要 12s。
**这正是流式要解决的核心问题：感知延迟 ≠ 完成延迟。**

## 4. ★ 新引入的风险与修法（真机踩坑）

### 4.1 逗号切分破坏了跨段规则匹配

**为了让首块快点，允许在逗号处切分。但这打破了一条规则的前提。**

**现象**：合规回答 `它不用于降血脂治疗，` 被拦了。

**根因**：

```
原句：它不用于降血脂治疗，也不具有护心作用。
切成：「它不用于」 + 「降血脂治疗，也不具有护心作用。」
                                  ↑ 单独看就是违规命中
    `_NEGATED_CLAIM` 要求「否定词」与「功效词」**紧邻**，
    切开后紧邻关系断了，否定词在前一段里看不见。
```

**修法**：检测时带上前文 20 字作为上下文，让紧邻关系恢复：

```python
probe = self._recent_text[-CONTEXT_TAIL_CHARS:] + text
```

**为什么是 20 字**：`_NEGATED_CLAIM` 用 `{0,14}` 匹配中间插入语，留 6 字余量。

**配套保护**：只保留「命中位置落在当前片段内」的违规，
避免上下文里的旧命中重复触发。

### 4.2 这个修法本身的风险：会不会变成「什么都放行」？

**必须有测试守住**。加了 6 条回归测试：

| 测试 | 守什么 |
|---|---|
| `test_negated_claim_not_blocked_across_chunks` | 4 种否定陈述在逗号切分下不被误拦 |
| `test_real_violation_still_blocked_across_chunks` | 带上下文后真违规仍拦 |
| `test_context_does_not_leak_into_output` | 上下文只用于检测，不重复拼进输出 |
| `test_first_chunk_arrives_before_full_sentence` | 首块确实早于整句完成 |

### 4.3 流式下主备切换的能力变弱（必须如实说明）

| 场景 | 非流式 | 流式 |
|---|---|---|
| 首帧就失败（401/超时） | ✅ 可切备用 | ✅ 可切备用 |
| **生成中途失败** | ✅ 可切备用 | ❌ **不可切**，直接抛异常 |

**为什么不能切**：已经向用户吐了前半段，再切备用会导致
「前半段千问 + 后半段 DeepSeek」+ 内容重复。

**取舍**：拿延迟收益，换「中途故障不可切」。
判断：中途故障概率远低于首帧失败，对演示场景值得。
代码里已明确注释这个限制。

## 5. 一个门禁挡住的设计错误

**初版把 `generate_stream` 写成端口的「带默认实现的方法」**（退化调用 `generate`），
想让现有适配器无需改动。

门禁立刻失败：

```
AssertionError: language_model_port 中存在未声明 abstractmethod 的公开方法
  （Port 只应声明能力，不含实现）: ['LanguageModelPort.generate_stream']
```

**门禁是对的**：端口里有实现就是架构腐蚀的开始——今天一个方便的默认实现，
明天就会有人在端口里塞业务逻辑。

**修法**：改为 `@abstractmethod`，在测试替身里各自实现「退化版」。
代价是所有实现类都要加一个方法，但这正是「显式契约」的应有代价。
