# 违规内容标注与部分保留

> ⚠️ **本阶段的遗留项可能有部分已完成** ——
> 最新汇总见 `文档/未完成事项清单.md`（2026-10-23 逐条核实过）。

> 日期：2026-10-23
> 产品决策：拦下的违规内容不删掉，标红展示 + 说明原因，其余合规内容保留

---

## 1. 为什么改

### 改之前：整段拒答

只要有一句违规，整篇文章都不给：

```
问：康源牌黑芝麻丸有什么功能
答：（整段拒答）关于这个问题，我不能按您期待的方式作答……
```

**问题**：LLM 原本答对了前两句（普通食品、配料、规格），只错最后一句「乌发养颜」。
整段拒答等于把正确信息一起丢掉，**学员什么也学不到**。

### 这是培训系统，不是客服系统

| 场景 | 诉求 |
|---|---|
| 客服系统 | 宁可少说，绝不能说错 → 整段拒答合理 |
| **培训系统** | 学员要知道「**这句话为什么不能说**」→ 必须让他看见 |

所以改成：**违规句标红保留 + 给出原因，合规内容正常输出**。

---

## 2. ★ 核心安全设计：双轨输出

「标红展示违规内容」有一个真实的合规风险：

> 违规表述仍然出现在返回体里，被复制 / 被日志采集 / 将来开放给客户查询，
> 就成了对外传播违法宣传 —— 与「输出护栏是必经节点」这条硬约束冲突。

**解法：一个接口，两个字段，各司其职。**

| 字段 | 内容 | 谁用 |
|---|---|---|
| `answer` | **剔除违规句后的纯合规版** | 对外安全。接口调用方、日志、剪贴板都拿这个 |
| `annotation.segments` | 逐句结构，含违规原文 + 原因 | 只给前端渲染标红 |

于是：
- 前端能标红教学（学员看得到「为什么不能说」）
- 复制正文 / 落日志 / 第三方调用拿到的是合规版本
- 二者从同一次分析产出，不会不一致

---

## 3. 三个必须守住的不变量

### ① safe_text 必须整体通过护栏

逐句删不等于删干净——拼回去可能出现新的跨句违规。
所以删完必须**再整体验一次**。

### ② 不能因为删除而引入新的违规

最危险的形态是「否定依赖」：

```
原文：「本品不是药物。但可以治疗糖尿病。」
删掉前半句 → 「但可以治疗糖尿病。」   ← 反而更像在宣称
```

检测到残留内容里有以转折词开头的句子 → **放弃部分保留，退回整段拒答**。

### ③ 警示语被误删时要补回

警示语若恰好和违规句在同一句里被删，`safe_text` 会变成「保健食品缺警示语」。
此时补回法定警示语（这是必须出现的内容，不是可选）。

## 4. 实现

### 4.1 数据结构

```python
@dataclass(frozen=True)
class AnswerSegment:
    text: str                      # 句子原文（含违规原文）
    ok: bool                       # 是否合规
    rule_types: tuple[str, ...]    # 类别标签，如「疾病治疗」
    reason: str                    # 给学员看的原因

@dataclass(frozen=True)
class AnnotationResult:
    safe_text: str                 # 剔除后合规版，可直接对外
    segments: tuple[AnswerSegment, ...]
    reason: str                    # 无法产出安全版时的说明
    repaired_warning: bool         # 是否补回过警示语
```

### 4.2 接口

```json
{
  "answer": "康源牌黑芝麻丸是普通食品。\n\n配料为黑芝麻和蜂蜜，每丸10g。",
  "refused": false,
  "annotation": {
    "has_safe_content": true,
    "segment_count": 3,
    "violation_count": 1,
    "segments": [
      {"text": "康源牌黑芝麻丸是普通食品。", "ok": true, "rule_types": [], "reason": ""},
      {"text": "配料为黑芝麻和蜂蜜，每丸10g。", "ok": true, "rule_types": [], "reason": ""},
      {
        "text": "黑芝麻有乌发养颜的功效，可以补钙。",
        "ok": false,
        "rule_types": ["普通食品不得声称功效"],
        "reason": "普通食品不得作任何保健功能声称（违反《食品安全法》）。可改为客观描述配料、规格、食用方法。"
      }
    ]
  }
}
```

### 4.3 前端渲染

- 违规句：红底 + 删除线 + 红色类别标签 + 「为什么不能说」说明
- 合规句：正常显示
- 顶部黄色提示条：说明有几处违规、已标红
- 徽标状态：「部分合规（N 处违规）」

### 4.4 流式的取舍

**流式保持原行为**（违规即截断），并在结束时提示：

> 流式模式下一旦命中违规就会立即截断。想看到「哪句话违规、为什么不能说」，
> 请关闭右上角的「流式输出」再问一次。

理由：流式的价值是「快」（边生成边展示），标注的价值是「学」（要看完才能分析）。
两者诉求冲突，不该混在一起。

## 5. ⚠️ 过程中发现的 5 个真实缺陷

### 5.1 ★★ 单句检测跳过警示语 → 合规底线被绕过

**问题**：逐句检测用 `check_warning=False`（警示语是整段属性，单句不含是正常的）。
但如果逐句全通过就**直接返回**，会完全跳过警示语检查——

一个缺法定警示语的保健食品回答被判成「全部合规」。

**修法**：逐句全通过后，仍要整段再验一次；缺警示语则补回。

### 5.2 ★★ 普通食品判定用另一套正则，没共用合规放行逻辑

**问题**：`check_forbidden_claims` 有一整套合规挖除链（引述、否定陈述、名词短语等），
但 `product_category.check_claim_allowed` 用的是**裸正则**。

结果：

```
「普通食品不能宣称任何保健功能或疾病预防、治疗作用。」
```

—— 这是《广告法》原文式的禁令陈述，完全合规，却被判「命中治疗」。

**修法**：把挖除链提取成 `neutralize_compliant()`，两处共用。

这正好印证项目里的老教训：**同一套标准只能有一份实现**。

### 5.3 「有助于 X」放行名单没按类别区分

**问题**：`_COMPLIANT_PHRASES` 里混了 8 条「有助于增强免疫力」这类**保健食品批准功能原文**。
它们对保健食品必须放行，对普通食品必须拦截。混在一起导致：

```
「有助于增强免疫力」 对普通食品 → 漏放
```

**修法**：拆成两组
- `_COMPLIANT_PHRASES`（A 组）：任何类别都合规 —— 警示语、边界话术
- `_HEALTH_FOOD_ONLY_PHRASES`（B 组）：仅保健食品合规 —— 批准功能原文

`neutralize_compliant(text, allow_youzhuyu=False)` 按类别控制。

### 5.4 指称语境被误拦（培训场景高发）

**问题**：

```
「乌发属于功能暗示，不符合普通食品的法规要求，因此不能这样表述。」
```

这是在**解释法规**，是培训系统最该说的话，却因含「乌发」被拦。

**修法**：新增 `_strip_named_terms()`，识别两类指称语境：
1. 被引号括起来：`「乌发」是功能暗示`
2. 带评价性谓语：`X 属于/是 功能暗示/违规/禁用`

关键区分：

| 表述 | 性质 | 判定 |
|---|---|---|
| 乌发**属于功能暗示** | 指称（在说这个词不能用） | ✅ 放行 |
| 黑芝麻**有乌发养颜的功效** | 使用（在宣称效果） | ❌ 违规 |

### 5.5 词表缺口：「治好」类

**问题**：`DC-01` 只覆盖 `治疗|治愈|根治`，但「**治好**」「药到病除」不在表里。

实测漏放事故：

```
「❌ 不能说：治疗，我们这个确实能治好」
```

前半句是反例教学（应放行），后半句「能治好」是真实宣称（必须拦）——
但因为「治好」不在词表，整句被判合规。

**修法**：`DC-01` 补上 `治好|医治|药到病除`。

---

## 6. 另一处误拦：JD-02 的「能+用」太宽

**问题**：

```
「保健食品不能用」 里的「能用」被 JD-02 配上 → 判「越界判断同服」
```

而那句是禁令陈述，完全合规。

**修法**：加负向断言 `(?<![不没别勿禁])`，排除前面有否定词的。

## 8. 遗留

| # | 问题 | 说明 |
|---|---|---|
| 1 | 流式不支持标注 | 只能提示用户切非流式；若要支持需重构 stream_guard |
| 2 | 真实 LLM 输出很少触发标注 | 说明提示词约束有效；需构造用例才能演示标红 |
| 3 | 标注原文的日志风险 | **已决策：方案 A（约定，不做技术强制）**，见下 |

### 8.1 决策：方案 A —— 靠约定，不做技术强制

**结论（2026-10-23 用户确认）**：`annotation.segments` 只给前端渲染，
**不做** UA 白名单、域名限制等技术手段，靠调用方遵守约定。

**理由**：

| 考虑 | 说明 |
|---|---|
| 收益不抵成本 | 现在只有内部前端一个消费方，加限制属于过度设计 |
| 技术手段可绕过 | UA 可伪造，真要做可靠隔离得走鉴权（P8） |
| 已有安全出口 | `answer` 本身就是合规版本，正常用法不应读 `annotation` |

**约定落地位置**（三处，都能查到）：

1. `AskResponse` 的类文档：一张「字段 → 允许用途」对照表
2. `AskSegment.text` 的字段描述：标明"可能含违规原文"
3. `POST /api/ask` 的接口描述：`/docs` 里直接可见

> ★★ 字段使用约定：
> - **`answer`** = 合规版正文，可直接对外（展示 / 复制 / 日志 / 转发）
> - **`annotation`** = 逐句明细，**含违规原文**，仅限前端渲染标红

### 8.2 什么时候必须改方案（触发条件）

出现以下任一情况，方案 A 就不够了，必须升级：

| # | 触发条件 | 建议方案 |
|---|---|---|
| 1 | 接口对外开放（第三方/客户可调用） | 方案 B 或 C，配合 P8 鉴权 |
| 2 | 实现请求日志（会把响应体一起记） | 日志侧脱敏：剔除 `annotation` 字段 |
| 3 | 要做用户行为分析，需要落库 | 只落 `answer` + `violation_count`，不落原文 |
| 4 | 多人协作，担心有人误用 | 方案 B（非浏览器 UA 不返回） |

**最需要注意的是第 2 条**：一旦加了访问日志中间件，
如果它记录响应体，违规原文就会自动进日志——那时必须同步做脱敏。
